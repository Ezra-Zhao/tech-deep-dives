# It Takes Another 47% Before It Complains: Measuring the Discrimination of the 0.75 Injection-Band Alert

Author: Guangyi Zhao

## 1. Background

One of the ten alert rules in net-assurance-lab exists for the fault scenario itself. fault_sustained is *supposed* to lose more than half its packets — the proxy drops 20% uniformly at random in each direction, plus a link-flap window that closes for 0.6 s in every 2.5 s period — so the baseline "loss above 5%" regression alerts are meaningless for it. Its own sanity-band alert, NalFaultLossAboveInjectionBand, asks a different question: if end-to-end loss exceeds 0.75, something other than the configured injection is dropping packets, and the run must not be attributed to the injection parameters alone. The rule's annotation puts the loss the injection can explain at "roughly 50–65%", with 0.75 set as headroom above that band.

In my 2026-10-24 audit of this alert chain I verified the threshold boundary: fixtures pushed through the exporter's real code path showed no firing at exactly 0.75 and firing at 0.80, so the greater-than semantics are correct. But a correct boundary is not correct discrimination. That article booked the open question explicitly: no "loss beyond the injection" scenario had ever been constructed, so neither the detection side (does it fire when out-of-band loss is real, and how much does it take?) nor the false-positive side (how far is injection alone from 0.75, and can run-to-run jitter push it over?) had been measured. This article settles that account.

First, the injection band itself, because everything else is relative to it. The proxy decides flap first, random loss second (decide() in src/fault_proxy.py: flap_is_down is checked first, and only survivors face the random drop). The flap duty cycle is 0.6/2.5 = 24%, so one leg survives with probability 0.76 × 0.80 = 0.608 — a per-leg loss of 39.2%. End-to-end traffic crosses two legs, and the answer depends on how the two legs' flap exposure correlates: fully independent legs give 1 − 0.608² = 63.0% loss; fully correlated legs give 1 − 0.76 × 0.80² = 51.4%. The annotation's 50–65% is exactly that correlation-uncertainty interval, not a hand-waved range. Where the real chain sits inside it is answered with a per-direction decomposition in Section 3.1 — closer to the edge than I expected.

The question, split in two: with the injection parameters untouched, add one more independent drop stage on the server side (probability q, client-to-server only, and only for packets that already survived the injection). How large must q be before the rule fires? And at q = 0, how far is it from firing spuriously? The headline: with bench noise isolated out, the rule is a step, not a slope. At q = 0.40, zero of four repeats fired (maximum 0.7324); at q = 0.50, all four fired (minimum 0.7678); the model puts the critical point at q* ≈ 0.47. In other words, almost half of the packets that survived the injection must additionally die on the server side — about 22 more points of end-to-end loss on top of the injection — before this alert can see anything at all. On the false-positive side it is conservative to the point of waste: across 2,000 model trials at q = 0 there is not one crossing, the live maximum is 0.5381, and the line sits 21 points away. Those 22 points between are the width of its blind zone.

## 2. Method

The design was frozen before the first run and is written into the bench script's header (data/2026-10-28-injection-band-bench.py), together with the grid and the seed rules:

- Live layer, all real lab components on loopback. Traffic identical to fault_sustained: traffic_gen in sustained mode, 2,000 pps for 5 s (10,000 packets), 256-byte packets, 1.5 s drain grace. The chain is traffic_gen → fault_proxy (loss 0.20, delay 40 ms, jitter 30 ms, flap 0.6/2.5, seed 1234 — byte-identical to the fault scenario in run_experiment.py) → extra-drop shim → echo_server. The shim is a small UDP relay I wrote for this experiment (data/2026-10-28-injection-band-shim.py): on the client-to-server direction only, it discards each arriving packet with probability q and counts the decision; the return path is forwarded untouched. Every packet it drops had already survived the injection, and the server never gets the chance to echo it — the most literal implementation of "extra loss on the server side". Its realised drop rates stayed within ±0.011 of nominal q in every run (e.g. 0.589–0.597 at q = 0.60; 0.093–0.100 at q = 0.10), so the shim's own books balance first.
- Grid: q in {0, 0.10, 0.20, 0.30, 0.40, 0.50, 0.60}, four repeats each, 28 runs. The extra-drop seed differs per run; the proxy seed is fixed at the lab default 1234; ports rotate per run. Four logs per run (generator summary, proxy per-packet JSONL, shim counters, server counters) are all kept, and total loss must decompose stage by stage — a run whose books do not balance does not enter the conclusions.
- The alert verdict travels the real path: each run's artifacts are assembled into a minimal results directory and pushed through the exporter's real collect() code, nal_loss_ratio{scenario="fault_sustained"} is read back out, and the rule expression (> 0.75) is evaluated on that value. In all 28 runs the exporter value equalled the generator summary value exactly.
- Model layer: a NumPy replica of the proxy's decision logic (flap first, Bernoulli loss per leg, the injected delay shifting the return leg's flap phase, the shim acting on the forward leg only), 2,000 trials per q value, flap phase uniform on [0, 2.5) s. It is a model, not a measurement; its job is to draw the detection-probability curve finely, and its q = 0 distribution has to match the live and archived runs before it is allowed to say anything. One known difference from the live proxy: the live code shares one RNG stream across both directions, the replica uses independent streams. Every draw is Bernoulli(0.20) either way, so the loss law is unchanged; only draw correlation differs, and there is no correlation structure there to preserve.
- Analytic layer: the two correlation extremes for the band (51.4% and 63.0%, Section 1), and the critical q obtained by solving total loss = 0.75 for a given injection-side loss L: q = 1 − 0.25/(1 − L). Arithmetic, not measurement — a reference frame for the other two layers.

One disclosure about reporting: the decomposition exposed a confounder the original design did not anticipate (bench-side loss between generator and proxy, Section 3.2), so results are reported on two curves. The *as-deployed* curve is the total loss the exporter actually sees, which is what the rule fires on. The *isolated* curve counts only packets that entered the proxy (the proxy's in_client as denominator), stripping bench noise out and measuring the shim stage's discrimination alone. Both are reported; picking the prettier one is not an option.

## 3. Measurements

### 3.1 The q = 0 anchor: the band sits at the correlated end

With no extra drop, injection alone produced:

| Source | Total loss (as deployed) | Isolated loss |
|---|---|---|
| Archived R1 (20261019-154535) | 0.5275 | 0.5275 (zero pre-proxy loss that run) |
| Archived R0 (20261019-171627) | 0.5897 | 0.5596 |
| Live q = 0, four runs | 0.5252 / 0.5295 / 0.5334 / 0.5381, mean 0.5315 | 0.5237 / 0.5295 / 0.5273 / 0.5316, mean 0.5280 |
| Model q = 0, 2,000 trials | — | mean 0.5277, sd 0.0041, range [0.5143, 0.5424] |

Three sources agree at 0.527–0.528: a quiet archived run, the live isolated curve, and the model mean are pairwise within 0.001. R0 is the only outlier, at 0.5596 even isolated — it was the full run with packet capture active and the busiest host, and Section 3.2 returns to it.

Why does the band land at the low end of the 51.4–63.0% interval, hard against the fully-correlated bound? The per-direction books (live q = 0, four runs pooled): flap drops on the forward leg took 23.97% of the proxy's input — the 24% duty cycle itself. Flap drops on the return leg took only 3.30% of the echoes entering the proxy. The mechanism is plain: an echo is only generated by a packet the forward leg forwarded during an up window, and it comes back 40–70 ms of injected delay later; for that echo to land inside a down window, its forward forwarding must have happened within one delay (at most 70 ms) before the window opened. At a median delay of about 55 ms the expected share is roughly 55/2500 ≈ 2.2%; the measured 3.30% is the same order. The flap, in effect, applies once, not twice. Reassembling from the measured shares: return-leg survival = 1 − 0.0330 − 0.1943 = 0.7727 (the random-loss share 0.1943 matches 0.20 × (1 − 0.033) = 0.1934, confirming the flap-first ordering in the accounts), predicted end-to-end loss = 1 − 0.608 × 0.7727 = 0.5302, within 0.0022 of the measured isolated mean 0.5280. Archived R1 has the same share structure (forward flap 24.09%, return flap 3.05%), which is why its 0.5275 landing on today's number is not a coincidence.

### 3.2 The confounder: the bench itself drops packets, and not a few

The 28 decompositions contain one loss stage the design did not schedule: the generator sent 10,000 packets every run, but the proxy's in_client was not always 10,000. In the four q = 0 runs the gap was 0–139 packets (at most 1.4%); as the run sequence progressed it grew, peaking at 2,983 packets (the second q = 0.20 run, 29.8% of everything sent). Every other hop's books balance exactly — proxy-forwarded vs shim-input differs by 145 packets in one run and zero in the other 27; shim-forwarded equals server-received, server-echoed equals shim-return-input, and proxy-return-forwarded equals generator-received, in every run. The loss sits on the generator-to-proxy hop's UDP receive path: host scheduling and receive-buffer noise on this machine, the same species of bench jitter that put the baseline p99 on opposite sides of its threshold in two runs of the 2026-10-24 article — except this time it is large enough to move conclusions.

The response is not to delete those runs but to report the two curves separately (Section 2). And the confounder deserves a name, because it looks exactly like the signal under test: to the exporter, a packet eaten by the bench's receive path and a packet eaten on the server side are the same thing — a packet that never came back. Its effect on the detection and false-positive sides is accounted separately below.

### 3.3 Detection side: a step at q ≈ 0.47

Isolated curve, four repeats per grid point:

| q | Isolated loss, mean | Isolated loss, range | Fired |
|---|---|---|---|
| 0 | 0.5280 | 0.5237–0.5316 | 0/4 |
| 0.10 | 0.6043 | 0.5881–0.6255 | 0/4 |
| 0.20 | 0.6549 | 0.6382–0.6658 | 0/4 |
| 0.30 | 0.6939 | 0.6858–0.7051 | 0/4 |
| 0.40 | 0.7299 | 0.7248–0.7324 | 0/4 |
| 0.50 | 0.7747 | 0.7678–0.7812 | 4/4 |
| 0.60 | 0.8123 | 0.8050–0.8163 | 4/4 |

The model's version of the same curve (2,000 trials per point): means 0.5277 / 0.5751 / 0.6223 / 0.6694 / 0.7166 / 0.7640 / 0.8111, with firing probability 0 at q = 0.40 (maximum of 2,000 trials: 0.7305) and 1 at q = 0.50 (minimum: 0.7519). The live isolated means sit 1–3 points above the model in the middle of the grid (+2.9 points at q = 0.10, +3.3 at q = 0.20, +1.1 at q = 0.50, converging at the top): in the loaded runs the proxy's decision time lags packet arrival, the pooled forward flap share over the whole grid rises to 26.96% (against 23.97% in the quiet q = 0 runs), and the injection-side baseline is lifted wholesale. But live and model agree on the conclusion: there is no transition band. The live maximum at q = 0.40 (0.7324) and the live minimum at q = 0.50 (0.7678) leave a 3.5-point gap between them. Two methods put the critical point in the same place: solving the algebra at L = 0.5277 gives q* = 0.4707; linearly interpolating the model means between q = 0.40 and 0.50 up to 0.75 gives 0.4705. With a model standard deviation of only 0.0041, the step's width in q (firing probability from near 0 to near 1) is about ±0.01. This is not a detector with gradually rising sensitivity; it is a switch that flips at 0.47.

Translated into operations language: packets surviving the forward injection are about 60.8% of everything sent. The server side must discard 47% of those — roughly 28.6% of all sent packets dying on the server side, 22.2 points of end-to-end loss stacked on the 52.8% injection baseline — before this alert gets its first chance to fire. A server-side fault at q = 0.40, already eating four in ten of the surviving packets, is indistinguishable from perfect health as far as this rule is concerned.

### 3.4 As deployed: the two early firings are the bench talking

The rule consumes total loss, and on that curve firing starts earlier: 1/4 at q = 0.20, 1/4 at q = 0.30, 3/4 at q = 0.40, and everything from q = 0.50 up. But the decompositions name the culprit in both early firings — they are the two runs with the largest bench gaps. The q = 0.20 run that fired read 0.7655 in total but only 0.6658 isolated, with a 29.8% pre-proxy gap; the q = 0.30 firing read 0.7693 total, 0.7051 isolated, gap 21.8%. And the third firing at q = 0.40 crossed at 0.7502 — a margin of 0.0002 — with an isolated value of 0.7314; a 7.0% bench gap pushed it over the line.

This is not the rule misfiring. Its annotation says "above 75%, something beyond the configured fault is dropping packets", and the bench's receive path *is* something beyond the configured fault, so semantically it told the truth. But attribution ends there: the exporter's total loss carries no information about which stage dropped the packets, and the same 0.7655 can be the server dropping, the bench dropping, or each dropping half. Anyone who wants to read this rule as "the server side is losing packets" has to lay the decomposition next to it first; fired only means *something* is wrong, never *where*.

### 3.5 False-positive side: a 21-point margin, and its condition

Distance from a spurious firing at q = 0: live total loss peaked at 0.5381 (margin 21.2 points), the model's 2,000 trials peaked at 0.5424 (margin 20.8 points), the quiet archived run read 0.5275. Running the same algebra backwards: with isolated loss at 0.5277, bench loss alone would have to consume 47.1% of everything sent before total loss crossed 0.75 — the largest bench gap observed in this session is 29.8%, and the 2026-10-19 full run R0 had 6.84% (684 packets). Both are far away. The injection's own random fluctuation is not a contender either: at 10,000 packets and a model sd of 0.0041, 0.75 sits about 54 standard deviations above the mean.

The condition attached to that comfort must be written down: it holds as long as bench loss stays in its observed range. On this host the bench gap ranged from 0.3% to 29.8% across just 28 runs, drifting with load and with no knowable prior bound; 47.1% is not physically impossible, merely unobserved here. The annotation's 0.75 reads, in my measurements, as an empirical bound that is conservative *under this bench's load profile* — not as an environment-independent constant. Move the bench to a busier host and the false-positive margin has to be measured again.

## 4. Analysis and Trade-offs

Side by side, the rule's character is clear: it is a sanity band that bought false-positive safety first. The purchase is real — under unchanged injection parameters it essentially cannot be pushed over by the injection's own fluctuation (zero crossings in more than 2,000 combined live and model observations at q = 0), so a firing can safely be read as "out-of-band loss exists". The price is equally real: a blind zone q ≈ 0.47 wide, about 22 end-to-end points, inside which server-side loss from mild to severe (one, two, three, four tenths of the surviving packets) draws complete silence from this rule. For a scenario whose design point is "half the packets die on purpose", the trade is not absurd: narrow the band and bench noise starts firing it (see below), destroying exactly the attribution value it exists for. Placed here, it fires late — but when it fires, it is right.

The same recorded numbers answer the obvious follow-up: what if the threshold were 0.70 or 0.65? (This is a re-evaluation of measured values against a different line, not a new experiment.) On the isolated curve, 0.70 starts firing at q = 0.30 (1/4) and is full at q = 0.40, with q* falling to about 0.36; at 0.65, q = 0.20 already fires 3/4 and q* falls to about 0.26. The sensitivity really does come back. But the false-positive ledger has to be settled in the same breath: at a 0.65 threshold, the bench gap needed to cross the line on bench loss alone drops to 25.9% — *below* the 29.8% actually observed in this session. Under a 0.65 rule, a run with perfectly normal injection on a merely busy host could cross on bench loss alone. (That this session's four q = 0 totals all stayed under 0.5381 is because those runs happened to run on a quiet host; it is not evidence that 0.65 is safe.) At 0.70 the required gap is 36.5%, above this session's maximum — a margin that is thin but not yet breached. My judgement (engineering judgement, evidence grade B): tuning the single number is a dead end. The defect of 0.75 is not the digit but the observable — total loss stirs three loss stages into one number. The exporter already publishes the proxy's per-stage counters (nal_fault_proxy_packets_total and friends); alerting on the *gap* between the end-to-end loss those counters predict and the measured end-to-end loss is what could keep the sensitivity and the attribution at once. That variant was neither implemented nor measured in this round; it is recorded as a direction, not dressed up as a finding.

One reading note, continuous with the 2026-10-24 article: this rule's for: is 1m, and the exporter publishes snapshots of finished runs, so for: measures how long a bad snapshot has been scraped, not how long a network condition persisted. "Firing" in this article means the expression holds on a single run's data, independent of the time condition; carrying the discrimination results to a streaming-exporter deployment adds for: and the evaluation interval to the detection delay, and that bill is outside this article's scope.

## 5. Limitations and Open Questions

- All live evidence comes from loopback on one host and its load profile: the bench-gap distribution (0–29.8%) is a measurement of this machine in this window, not a constant of any other environment. q* ≈ 0.47 has the injection baseline 0.5277 inside it; change the injection parameters and it must be recomputed and remeasured.
- Four live repeats per grid point give a firing-rate resolution of 25 points; the curve's shape (step position and width) leans on the model's 2,000 trials per point, and the model sits 1–3 points below live in the middle of the grid (attributed in Section 3.3 to the bench raising the injection baseline), so q* should be read as an interval of roughly 0.45–0.48, not the single point 0.4707.
- The model samples flap phase uniformly; the live phase is set by start-up timing and is nearly fixed. Phase sensitivity is available only through the model (its q = 0 5–95 percentile width is just 0.0136, so phase is not the main term), and no dedicated live phase sweep was run.
- The shim drops forward requests only, modelling a server side that discards on receive. A real fault dropping the server's *replies* has the same end-to-end algebra (survival probabilities multiply), but a different decomposition shape; no return-path drop control run was made.
- R0's isolated 0.5596 is still not fully explained: the known raisers (concurrent capture, a 684-packet bench gap) account for the direction, and whether they account for the full amount was not separately re-verified. It does not touch the main conclusions — the other three anchors interlock — but it stays on the books as an open residue.
- Open: the decomposition-aware alert proposed in Section 4 (predicted vs measured end-to-end loss) is unimplemented, and its immunity to bench gaps is reasoning, not measurement. Separately, the drift of the bench gap across the run sequence — its quantitative relation to host load — was observed but not put under controlled experiment.
