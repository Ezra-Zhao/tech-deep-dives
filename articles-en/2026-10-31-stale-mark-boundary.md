# Add a Timestamp to the Sample and the Blind Window Goes Back to Six Minutes: Measuring the Boundary of the Stale Mark

Author: Guangyi Zhao

## 1. Background

When I measured blind-spot alerts on 2026-10-27, one cell of my preregistration was overturned live. I had budgeted the absent() blind window for a killed exporter at 360–380 s, assuming a disappeared series stays visible until the 5-minute lookback expires. The measurement was about 75 s. The correction, written up in section 3.3 of that article, is that on the ordinary scrape path Prometheus marks a series stale the moment a scrape stops returning it, and the stale mark voids the lookback on the spot. But that article also left a boundary booked as reasoning only (evidence grade B, never measured): the official documentation's Staleness section names an exception — exporters whose samples carry their own timestamps keep their last value visible for the full lookback after they stop sending. This article takes that boundary live, along a second path that has no scrape bookkeeping of its own.

"No scrape bookkeeping" splits in two, and the two paths I test turn out to be opposites:

- The timestamped path (T): the exporter writes an explicit timestamp on every sample. The sample's time is decided by the exporter's own clock, not by the scrape moment.
- The recording-rule path (R): a recording rule replicates the present series under a new name, nal_present_recorded, and absent() watches the replica. The replica is bookkept by nobody's scrape; its samples come from rule evaluation. Intuition says that might dodge the scrape layer's stale mark — but the documentation lists "a rule evaluation no longer returns a sample" alongside scrapes as a trigger for marking a series stale. Whether the intuition or the documentation is right is a measurement, not an argument.

The headline: the reasoning about T holds. Its blind window is 369.4–373.8 s, roughly five times the ordinary scrape path (74.2–75.5 s, re-measured here). The intuition about R fails. In a single kill event, the replica's absent alert and the original's enter pending in the same evaluation cycle, with microsecond-identical activeAt, and fire in the same interval (74.1–75.2 s). The boundary of the stale mark is not who produces the series. It is who provides the sample's timestamp.

## 2. Method

One measurement discipline for all three paths: Prometheus 3.15.0 (official tarball, 111,651,578 bytes, gzip verified; the version was chosen for comparability with the 2026-10-24 and 2026-10-27 articles, not for any new feature), a separate instance with a fresh TSDB per path, scrape interval 5 s, scrape timeout 4 s, rule-group evaluation 15 s, and for: 1m on every absent alert. Differences between paths can only come from the bookkeeping, not from tuning. The design and four preregistered predictions were frozen to disk before any live run (data/2026-10-31-stale-prereg.md).

- C, ordinary scrape (control, a re-measurement): the repository's real exporter (src/prom_exporter.py) serving a copy of run 20261019-171627; samples carry no timestamp; the alert is absent(nal_exporter_results_present{group="scenario_summaries"}), word for word the expression measured on 2026-10-27.
- T, timestamped: a minimal exporter I wrote for this test (data/2026-10-31-stale-ts-exporter.py, standard library only). Each scrape returns only the same series in its three groups, value always 1, every sample carrying an explicit millisecond timestamp taken at request time. The scrape config does not set honor_timestamps (default true). Serving a single metric family is deliberate: the only variable under test is the timestamp.
- R, recording-rule replica: scraping as in C, plus a recording group (15 s evaluation) with record: nal_present_recorded over the same present expression. Two alerts run side by side in the same kill event: absent() on the original series and absent(nal_present_recorded), so the comparison needs no cross-run alignment.

Each path runs the same phases: wait for a healthy baseline (present equal to 1; the R path also waits for recorded equal to 1), hold 30 s, SIGTERM the exporter, poll until the path's main alert fires, hold 20 s. The poller records instant queries for up, present, absent and recorded, plus the full alert snapshot, every 5 s. Blind windows are measured as in the previous article: pending from the alert API's activeAt, firing as the interval [activeAt + for:, first poll that saw firing]. promtool check rules returned SUCCESS for both rule files (1 rule in the control file, 3 in the recorded file).

One execution fact, reported plainly: during the first live run, the host restarted 5.1 s after the kill in the R phase and took the run's processes with it. Paths C and T had completed before that, with every poll already flushed to disk, so nothing of theirs was lost. The R phase was then rerun in full with a script identical to the first run's except for the plan list and output filenames; both scripts and both progress files are in data/. The R numbers below come from the rerun; the rest come from the first run.

## 3. Measurements

### 3.1 Path C: the 75-second baseline replicates

In the first poll after the kill (5.1 s), the instant query for present is already empty, absent() already returns 1, and up has flipped to 0 — all three in the same poll. The absent alert enters pending 14.2 s after the kill (the first evaluation cycle) and fires in the interval 74.2–75.5 s. Against the original 2026-10-27 measurement (pending 13.9 s, firing 73.9–75.1 s), every number agrees to within half a second across two independent live runs. The 30 s baseline and every healthy segment stayed silent. Preregistered prediction P-C (60–85 s) hit.

### 3.2 Path T: the sample outlives its source by 303 seconds

After the kill, the scrape layer knows immediately: up flips to 0 in the 5.0 s poll. But the present series does not disappear with it. It stays visible to instant queries until the poll 303.1 s after the kill, which is the first to return empty; absent() first returns 1 in that same poll. Converted to the sample's own timeline, the bracket is tight: the last poll before the kill (at most 5 s earlier) still saw present equal to 1, and up only flipped at the +5.0 s poll, so the last successful scrape fell within one scrape interval before the kill, and its sample timestamp sits in that moment. The series therefore remained visible for 303.1–308.1 s after that timestamp — the 300 s lookback plus query and evaluation alignment, exactly the "kept for the full lookback" the documentation promises.

The alert shifts by the same amount: pending 309.4 s after the kill (the first evaluation cycle after the lookback expired), firing interval 369.4–373.8 s. Prediction P-T (355–390 s) hit. Against path C, pending is 295.2 s later and the firing lower bound is 295.2 s later — one lookback (300 s) minus the roughly 5 s the ordinary path takes to go stale. The books balance.

There is also a contrast inside this one path worth naming. In path T, up flips at 5 s while absent fires at about 370 s. If this chain's only health rule were the absent one, then for six minutes after the exporter's death the series would still read 1 and the picture would look healthy. In the kill cell of the ordinary path the two rules were interchangeable; here the up rule is the only fast channel, and the division of labour stops being redundancy.

One startup race, disclosed rather than smoothed over: in path T, the first rule evaluation after Prometheus started ran before the series had ever been scraped, so the absent alert sat pending for four early baseline polls (activeAt at startup time). Once the series appeared, the next evaluation resolved it; it never fired, and the baseline was clean for the 20 s before the kill. The kill-time pending is a second, distinct activeAt (309.4 s). The race is itself a small lesson: an absent rule on a cold start naturally pends once, and for: 1m is exactly the kind of cushion that absorbs it.

### 3.3 Path R: the replica dies in the same cycle as the original

In the rerun, the poll 5.0 s after the kill shows present empty, recorded already empty, and both absent() queries returning 1. The two alerts' activeAt values are identical to the microsecond (pending at 14.1 s), and both fire in the interval 74.1–75.2 s. The recording rule's output series was staled within one evaluation cycle of the source's death — consistent with the preregistered mechanism prediction (a rule evaluation that stops returning a sample marks its output stale; predicted window 65–100 s, P-R hit), and at the fast edge of it: not even one extra evaluation alignment was spent. The original-series alert in the same run also matches path C's separate run to within 0.3 s (P-R2 hit).

Why can recorded already be empty in the 5 s poll, faster than one 15 s recording interval? The explanation consistent with the data: the source series is staled at the first failed scrape (within about 5 s), the first recording evaluation after the stale point returns empty, and Prometheus stales the replica at that moment; both steps happened to fall inside the same 5 s polling window. At 5 s poll granularity the two steps cannot be timed separately, and I record this as a data-consistent explanation, not as a measured step-by-step sequence.

## 4. Analysis

First, a decision rule that can be taken away directly. A series' absent blind window is set by its bookkeeping, and there are exactly two measured tiers. If samples are bookkept at "now" by a scrape or a rule evaluation, the stale mark lands within one scrape/evaluation cycle of the source's death, and the blind window is roughly for: plus alignment — about 75 s at this article's settings. If samples carry their own timestamps, nobody writes a stale mark for them; the series lives out the lookback, and the blind window is roughly lookback plus for: — about 370 s at the same settings. Before budgeting any blind-spot rule, establish which tier its target series is in. Checking whether the exporter stamps its samples comes before checking whether the expression is written correctly.

Second, a recording rule is not a shelter from staleness. Replicating a series under a new name through a recording rule changes the absent behaviour by zero seconds, in the same kill event, to the microsecond. The practical consequence cuts the hopeful way people reach for replicas: do not expect "record it first, then alert on the derived series" to change anything about disappearance semantics. Recording rules change computation and naming, not the bookkeeping layer. The same fact is also good news in the other direction: alerting on a derived series is not slower than alerting on the original, and this run's identical activeAt is the evidence (grade A, at this chain's settings).

Third, the timestamped tier is double-edged, and the edge belongs to exporter authors. A self-provided timestamp makes samples more honest under reordering, retries and clock questions — and it makes "I am dead" arrive five minutes later in absent()'s view. If a chain's exporter stamps its samples and its only health check is an absent rule, the blind-window budget must be written in the lookback tier, and scrape-layer signals such as up stop being optional extras: in path T they are the only fast channel, 5 s against about 370 s.

Fourth, a note on method. The 2026-10-27 article was right to book this boundary as reasoning (grade B); what promotes it to measurement (grade A) here is not cleverer reasoning but killing the source once per path under one discipline. All four preregistered predictions hit this time, against one miss in four last time — and the miss last time was a missing mechanism (the stale mark), which this round was written into the preregistration before running. Mechanism first, numbers after: so far, that is the most reliable prediction style in this series.

No repository rule files were changed in this round. The candidates and the measurement material stay in this project's data/, as in the previous articles.

## 5. Limitations and Open Questions

- The timestamped exporter is a minimal artifact of mine: timestamps taken at request time, value always 1. Real self-stamping exporters may stamp event time, batch their emissions, or run on a skewed clock, and each of those moves the post-mortem visibility (the older the sample timestamp, the shorter the series outlives its source). This round measures only the "timestamp approximately equal to emission time" case.
- Path T was measured on the present family only. Other absent targets with self-stamped samples are inferred to follow the same mechanism; they were not measured family by family.
- In path R the recording group's interval equals the alert group's (15 s). If a recording interval were much larger than the scrape interval, whether the replica would still go stale in the same cycle as the original is unmeasured; the conclusion is scoped to comparable intervals.
- The two-step staling inside path R (source first, replica second) could not be resolved at 5 s poll granularity; see the note in section 3.3.
- The host restart cut the first run's R phase, so R's numbers come from a rerun: both runs used fresh TSDBs and identical flows, and cross-run comparability is supported by the original-series alert inside the rerun matching the first run's path C within 0.3 s. Strictly, though, R's side-by-side comparison is internal to the rerun, not shared with path C's run.
- Loopback, single host, one chain, for: 1m — the same scope limits as the previous articles. The absolute 370 s is bound to the default 300 s lookback; a chain that changes lookback-delta or disables honor_timestamps must recompute from the two-tier frame in section 4 rather than copy the number.
- Open: the scrape-timeout death (process hung, every scrape burning the full 4 s timeout) is still unmeasured on all three paths; the previous article listed it and this one still owes it. And remote write — no scrape, no local rule evaluation — is the next testable boundary: whether its absent blind window falls in the lookback tier is a clean, falsifiable question.
