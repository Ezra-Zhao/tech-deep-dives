# Blind-Spot Alerts, Measured: I Expected absent() to Take Five Minutes — Three Guard Rules, Three Ways to Die, and None Sees Them All

Author: Guangyi Zhao

## 1. Background

In my previous audit of the net-assurance-lab alert chain, I left one item explicitly booked as reasoning rather than measurement. Of the ten rules, exactly one watches the monitoring itself: NalExporterResultsMissing, which fires when the exporter's own nal_exporter_results_present series reads 0. That works while the exporter is alive and only the artifacts are incomplete. If the exporter process dies outright, the input series disappears with it, and the expression has nothing left to compare — the blind-spot alert is itself blind to the exporter's death. The standard remedy is a second rule based on the scrape layer, up or absent(), but I had not run it live. This article settles that account, together with the open question of how such rules should divide the work with the existing one.

The headline result contradicts my own preregistered prediction in one cell. Three candidate rules, three ways for the chain to die, and no row of the coverage matrix is full:

| Failure mode | present == 0 (existing rule) | up == 0 | absent() |
|---|---|---|---|
| Artifacts deleted, exporter alive | fires at ~65 s | never | never |
| Exporter process killed | never | fires at ~75 s | fires at ~75 s |
| Impostor endpoint (scrape succeeds, target series gone) | never | never | fires at ~65 s |

My preregistered budget had put absent() at 360–380 s for the kill case, on the theory that an instant query keeps returning the last sample for the 5-minute lookback period, so the series would only vanish once the lookback expired. The live run measured 75 s, with absent() entering pending in the very same evaluation cycle as up. The arithmetic was fine; the mechanism was wrong. When a scrape stops returning a series, Prometheus marks that series stale, and the stale mark voids the lookback on the spot. The five minutes only govern paths where no stale mark gets written. Section 3.3 corrects the preregistered model in the open, with the boundary stated.

## 2. Method

Three candidate rules, frozen before any live run (the bench script and the rule file were committed to disk first):

- NalExporterResultsMissing: the existing rule, copied verbatim from the repository's monitoring/rules/alerts.yml — expression, for:, labels and annotations all byte-identical (verified programmatically in part A of the bench script).
- NalExporterDown (new): `up{job="net-assurance-lab"} == 0`. The up series is synthesised by Prometheus at the scrape layer for every target; it never comes from the exporter.
- NalExporterSeriesAbsent (new): `absent(nal_exporter_results_present{group="scenario_summaries"})`, watching for the disappearance of the same self-reported series the existing rule reads.

Fair-comparison discipline: all three rules use for: 1m (matching the existing rule), the same rule-group evaluation interval of 15 s, a 5 s scrape interval and a 4 s scrape timeout — the deployment parameters of the repository's own monitoring/prometheus.yml. Any difference in outcome therefore comes from expression semantics and from which layer supplies the signal, not from tuning. By construction the three signals live on three different layers: present is the monitored process reporting on itself, up is the monitor's scrape ledger, and absent() is the monitor inferring something from a disappearance.

Three layers of testing:

1. Offline truth table (bench script parts B/C): the series visible to an instant query are modelled in four states — healthy; artifacts deleted; exporter killed, still inside the lookback window; exporter killed, past it — each candidate expression is evaluated for whether it can produce a result at all, and a theoretical blind-window budget is computed from scrape 5 s + evaluation 15 s + for: 60 s + lookback 300 s. The inside/outside-lookback split in this model is exactly what the live run later corrected; the file is kept as preregistered, as evidence.
2. promtool layer: promtool check rules / check config validate the candidate file; promtool test rules builds three synthetic worlds (artifacts deleted; series never existed; healthy) and asserts each rule's state at the 30 s (silent), 2 m (firing) and 10 m (still silent) evaluation points.
3. Live layer: Prometheus 3.15.0 downloaded fresh from the official release page (tarball 111,651,578 bytes, same version and size as the previous article, gzip verified), with the repository's real exporter code serving a copy of run 20261019-171627's artifacts. Deletions and the kill act only on the copy and on processes I started; the repository itself is untouched. A poller records the three instant queries (up, present, absent), target health and the full /api/v1/alerts snapshot every 5 s — 71 polls over 331.4 s — through the phases: 45 s healthy baseline; delete malformed.json from the copy; wait for the existing rule to fire, hold 30 s; restore the file and wait for resolution; settle 30 s; SIGTERM the exporter; wait for the absent rule to fire, hold 30 s; restart the exporter and wait for everything to resolve. Blind windows are measured honestly: pending time comes from the alert API's activeAt (the engine's own timestamp), and firing time is reported as the interval [activeAt + for:, first poll that saw firing], never as a single poll-granularity number dressed up as precision. The impostor endpoint gets its own short live run: a dummy server holds port 9108, answers every request with HTTP 200 and one unrelated metric, and Prometheus starts from an empty TSDB.

The cross-review method is recorded in the ledger and the review record; every number below traces to data/2026-10-27-blind-alert-bench.json, data/2026-10-27-blind-alert-live.json, data/2026-10-27-blind-impostor-live.json, or the promtool test file.

## 3. Measurements

### 3.1 Artifacts deleted: the self-report rule's exclusive cell

After malformed.json is deleted, the exporter's very next scrape renders the scenario_summaries group of present as 0: the first poll 5.0 s after deletion already shows present = 0, the existing rule's activeAt lands 4.2 s after the event (the first evaluation cycle), and firing falls in [64.2 s, 65.2 s] — a blind window of about 65 s, inside the theoretical budget of [60, 80] s, composed of the 60 s for: plus roughly 5 s of scrape and evaluation alignment. Throughout the same window up stays at 1 in every poll (the exporter is perfectly healthy) and the absent() instant query stays empty: the series exists and reads 0, and "present but zero" is a different thing from "not there" — that is absent()'s exact semantic boundary. After the file is restored, the rule is gone from the alerts list by the poll 15.0 s later. Across the 45 s baseline and the recovery segments, all three rules stay silent: no false positives.

The promtool world is isomorphic: with present = 0 and up = 1 held constant, the existing rule is silent at 30 s, firing at 2 m, and the other two stay silent out to 10 m. All assertions pass.

### 3.2 Exporter killed: up and absent() in the same cycle

After the SIGTERM, the first numbers already disagree with the preregistered model. In the poll 5.0 s after the kill, the instant query for present is empty — not still showing the last value of 1 while the lookback runs out, but gone; absent() returns 1 in the same poll. Target health flips to down and up reads 0. Both new rules enter pending 13.9 s after the kill, with activeAt timestamps identical to the nanosecond (the same evaluation cycle), and both fire in [73.9 s, 75.1 s]. The blind window is about 75 s; the roughly 10 s premium over the deletion cell is the cost of confirming a failed scrape plus evaluation alignment — an order of magnitude below the for: term.

The existing rule never goes pending or firing during the 105.2 s from kill to exporter restart, and that is not an observation-window artefact: its input series has vanished, and == 0 evaluated over an empty set is empty, structurally. The reasoning-only debt from the previous article is now discharged as measurement plus mechanism. After the exporter restarts, both firing rules resolve by the poll 15.0 s later.

### 3.3 Why the five-minute lookback never showed up

The preregistered budget modelled absent() in the kill cell as [360, 380] s: the last present sample would sit in the lookback window for 300 s with absent() empty throughout, then for: and alignment would be added on top. The model omitted stale markers. The Prometheus documentation's Staleness section is explicit: if a target scrape or rule evaluation no longer returns a sample for a previously present time series, that series is marked as stale, and queries stop returning values for it after the stale point. The 5-minute lookback is the value-assignment rule for when no stale mark exists, and the same section names the exception — exporters that put their own timestamps on samples keep their last value for the full lookback period after they stop. This exporter attaches no timestamps, so it travels the ordinary scrape path: the stale mark lands with the first failed scrape (measured bound: 5 s, one scrape interval), and absent()'s wait collapses from 300 s to parity with up.

The boundary of the correction matters. What was refuted is the generalised claim "a scraped series takes the lookback period to disappear", not the lookback itself. If the ingestion path changes to one with no scrape bookkeeping (remote write, recording-rule output), or the exporter starts stamping its own timestamps, absent()'s blind window for the same death may return to the five-minute scale. That sentence rests on the documentation alone and was not measured in this run; it is booked as reasoning, evidence grade B, and listed under Limitations.

One more same-number-different-cause note, worth stating plainly: in promtool's "series never existed" world the absent rule also fires at the 2 m evaluation point, numerically close to the live kill's 75 s. But promtool has no scrape history; there the series is non-existent because the test author declared it so. Same number, different mechanism. promtool can prove whether an expression fires on a given input; it cannot prove when a series disappears. Any question about staleness timing is a live-run question.

### 3.4 Impostor endpoint: absent()'s exclusive cell

With the dummy server on the port, scraping is, to Prometheus, completely healthy: up reads 1 in every successful poll and the target is up. The present series never exists, absent() returns 1 from the first successful query, the absent rule enters pending about 5 s into the run and is first seen firing in the poll at 65.1 s; the other two rules never appear in the 85 s window. This cell is not a contrived corner: an exporter upgrade that renames the metric family, another service taking over the port, or scraping the wrong program's /metrics all produce exactly "scrape succeeds, series is not there". The up rule vouches for HTTP-level success only; it has nothing to say about whether what answered is still the exporter you meant.

A writing detail measured along the way: absent()'s output labels are derived from the equality matchers in its input selector — this rule's alert carries group = "scenario_summaries", identically in promtool and live, matching the documented examples. Write the matcher as a regex (group =~ "…") and the label derivation does not happen, so the alert loses its locating label. Equality matchers in absent() rules are not a style preference.

## 4. Analysis and trade-offs

First takeaway: blind-spot protection is not about picking the strongest rule; it is about completing a truth table that localises the dead layer. Across the three failure modes the three rules fire in distinct patterns — present alone means the artifact layer (the data died, the process lives); up and absent together mean the scrape/process layer; absent alone means the content layer (something answers, but it is not the series you watch). Together their firing pattern is a locating instrument; each rule alone is one cell of it. The minimal complete set is present + absent, covering all three cells at the cost of one added rule plus a promtool test group (one-off to build, seconds to re-run). The up rule overlaps absent() completely in the kill cell; the reason to keep it is diagnostic language, not coverage — it says "target is down" in plain terms, and it is a reference that depends on no metric name when an absent() rule misbehaves because its selector was mistyped. On the benefit side: the kill blind window drops from unbounded (the existing rule structurally cannot fire) to about 75 s, and the impostor window from unbounded to about 65 s. Coverage and timings alike are real-engine measurements, evidence grade A.

Second: for: dominates the blind window. In all three cells that can fire, the window is 65–75 s, of which for: contributes 60 s; scrape plus evaluation alignment contributes 5–15 s. The only knob that meaningfully compresses the window is for:. On this chain, though, for: is not carelessness — the snapshot exporter's artifact directory is swapped wholesale, and present legitimately reads 0 mid-swap; the repository rule file's header comment documents exactly this debounce intent. My call is to leave 1m alone: 65 s is ample for an experimental bench, and trading it against swap-time false positives is a bad bargain. On a production chain the conclusion must be recomputed, but the recomputation is just this article's budget formula with that chain's parameters.

Third: the ceiling of self-reported health is structural. The present rule is not buggy — inside its own cell it fires on time at 65 s. Its blind spot comes from where its signal originates: asking the monitored process to report its own health means the reporting ability dies in the same moment as the process. Every "the exporter reports X about itself" health check inherits this blind spot, and the fix lives at the signal-source layer, not in the expression: pair it with at least one rule whose signal never passes through the monitored process (up from the scrape layer, absent() from the monitor's inference over disappearance — both qualify). When reviewing a monitoring design, label each health rule with the layer its signal comes from; a combination that can be wiped out layer-by-layer is visible on paper, before an incident demonstrates it.

As with the previous article, the repository's alerts.yml is unchanged by this work: the candidate rules live as a separate file with tests and live data in this project's data/, and merging them is a decision for the repository's normal commit flow.

## 5. Limitations and open problems

- The bench is a loopback setup with a single Prometheus. The coverage matrix's structural conclusions (self-reports die with the reporter; the three signal layers are separable) do not depend on the specific numbers, but they were measured on this one chain; the timings are bound to its parameters (scrape 5 s, evaluation 15 s, for: 1m) and were not re-measured on a second chain.
- The kill used SIGTERM with an immediate connection refusal. A process that hangs while still accepting connections, so every scrape burns the full 4 s timeout, was not tested; up would flip a timeout later there, and when the stale mark lands in that mode is unmeasured.
- The impostor endpoint is a synthetic stand-in (fixed 200 plus an unrelated metric). Real impostors — an old exporter version, a renamed metric family — are equivalent in the one respect that matters here (the watched series does not exist), but were not tested one by one.
- The lookback path was corrected at the documentation level only (Section 3.3): whether absent()'s blind window really returns to the five-minute scale under a different ingestion path or self-timestamped samples was not verified live.
- All three rules live inside the Prometheus process. If Prometheus itself dies, all three die with it; that needs a watchdog outside the process and is out of scope here.
- Open problem: the discriminative power of NalFaultLossAboveInjectionBand's 0.75 upper bound is still unmeasured (the next item in the topic pool, out-of-band loss injection). And the candidate rules' long-run false-positive rate after merging has no data yet; this run's observation windows are 331.4 s for the main live run and 85 s for the impostor run.
