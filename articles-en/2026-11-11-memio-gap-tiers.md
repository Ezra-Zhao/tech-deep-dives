# Memory and Disk Both Pressed, and the Gap Sent Only 46 Packets: The Bench Gap on the Memory and IO Axes, Measured

Author: Guangyi Zhao
Date: 2026-11-11
Subject: Controlled memory-residency and sync-write IO tiers against the generator-to-proxy bench gap in the author's net-assurance-lab (loopback only), closing the CPU article's open question of 2026-11-03

## 1. Problem and background

The bench-gap case is now on its third article. Measuring the injection-band alert on 2026-10-28, I found the generator's 10,000 packets did not always all reach the proxy: the first-hop gap, gap = 1 − in_client/sent, drifted from 0 to 29.8% across that batch of 28 runs, large enough to move alert conclusions. On 2026-11-03 I put the CPU axis under controlled experiment: only at 1.5× CPU overcommit did the gap show up routinely, with a maximum of 9.69 points — shape, mechanism (receive-buffer overflow, reconciled packet by packet), and an upper bound all pinned down, except that 29.8% would not reproduce. That article closed by saying the gap needs a co-factor outside CPU, and named the next bill: the memory and disk-IO axes.

This article pays that bill. The design is isomorphic to the CPU article: the same chain (generator, fault proxy, q=0 counting shim, echo server), the same injection parameters (20% loss both ways, 40 ms delay plus 30 ms jitter, flap window 0.6/2.5, proxy seed 1234), the same traffic (2000 pps for 5 s, 10,000 packets), the same frozen verdict lines (0.75 for the alert, 0.10 for the decomposition rule). Only the manipulated variable changes. The memory arm has four tiers: resident touched memory of 0, 0.5, 1.0, and 1.6 times the baseline available memory measured at bench start (absolute cap 1000 MB). The IO arm has four tiers: 0, 1, 2, and 4 synchronous-writer processes, each looping a 4 KB append write plus fdatasync — on a disk that is slow to begin with: at intake, a single fdatasync averaged 22.1 ms. Four repeats per tier, 32 runs across both arms. The design, the guard (kill the memory hog if available memory reads below 120 MB twice in a row; the run stays on the books), and eight predictions were frozen to disk before the runs (data/2026-11-11-memio-gap-prereg.md).

The headline: both axes were pressed, and the gap essentially never came. Thirty-one of 32 runs show a gap of exactly zero. The single nonzero run sits in the top memory tier: 46 packets, 0.46 points, matched packet-for-packet by the system receive-buffer error delta (46 against 46). And the pressure demonstrably landed: in the top IO tier, full IO stall per run (PSI io full) medians 2.48 seconds, about 22 times the zero tier, and round-trip p99 rose 14%; the memory arm pushed the in-run available-memory floor down by roughly 430 MB. With both pressure fingerprints verifiably moved, neither memory (1 GB resident, zero swap) nor disk IO (four sync writers saturating the disk's sync channel) produces the gap on its own. Two more axes are crossed off by exclusion; what remains for the 29.8% case is dimensions acting together, and bursty rather than sustained pressure — section 5.

## 2. Method

- Memory hog: my own Python process allocates bytearrays per tier size, writes every page, then keeps re-touching its pages in round-robin passes so the kernel cannot reclaim them cheaply. It starts before a tier's first run, finishes allocation plus a full touch, settles for 2 seconds, and dies at tier end. A guard thread samples MemAvailable every 0.25 s; it never fired in 32 runs.
- IO hogs: my own Python processes, one file each (deleted after the run), looping a 4 KB write plus fdatasync, reporting completed sync writes at exit. Per-tier totals (warm-up plus 4 runs): 1,459 for one writer, 2,066 for two, 3,901 for four — doubling the writers only multiplied throughput by 1.42 and 2.67, a saturation shape that matches the PSI stall saturation in section 3.3.
- Per run I recorded: the six hop counts by direction, the exporter's real collect() readback of total loss L and the five quantities behind D, pre-run load average, in-run MemAvailable samples (min and median at 0.25 s intervals), PSI memory/io some and full stall deltas around the run, /proc/vmstat scan/steal/swap deltas, and the system-wide UDP RcvbufErrors and InErrors deltas.
- Measurement definitions follow the earlier articles: gap as above; L_iso is the isolated-basis loss; D = 1 − in_server/F_c; the top-line gap g* is solved analytically from the pooled zero-tier L_iso mean. The preregistration included a manipulation check: if a tier's pressure fingerprint (PSI) does not move, that tier's zero result may only be read as "pressure not applied", never as "this axis is harmless". The memory arm made real use of that clause — see 3.2.
- Two profile numbers up front. This host is nominally 8 GB and shared with several other production lines; at intake sampling, MemAvailable was only 622–672 MB. By the time the bench actually started and measured MA0, it had recovered to 1,199.2 MB (median of five samples), and during the IO arm the zero tier's in-run median reached 1,769 MB — the host's own state drifted across the roughly 13-minute experiment window. Tiers were fixed from start-of-bench MA0 (599/1000/1000 MB; see the cap note in 3.2), and the drift itself is on the limitations list in section 5 rather than dressed up as a manipulated variable.

The by-direction six-hop reconciliation is cleaner than the headline table: across 32 runs × 6 hops, exactly one hop in one run lost anything — the first hop in M3's second run, 46 packets. The other 191 hop readings are exactly zero; apart from injected loss, the chain is lossless, in visible contrast to the CPU article's overcommit tier, where downstream hops started leaking too. That single event carries the same signature as the CPU article: the run's system RcvbufErrors delta is exactly 46, packet for packet — the proxy missed a short stretch of receiving and the kernel dropped what the full buffer could not hold. Total loss L across all runs stayed between 0.5157 and 0.5303, nowhere near 0.75; D was 0.0000 in every one of the 32 runs — not below its line, exactly zero.

One more difference from the CPU article: the injection baseline itself did not move. Tier means of L_iso all sit between 0.5243 and 0.5273 (a 0.30-point spread), and pooled flap shares are flat across tiers (client-to-server 23.5%–24.1%, server-to-client 3.0%–3.2%). CPU overcommit drifted the baseline by +3.57 points because scheduling lag blurred the proxy's decision times. Neither memory nor IO even touched that fingerprint — neither one reached the proxy's packet-reading rhythm at all.

### 3.2 The memory arm: a stock of pressure, not a flow — and the top two tiers merged by the cap

First, a design confession. MA0 measured 1,199.2 MB, so the 1.0× and 1.6× tiers are 1,199 and 1,919 MB, and both hit the preregistered 1000 MB absolute cap: M2 and M3 carried the same 1000 MB hog. The contrast between the top two tiers is thereby weakened — whatever differs between M3 and M2 is the background state during the hog's life, not a larger residency. This was not foreseen (at intake, available memory was about 0.64 GB, against which the cap would never have triggered). It is recorded here plainly, and every M2/M3 comparison in this article is read as "two batches at the same size".

Did the pressure land? Two sets of readings point in opposite directions, and both go on the record. Landed: the median of in-run MemAvailable minima is 1,130 MB at M0, 698 MB at M1, 719 MB at M2, 802 MB at M3 — the hogs were resident and pressed the available-memory floor down by about 430 MB, and the 120 MB guard line was never approached. Not landed, and more important: pswpout and pswpin deltas are zero in all 32 runs — no page was ever swapped — and the per-run PSI memory full delta median declines tier by tier (M0 93 ms, M1 61 ms, M2 20 ms, M3 5 ms). Under the preregistered manipulation check, the memory arm's pressure fingerprint did not rise with tier. That is not the hog slacking: PSI is a host-wide account that includes other tenants, and M0 ran at the very front of the window, when background reclaim activity was heaviest (M0's four runs total 244,842 stolen pages against M1's 2,881 — that is not the hog's doing; it had not started). There is also a mechanism that fits better than either reading alone: a resident hog is a one-time stock of pressure. Allocation and touching in the warm-up evict the page cache and reach equilibrium; once the runs start, the hog merely re-touches its own pages and generates no continuing reclaim work. The chain components' anonymous pages were never evicted (no swap means no page-in stalls), so the memory subsystem had no channel through which to starve the receive loop. CPU hogs and IO hogs are flow-type pressures that keep doing work; a resident allocation is not. That distinction is the memory arm's most portable finding, and it is narrower and more honest than "memory is harmless": what this experiment shows is that under a 1 GB resident stock with zero swapping, the gap does not appear.

The lone 46 packets sit in this arm's top tier (M3 run 2: in-run MemAvailable minimum 615 MB, 64,803 stolen pages that run), with the receive-buffer signature. Read against three zero runs in the same tier and zeros everywhere else, it looks like one brief stall when background reclaim coincided with the resident stock — not the start of a tier effect. The article does not promote it to a trend.

### 3.3 The IO arm: stalls verified, latency verified, gap zero

The IO arm's manipulation check is unambiguous. Per-run PSI io full delta medians: I0 0.114 s, I1 2.357 s, I2 2.374 s, I3 2.483 s — a single writer multiplied host-wide full IO stall about twenty-fold, and the curve then saturated (more writers barely added stall; the disk's sync queue was already full). The chain felt it too: round-trip p99 medians rose from 136.4 ms at I0 to 155.9 ms at I3 (+19.6 ms, +14.3%). The proxy flushes its decision log at the end of every loop iteration, and the generator and server also write files — all of that IO genuinely slowed down.

Yet the gap is zero in all four tiers. The magnitude reasoning holds up: a 22 ms fdatasync is the writer's own wait, not the chain's. The page cache absorbs the chain's sequential writes (the proxy's log flush goes to the kernel, not to a disk confirmation), and no link in the chain ever waits on a disk acknowledgement. The extra 19.6 ms spread into the round-trip account — the same order as the 30 ms jitter window — without ever turning into a batched receive-loop stall. The receive buffer holds 212,992 bytes, a few tenths of a second at 2000 pps; to starve it, some chain process must block outright for that long, and under sync-write pressure no link has such a blocking point. This axis pressed exactly where the chain is neither defended nor wounded: it has no synchronous IO.

### 3.4 The false-alarm margin: two more blocks on the exclusion map

The analytic layer, as before: from the pooled zero-tier L_iso mean of 0.5268, the gap needed to top the 0.75 line is g* = 47.17% — the third independent computation of that number, after 47.1% on 2026-10-28 and 47.19% on 2026-11-03. Set the three articles' measured ceilings side by side and the bench's exclusion map now reads: pure CPU (to 1.5× overcommit) at most 9.69 points; pure memory residency (to 1 GB, zero swap) at most 0.46 points; pure disk sync IO (to about 2.5 s of host-wide full IO stall per run) at most 0 points. No single axis reaches a fifth of g*. The operational reading sharpens accordingly: if a first-hop gap above 20 points ever shows up in the wild, this series' evidence says it does not come from any one of these three axes acting alone — look for dimensions acting together, for a different pressure shape (bursts, not sustained tiers), or for variables that have never entered this bench (other tenants' UDP traffic competing for the same buffers, host-level scheduling events). Those are section 5's open items.

### 3.5 Preregistration scorecard

P1 (memory-tier medians non-decreasing): literally satisfied and information-free — all four medians are zero; the substance was P3's to judge. P2 (all 8 zero-tier runs at or below 2 points): hit, all exactly zero. P3 (M3 median at least M0 + 2 points): missed — M3 medians zero with a 0.46-point maximum; the predicted mechanism ("residency starves the receive loop in batches") is corrected by the stock-versus-flow analysis in 3.2: with no swapping and no continuing reclaim, the starvation channel does not exist. P4 (IO medians non-decreasing, I3 at least I0 + 1 point): missed — all four tiers zero; the pressure fingerprints (PSI about 22×) and the latency (+14.3%) both landed, what was missing is a blocking point that passes the stall into the receive loop, and the prediction was wrong to assume the log flush waits on disk. P5 (RcvbufErrors attribution of at least 50% for any gap tier): no tier met its trigger condition (a median above 0.5 points), so it stands vacated by its own preregistered terms; the single nonzero run attributed 46 of 46 packets, recorded as an attachment, not a hit. P6 (D at most 0.03 in all 32 runs): hit, and stronger than predicted — exactly 0.0000 every run; the decomposition rule's immunity now replicates across CPU, memory, and IO. P7 (no OLD firing): hit, L maximum 0.5303. P8 (manipulation checks): IO side hit (I3/I0 about 22×, against a predicted 3×); memory side missed (PSI memory full declined tier by tier, see 3.2) — and per the preregistered rule, the memory arm's zero result is downgraded to a claim about the resident-stock shape only, not about the memory axis in general.

## 4. Analysis and trade-offs

Across three articles the bench gap is now a fairly three-dimensional object: a known mechanism (a starved receiver, kernel buffer overflow, reconcilable packet by packet), a threshold shape on the CPU axis (routine only past overcommit), a second fingerprint in the injection baseline drift that CPU drag produces, and now two clean exclusions (memory stock, disk sync IO) plus a pressure-shape distinction (stock versus flow). Three things I am taking into bench operations directly. First, the pre-run bench-state checklist grows from four numbers to six: gap, flap share, RcvbufErrors delta, and load average, plus PSI memory/io deltas and the in-run MemAvailable minimum — when several axes are live at once, read which fingerprint is moving before blaming any of them. Second, resident memory occupancy (cache-style and preload-style loads) does not belong in the same bucket as CPU and IO pressure under a vague "the host is busy": in this chain's profile it does not even drift the baseline. Third, the alert-side reading is unchanged and now harder: when a first-hop gap above 20 points appears, investigate multi-axis coincidence or burst shapes first, and stop suspecting any single sustained load.

Two things were deliberately not done, with the trade-off stated. I did not scale the memory hog into the multi-GB range that would actually force swapping: the guard line and a shared host with other production lines running do not permit gambling the whole machine's OOM risk on an experiment. That cell waits for an exclusive window or an isolation mechanism (pressing a single component inside a cgroup limit, for instance) and is not laziness in this round. And I did not run the combined tiers (CPU overcommit × residency × sync writes) here: that shape is the most likely match to the old case, but its tier space and attribution design need their own preregistration round; nothing in this article pre-spends its conclusions.

## 5. Limitations and open questions

- The memory arm's ceiling is a shape limit: the hog capped at 1 GB and never swapped a single page, so the regime "available memory pressed into swapping, chain pages evicted" went untested; M2 and M3 were additionally merged by the cap into two batches of the same size. The memory conclusion is strictly bounded to "1 GB-class resident stock, no swapping"; the swapping regime remains open.
- PSI and pgsteal are host-wide accounts, and other tenants' activity (visibly heavier at the front of the window) drifts with time while tier order was not randomized (memory arm first, IO arm second), so memory-arm background decay and tier effects cannot be fully separated. The headline zero-gap conclusion is insensitive to background direction (the gap was zero when background was heaviest, too), but fine readings like the PSI decline are attribution references only, not tier laws.
- The IO arm tested one disk shape only — synchronous writes. Bulk sequential reads, random reads, and page-cache churn (mass file traversal evicting the cache) went untested; and because this chain performs no synchronous IO, the second half of 3.3 does not transfer to systems under test that fsync. Do not carry it over.
- Four repeats per tier give no frequency resolution for a roughly 1-in-32 event like the 46 packets: whether that event belongs to the memory tier or to pure background chance cannot be separated in this round; I report its signature and same-run covariates only.
- The 29.8% case from 2026-10-28 remains open; this article only excludes two more axes. Remaining suspects, in rough order: dimensions acting together (that batch's flap-share fingerprint matches the CPU overcommit tier, so CPU was present but cannot account for the magnitude — precisely the missing co-factor), burst-shaped pressure (second-scale full-load pulses hit a buffer differently from sustained tiers), and competing UDP tenants on the same host. The candidate next article is a combined-factor run — CPU overcommit, residency, and sync writes switched on together, plus a burst arm — under its own separate preregistration.
- All evidence remains one host's profile: loopback, Python components, default receive buffer. The ceiling numbers (9.69 / 0.46 / 0 points) are this machine's; a different host remeasures.
