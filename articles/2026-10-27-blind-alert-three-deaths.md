# 防盲告警实测：我以为 absent() 要等五分钟——三条规则、三种死法，没有一条全看见

作者：Guangyi Zhao

## 1. 问题与背景

上一篇审计 net-assurance-lab 告警链路时，我在分析里留了一笔标明「只算推理、不算实测」的账：现有 10 条规则里唯一管监控健康的是 NalExporterResultsMissing，它看的是 exporter 自己吐出的 nal_exporter_results_present 是否为 0。exporter 活着、只是产物缺件时它能响；可 exporter 进程若整个死了，这条输入序列随之消失，表达式连比较的对象都没有——防盲的告警对「exporter 之死」本身是盲的。当时给的常规解法是另配一条基于抓取层 up 或 absent() 的规则，但没有为它单独起一轮活体。这篇来还这笔账，顺带把上次未解问题里的那句「up/absent 型防盲规则该怎么配、配上之后与现有规则如何分工」一并测掉。

先说结论，因为它和我动手前的预判有一格是反的。三条候选规则、三种死法，覆盖矩阵里没有一行全满：

| 死法 | present == 0（现有规则） | up == 0 | absent() |
|---|---|---|---|
| 删产物、exporter 活着 | 65 秒响 | 不响 | 不响 |
| 杀 exporter 进程 | 不响 | 75 秒响 | 75 秒响 |
| 冒名端点（抓取成功、无目标序列） | 不响 | 不响 | 65 秒响 |

而我预注册的理论预算里，absent() 在「杀进程」一格写的是 360–380 秒——理由是即时查询有 5 分钟回望期（为某个时刻取值时，最多往回找 5 分钟内的最近样本），序列消失要等回望过期。活体实测 75 秒，与 up 规则同一评估周期 pending、同一时刻 firing。错的原因不在算术，在机制：抓取不再返回样本时，Prometheus 会给序列打陈旧标记，陈旧一打，回望期当场作废；那 5 分钟只管没有陈旧标记可打的路径。这一格是本文档公开修正的预注册模型，细节在第 3.3 节。

## 2. 方法

候选规则三条，设计在跑活体之前冻结（bench 脚本与规则文件同日落盘）：

- NalExporterResultsMissing：现有规则，从仓库 monitoring/rules/alerts.yml 原样复制（表达式、for:、标签、注释逐字比对，四项全等，bench 脚本 A 部分验过）。
- NalExporterDown（新）：`up{job="net-assurance-lab"} == 0`。up 是 Prometheus 在抓取层为每个目标合成的序列，不来自 exporter 本身。
- NalExporterSeriesAbsent（新）：`absent(nal_exporter_results_present{group="scenario_summaries"})`，盯与现有规则同一条自报序列的消失。

公平口径：三条规则同用 for: 1m（与现有规则一致）、同一规则组评估间隔 15s、抓取间隔 5s、抓取超时 4s，与仓库 monitoring/prometheus.yml 的部署参数相同。这样测出的差异只来自表达式语义与信号来源层，不来自调参。三条规则按信号来源正好分属三层：present 是被监控者自报，up 是监控者的抓取账，absent 是监控者对缺失的推断。

测试分三层：

1. 离线真值表（bench 脚本 B/C 部分）：把四种状态下即时查询能见的序列建模——健康、删产物、杀进程后回望窗内、杀进程后回望窗外——逐条评估三条表达式能否产生结果，并按抓取 5s + 评估 15s + for: 60s + 回望 300s 给出理论盲窗预算。这一层的回望窗内/外拆分正是后来被活体修正的地方，原文保留，作为预注册证据。
2. promtool 层：promtool check rules / check config 确认候选文件合法；promtool test rules 构造三个合成世界（删产物、序列从未存在、健康），断言每条规则在 30 秒静默、2 分钟 firing、10 分钟仍静默等评估点上的状态。
3. 活体层：重新从官方发布页下载 Prometheus 3.15.0（tar 包 111,651,578 字节，与上一篇同版同大小，gzip 校验通过），用仓库自己的 exporter 代码对运行 20261019-171627 产物的一份副本提供服务——删除与杀进程只作用于副本和我自己起的进程，仓库本体零改动。主轮询器每 5 秒记录三条即时查询（up、present、absent)、目标健康与 /api/v1/alerts 全量快照，全程 331.4 秒、71 次轮询，阶段依次为：健康基线 45 秒 → 删掉副本的 malformed.json → 等现有规则 firing 并保持 30 秒 → 恢复文件等解除 → 静置 30 秒 → SIGTERM 杀 exporter → 等 absent 规则 firing 并保持 30 秒 → 重启 exporter 等全部解除。盲窗的量法：pending 时刻取告警 API 的 activeAt（评估引擎自己的时间戳），firing 时刻给区间［activeAt + for:，首次轮询见到 firing］，不靠轮询粒度冒充精度。冒名端点另起一轮短活体：一个哑服务器占住 9108 端口，对任何请求回 HTTP 200 与一条无关指标，Prometheus 用全新 TSDB 从零开始抓。

交叉审方式见台账与审稿记录；正文数字全部来自 data/2026-10-27-blind-alert-bench.json、data/2026-10-27-blind-alert-live.json、data/2026-10-27-blind-impostor-live.json 与 promtool 测试文件。

## 3. 实测数据

### 3.1 删产物：自报规则独占的一格

删掉 malformed.json 后，exporter 在下一次抓取就把 scenario_summaries 组的 present 渲染成 0：删除后第 5.0 秒的轮询已见 present = 0，现有规则的 activeAt 在删除后 4.2 秒（第一个评估周期），firing 区间［64.2 秒，65.2 秒］，即盲窗约 65 秒——落在理论预算［60，80］秒内，构成是 for: 60 秒加抓取与评估对齐的约 5 秒。同一段时间里，up 在全部轮询中恒为 1（exporter 活得好好的），absent() 的即时查询全程空（序列存在、只是值是 0，「在但为零」与「不在」是两回事，这正是 absent 的语义边界）。恢复文件后，规则在恢复后 15.0 秒的轮询里解除。健康基线 45 秒与各恢复段里三条规则全程静默，无误报。

promtool 合成世界同构：present = 0、up = 1 持续输入下，现有规则 30 秒静默、2 分钟 firing，另两条到 10 分钟仍静默，断言全过。

### 3.2 杀进程：up 与 absent 同一周期并列

SIGTERM 杀掉 exporter 后，第一批数字就和预注册模型对不上：删除事件后第 5.0 秒的轮询里，present 的即时查询已经是空——不是还停在最后的 1 上等回望过期，是序列已经不可见；absent() 同一轮询返回 1。目标健康随即翻 down，up = 0。两条新规则在杀进程后 13.9 秒同时 pending——activeAt 逐微秒相同（同一评估周期），firing 区间同为［73.9 秒，75.1 秒］。盲窗约 75 秒，比删产物格多出的约 10 秒是抓取失败被确认与评估对齐的成本，量级上和 for: 不在一个档次。

现有规则在这 105.2 秒（杀进程到重启 exporter）里从未 pending 或 firing，且这不是观察窗不够长：它的输入序列已经消失，`== 0` 对空集求值只能是空集，结构性无解——上一篇留的那笔推理账，活体这一轮算是把「响不了」从推理升格为实测加机制双确认。exporter 重启后，两条 firing 的规则在重启后 15.0 秒的轮询里同时解除。

### 3.3 五分钟回望为什么没有出现

预注册预算把 absent 在杀进程格的盲窗写成［360，380］秒，模型是：最后一个 present 样本留在回望窗内 300 秒，absent() 在此期间恒空，之后再叠 for: 与对齐。这个模型漏了陈旧标记。Prometheus 官方文档在 Staleness 一节写得很明确：某个抓取或规则评估不再为先前存在的序列返回样本时，该序列会被标记为陈旧（stale)，查询在陈旧点之后不再返回它的值；5 分钟回望是给没有陈旧标记时的取值规则，文档同节还点名带自有时间戳的 exporter 是例外——它们的序列停发后会把最后的值保留满回望期。本 exporter 不给样本打时间戳，走的是普通抓取路径，所以陈旧标记在第一次失败抓取时就落下（实测上界 5 秒，一个抓取间隔内），absent() 的等待从 300 秒塌到与 up 同级。

要紧的是把这格修正的边界说清：被推翻的是「抓取型序列消失要等回望过期」这个一般化说法，不是回望本身。若 ingestion 路径换成没有抓取记账的来源（例如远端写入、录制规则的输出），或 exporter 改成自带时间戳，absent() 在同类死亡上的盲窗仍可能回到 5 分钟量级——这一条只有文档依据、本轮未实测，按推理记账（证据等级 B），写进局限。

还有一处同数不同因，值得单独点名：promtool 的「序列从未存在」世界里，absent 规则也是 2 分钟评估点 firing，与活体杀进程的 75 秒读数接近；但 promtool 里没有抓取历史，序列是被测试作者声明为不存在的，两边同数、机制不同。promtool 能证表达式在给定输入下响不响，证不了序列何时消失——凡是涉及陈旧化时间的问题，只能活体。

### 3.4 冒名端点：absent 独占的一格

哑服务器占住端口后，抓取在 Prometheus 眼里是完全健康的：每次成功轮询里 up 恒为 1，目标健康 up。present 序列从未存在，absent() 从第一次成功查询起返回 1，absent 规则在运行开始约 5 秒进入 pending、65.1 秒的轮询首次见 firing；另两条规则在 85 秒观察窗内从未出现。这一格不是编出来的极端情形：exporter 升级后改了指标名、端口被另一个服务接管、抓到的其实是别的程序的 /metrics，都是「抓取成功、序列不在」。up 只对 HTTP 层面的成败负责，它对内容是否还是原来那个 exporter 不置一词。

顺带一个实测到的写法细节：absent() 的输出标签从输入选择器的等值匹配器推导——本轮规则的告警标签带 group = "scenario_summaries"，promtool 与活体一致，与官方文档示例吻合；若把匹配器写成正则（group =~ "…"），标签推导就不发生，告警会丢掉定位信息。写 absent 规则时匹配器要用等值式，这不只是风格问题。

## 4. 分析与取舍

第一条可直接拿走的：防盲不是选一条最强的规则，是凑齐一张能定位死层的真值表。本轮三种死法下三条规则的响法互不相同——只有 present 响，是产物层（数据死了、人活着）；up 与 absent 一起响，是抓取/进程层；只有 absent 响，是内容层（有人应答、但不是原来的序列）。三条规则的 firing 图案合起来是一台定位仪，任何单条都只是其中一格。最小完备集是 present + absent：三格全覆盖，成本为新增一条规则加一组 promtool 用例（一次性搭建、回归秒级）；up 与 absent 在杀进程格完全重叠，留它的理由不是覆盖而是诊断语义——它把「目标 down」说成人话，且当 absent 因选择器写错而长鸣或长哑时，up 是一个不依赖指标名的独立参照。收益侧：杀进程的盲窗从无穷大（现有规则结构性不响）降到约 75 秒，冒名端点从无穷大降到约 65 秒；以上覆盖关系与时延均为真引擎实测（证据等级 A）。

第二条：盲窗的构成里 for: 是绝对大头。能响的三个格子里，盲窗 65–75 秒中 for: 占 60 秒，抓取加评估对齐只占 5–15 秒。想压缩盲窗，唯一有效的旋钮是 for:；但这条链上的 for: 不是疏忽——快照式 exporter 的产物目录是整批替换的，替换中途 present 会短暂为 0，仓库规则文件头注释里写的就是这个防抖意图。我的取舍是维持 1m 不动：65 秒对一条实验台链路绰绰有余，为省几十秒去吃运行替换的误报不划算。换到真实链路结论要重算，但重算的方法就是本文的预算公式，参数换成那条链自己的。

第三条：自报信号的天花板是结构性的。present 这条规则本身没有写错——它在自己的格子里 65 秒准时响；它的盲区来自信号来源：让被监控者报告自己是否健康，它死透的那一刻报告能力同归于尽。任何「exporter 自报 X」形态的健康检查都继承这个盲区，修法不在表达式里，在信号来源层：至少配一条信号不经过被监控者的规则（up 来自抓取层、absent 来自监控者对缺失的推断，都满足）。评审一条监控设计时，先把每条健康规则的信号来源层标出来，同层全灭的组合当场就能看出来，不需要等事故。

本轮同样没有改仓库里的 alerts.yml：候选规则以独立文件加测试与活体数据的形式留在本项目 data/，是否合入由仓库走正常提交流程决定，与上一篇的处置一致。

## 5. 局限与未解问题

- 实验台是回环环境加单机 Prometheus：覆盖矩阵的结构结论（自报同死、三层信号可分）不依赖具体数字，但只在这条链上测过；时延数字绑定本链参数（抓取 5s、评估 15s、for: 1m），未在第二条链复测。
- 杀进程用 SIGTERM、连接被立即拒绝：进程挂死但端口仍收连接、每次抓取走满 4 秒超时的死法没有测，那种情况下 up 的翻转会慢一个超时量级，absent 的陈旧标记何时落下也未测。
- 冒名端点是合成替身（固定 200 加无关指标）；真实替身如旧版 exporter 或改名后的指标族，在「目标序列不存在」这一点上等价，但没有逐一实测。
- 回望路径只做了文档层面的归因修正（第 3.3 节）：换 ingestion 路径或自带时间戳后 absent 的盲窗是否真回到 5 分钟量级，未起活体验证。
- 三条规则都活在 Prometheus 进程里：Prometheus 自己死时全灭，这不在任何一条表达式的管辖内，需要进程外的看门狗，不在本篇范围。
- 未解问题：NalFaultLossAboveInjectionBand 的 0.75 上界判别力仍未测（注入带外丢包的判别力实测，选题池下一条）；候选规则合入仓库后的长期误报率没有数据，本轮只有 331.4 秒主活体与 85 秒冒名活体的观察窗。
