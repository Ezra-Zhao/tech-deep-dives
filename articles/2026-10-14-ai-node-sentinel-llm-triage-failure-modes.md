# 给 GPU 故障诊断接一个 LLM 之前：AI-Node-Sentinel 的接线点设计与六个失效模式实测

作者：Guangyi Zhao
日期：2026-10-14
实测对象：AI-Node-Sentinel（自有开源项目，github.com/Ezra-Zhao/AI-Node-Sentinel），scaffold v0.1，Python 3.12.3
实测环境：Linux x86_64 虚拟机，本机直跑仓库未修改代码；LLM 实验用本地假 provider 实现仓库自有协议，未调用任何真实模型 API

## 一、问题与背景

GPU 集群里最先冒头的硬件故障信号，往往是内核日志里的一行 Xid。XID 是 NVIDIA 驱动给 GPU 硬件与固件错误编的号：掉总线、显存双比特 ECC 错误、NVLink 故障、GSP 固件超时，各有各的码。值班工程师的日常是把散在上千块 GPU 上的 dmesg 捞回来，逐条查这个码是什么意思，再决定排空节点、重置 GPU、重启，还是走 RMA 换卡。这个决定做慢了，训练任务继续在坏卡上重试，烧掉的是真金白银的 GPU 小时。

自然的冲动是：把这一步交给 LLM agent。让模型读遥测、查错误码、给处置建议，不就是为这种场景准备的吗？

我自己的开源项目 AI-Node-Sentinel 就是按这个想法搭的脚手架：遥测进来，抽出 XID 事件，查表补全含义，套分诊规则，最后渲染一份结构化报告，LLM 推理留了一个基于 LangChain 的接线点。先把实情说清楚，免得后文被误读：这个项目现在是 scaffold v0.1，仓库 README 里就写着这行字。分诊决策树是刻意留空的桩，任何事件进来都只得到 NEEDS_HUMAN_REVIEW、置信度 0.0；LangChain provider 也是桩，实例化直接抛 NotImplementedError。遥测全部是模拟器生成的合成数据。真正跑通的只有摄入、查表、报告渲染这三段。

所以本文写的不是一个已经上线的智能诊断系统。恰恰相反：我把这套脚手架当解剖台，用六组故障注入实验量了一遍当 LLM 真的接进来时、这条管线会在哪里断。结论对任何准备给运维系统接 LLM 的人都有用，因为这六个断点没有一个是模型能力问题，全是接线问题：输出契约对不上、证据喂得太薄、一条坏数据毒死整批、提示词路径和工作目录耦合、单事件无记忆、佐证信号被管线自己丢掉。模型再强，这些坑一个都躲不过。

## 二、方法与架构

代码很小：核心 Python 文件 8 个，加上测试与示例共 470 行上下。分工是四段。agent/schemas.py 定义三个数据类：TelemetryEvent（归一化遥测事件，带来源、类型与 payload）、XidFinding（查表补全后的 XID 发现）、TriageVerdict（处置结论，含动作、置信度、理由）。tools/xid_lookup.py 是一张静态查表，码到名称、类别、严重度的映射只取自 NVIDIA 官方 XID 文档与 Google Cloud 的 GPU 排障指南，查不到就返回 None，绝不猜。tools/triage_rules.py 是决策树，目前是桩。agent/orchestrator.py 是编排器 TriageAgent，管线顺序是摄入、抽 XID 事件、逐条查表与分诊、渲染报告。

LLM 的接线点在 agent/llm.py：一个极小的协议 LLMProvider，只要求一个方法 reason(system_prompt, evidence) 返回字符串。编排器的逻辑是：先由确定性部分算出结论，再在有 provider 时把一段证据字符串拼给 provider，把它返回的文本以 [LLM] 前缀追加到结论的理由字段末尾。系统提示词草稿单独放在 prompts/triage_system.md，要求模型只引用所给证据、未知码明说未知、恰好给出一个动作与 0 到 1 的置信度、置信度低于 0.7 时动作必须是 NEEDS_HUMAN_REVIEW，并以 JSON 格式输出。

实验方法：仓库代码原样不改，在本机跑五组实验，脚本与原始 JSON 随本文归档。一，基线规模实验：用自带模拟器生成 4、16、64 节点三种规模的遥测窗口，统计事件构成、结论分布与管线耗时。二，查表覆盖实验：统计查表规模，并用 10 个表外码做探针。三，畸形数据注入：分别混入缺 xid 键、xid 为非数字字符串、xid 为 None 的事件，看单条坏数据的影响面。四，假 LLM 实验：实现一个严格按提示词要求返回 JSON 的本地假 provider，观察结论字段的实际变化；再用一个必抛异常的 provider 看故障传播。五，失效模式实验：同卡重复故障的升级行为、佐证事件的命运、换工作目录后的提示词加载。

## 三、实测数据

### 3.1 基线：确定性部分快得没有讨论价值，结论分布由桩决定

模拟器为每块 GPU 生成一条温度与一条 ECC 基线事件，再以约 35% 的概率注入 1 到 2 条 XID。结果：

| 规模 | 事件总数 | XID 事件 | 结论数 | unknown 结论 | 严重度分布（critical/high/unknown） | 管线耗时 |
|---|---|---|---|---|---|---|
| 4 节点 × 8 GPU（seed 42） | 76 | 12 | 12 | 1 | 10 / 1 / 1 | 约 0.1 ms |
| 16 节点 × 8 GPU（seed 42） | 313 | 57 | 57 | 5 | 39 / 13 / 5 | 约 0.2 ms |
| 64 节点 × 8 GPU（seed 42） | 1285 | 261 | 261 | 34 | 157 / 70 / 34 | 约 0.7 ms |
| 64 节点 × 8 GPU（seed 7） | 1295 | 271 | 271 | 35 | 177 / 59 / 35 | 约 0.7 ms |
| 64 节点 × 8 GPU（seed 123） | 1282 | 258 | 258 | 28 | 167 / 63 / 28 | 约 0.7 ms |

三件事值得说。第一，全部结论的动作都是 NEEDS_HUMAN_REVIEW、置信度都是 0.0，这是桩的行为，不是测出的智能水平，把它写出来是为后文的对照组立标尺。第二，管线在 64 节点规模下处理约 1300 条事件只要不到 1 毫秒，按原始计时折合约每秒 177 万条（耗时为单次 perf_counter 计时、表中保留到 0.1 ms，亚毫秒读数只作量级参考，不作精确基准）：查表本质是字典查询，确定性部分在本文规模下不是瓶颈；将来接入流式摄入与窗口状态后，其开销要另测，但延迟与成本的大头只会来自 LLM 那一步。第三，unknown 占比约 11% 到 13% 不要误读：模拟器的注入池是 8 个码，其中 999 是人为放进去的合成未知码，占注入期望的八分之一，unknown 比例是注入池设计的结果，不是真实机群的未知码发生率。

仓库自带的 6 个测试在本机逐个直跑全部通过，覆盖模拟器确定性、已知码查表、未知码不猜、桩路由到人工复核、报告形状五类断言。本机没装 pytest，我用函数直调的方式跑的，这一点如实标注。

### 3.2 查表覆盖：只有 7 个码，其余一律未知

查表里只有 7 个码：13、31、48、74、79、119、120。我另取 10 个表外数字码（43、45、56、63、64、68、92、94、109、154）做探针，全部返回 None，与 999 的待遇相同：severity 记为 unknown、known 记为 False、路由人工复核。这个行为本身是对的，未知不猜是这条管线最重要的安全设计。但覆盖面就是另一回事：真实机群里出现的 XID 码只要不在这 7 个之内，系统能给的全部信息就是「有个未知错误，找人看」。查表是从公开文档手工种子化的，扩表是体力活，也是这条管线在接 LLM 之前性价比最高的一笔投入，理由在 4.3 节说。

### 3.3 畸形数据：一条坏事件毒死整批

编排器取码的写法是 int(event.payload["xid"]) ，没有校验、没有逐条隔离。我注入三种畸形事件与正常事件混跑：

| 注入 | 结果 |
|---|---|
| 单条正常事件 | 正常完成，1 条结论 |
| 正常 + 缺 xid 键 + 正常 | 整个 run 抛 KeyError，已处理的结果一并丢失 |
| 正常 + xid 为非数字字符串 | 整个 run 抛 ValueError |
| 正常 + xid 为 None | 整个 run 抛 TypeError |

run 方法用列表推导逐条处理，任何一条抛异常，整批结论全部拿不到。放到真实场景里想：dmesg 解析器迟早会吐出一条字段不全的事件，届时不是这一条没诊断，而是整个窗口的所有结论一起消失，且故障形态是进程级异常而不是报告里的一行标注。逐条隔离加坏数据计数，是这类管线的基本功，这里缺席。

### 3.4 假 LLM 实验：输出契约是断的，模型说了不算

这是本文最重要的一组实验。我实现了一个假 provider，严格按系统提示词的要求返回 JSON：对 XID 79（GPU 掉总线）给出动作 DRAIN_NODE、置信度 0.95。把它接进编排器后，结论的实际状态是：

| 字段 | 假 provider 的输出 | 最终结论 |
|---|---|---|
| action | DRAIN_NODE | NEEDS_HUMAN_REVIEW（未变） |
| confidence | 0.95 | 0.0（未变） |
| rationale | JSON 全文 | 被当作纯文本追加在理由末尾，前缀 [LLM] |

原因在代码里很直白：协议要求 reason 返回字符串，编排器拿到字符串后只做拼接，从不解析 JSON，更不会用解析结果覆盖确定性结论。提示词里写的输出格式、置信度门槛，全是给模型的君子协定，代码侧没有任何一处兑现。也就是说，哪怕明天把真实 LangChain provider 实现出来、模型每次都完美遵守格式，这条管线的处置结论仍然百分之百由桩决定，LLM 的全部影响只是一段贴在理由后面的文本。

同一组实验的第二半是证据的厚度。编排器实际拼给 provider 的证据字符串全文是：node=node-00 gpu=0 xid=79 name=GPU has fallen off the bus severity=critical ts=时间戳。就这些。查表里明明有 category（类别）与 notes（处置提示与来源说明）两个字段，都没有进入证据；同一块 GPU 的温度、ECC 计数更不在内，因为证据是在单条事件的分诊函数里拼的，函数签名里根本没有窗口上下文。提示词第一条要求模型「只引用所给证据」，而管线给的证据薄到只够复述错误名称：模型想给出有信息量的判断，就只能往证据之外找，那正是提示词禁止它做的事。管线先把证据饿瘦，再要求模型不许编造，这个矛盾是接线设计造成的，与模型无关。

第三半是故障传播：把 provider 换成必抛 RuntimeError 的版本，triage_event 直接把异常抛穿，整批 run 随之中断，与 3.3 节的畸形数据同一种死法。provider 是外部依赖，超时、限流、网络抖动都是常态，可选步骤的故障不该升级成整批故障，这里没有降级路径。

### 3.5 提示词路径：与工作目录耦合

编排器读提示词的写法是相对路径 open("prompts/triage_system.md")。我在仓库根目录跑一切正常，切到 /tmp 再跑同一段代码，立刻 FileNotFoundError。同理，LangChainChatProvider 目前实例化即抛 NotImplementedError，这是诚实的桩，算不上缺陷；但相对路径这一处是会真的在部署时咬人的：服务以 systemd 单元、容器或定时任务方式启动时，工作目录很少恰好是仓库根。这类 bug 在开发机上永远复现不了，因为开发者的终端永远停在仓库里。

### 3.6 无记忆与佐证盲区：两条失效模式同源

第一条，重复故障不升级。我给同一块 GPU 在三小时内连注三条 XID 79，得到三条互不知情的结论：动作相同、置信度相同、理由相同。先把因果说准：三条结论相同，直接原因就是决策树是桩，换成什么架构都一样；架构层的问题在再下一层。决策树桩的注释里其实写着期望的真实规则形态，XID 79 在 24 小时内同一块 GPU 出现两次就该排空加重启。但编排器是逐条无状态处理，每条事件的分诊函数看不到历史——就算将来把这条规则写进决策树，逐条无状态的编排也放不下它。缺的不只是规则，是放状态的地方。

第二条，佐证信号被管线自己过滤掉。我手工构造了一个三条事件的窗口：同一块 GPU 先报 ECC 双比特错误计数 17，再报温度 104 摄氏度，然后是一条 XID 13。按系统提示词自己的第二条规则，XID 13、31 这类应用层故障不应在没有佐证证据时建议排空节点，反过来说，佐证齐了，判断就该不同。实测结果是：3 条事件进去，只出来 1 条结论，另外两条非 XID 事件在抽取阶段就被过滤，不生成结论，也不挂到 XID 13 的结论上做上下文。基线实验里这件事的规模版本是：64 节点窗口的 1285 条事件中，1024 条温度与 ECC 事件全部如此。管线一边在提示词里要求模型结合佐证判断，一边在数据通路上把佐证全部丢掉。

## 四、分析与取舍

### 4.1 先确定性、后 LLM 的分层是对的，而且顺序不能反

这套脚手架最值得肯定的判断，是把查表与规则放在确定性层、LLM 只做后置的推理补充，并且在决策树没写完之前全量路由人工、置信度如实给 0。理由很硬：分诊动作里排空、重启、RMA 都是对生产机群的真实操作，能由查表与规则确定的事，不该交给一个概率模型临场发挥；LLM 的价值在综合与解释，不在拍板。回看 3.4 节还有一个反直觉的推论：输出契约断裂目前反而是一道意外的安全网，正因为模型的 JSON 从没被解析进结论字段，一个胡说八道的模型今天最多污染理由文本，动不了处置动作。但这道网是事故，不是设计。正确的修法不是保持断裂，而是补上解析与校验：动作文本必须落在站点的 runbook 词表内、置信度低于 0.7 强制改写为人工复核（提示词里已经写了这条规则，要把它从提示词搬进代码）、解析失败一律降级为只保留确定性结论。谁先把解析接上、却没接校验，谁就亲手拆了这道网。

### 4.2 失效模式清单：按修复顺序排

六个失效模式里，没有一个需要换模型或改提示词，全是普通工程问题，我按修复的先后排：

一，逐条隔离。每条事件的分诊包一层异常捕获，坏数据记数并标注进报告，先保证整批结论的存活率。这是一切的前提。
二，输出契约兑现。按 4.1 节说的，把 JSON 解析、词表校验、置信度门槛写进代码，而不是停留在提示词里。
三，证据组装。把查表的 category 与 notes 纳入证据，并给分诊函数传入同 GPU 的时间窗口摘要（近期同码次数、温度与 ECC 的极值），让提示词第一条「只引用证据」变得可执行。
四，状态层。重复计数与升级规则需要窗口级聚合，这意味着管线从逐条无状态改为先聚合后分诊，是架构级改动，排在契约与证据之后做。
五，资源路径与故障降级。提示词改用包资源或绝对路径加载；provider 调用包超时与异常捕获，失败时静默降级为确定性结论并留下标注。
六，佐证信号打通。把非 XID 事件从「抽取即丢弃」改成挂到同 GPU 的 XID 结论上作上下文。它与第三项同源，但单列一项：第三项改的是证据模板，这一项改的是数据通路。

扩查表不在这六项里。它是数据字典的体力活，不是失效模式；7 个码的覆盖该扩，但排在六项之后——六项不修，表扩到 70 个码，管线照样会整批死在一条坏数据上。

### 4.3 一个判断：这类系统的可信度来自克制，不来自模型

这套脚手架里我最愿意为之辩护的设计，恰恰是它拒绝做的事：查不到的码不猜含义，决策树没写完就不给动作，模拟数据从生成器到报告头全程标 SIMULATED，桩抛 NotImplementedError 而不是返回一段编造的推理。这些克制让它的每一条输出都可复核：结论从哪来，查表、规则还是模型，一目了然。给运维系统接 LLM 时最容易丢掉的正是这个：一旦模型的流畅文本盖过了确定性部分的真实状态，值班工程师就分不清哪句是查出来的、哪句是编出来的，分诊报告也就失去了被信任的资格。本文六个失效模式全都指向同一个修复方向：让模型的活动范围、证据来源、失败方式都在代码里显形，而不是藏在提示词的措辞里。

## 五、局限与未解问题

本文的局限必须写明。第一，全部遥测为模拟器生成的合成数据，事件分布由注入概率与注入池决定，本文的比例数字只能用于验证管线行为，不能外推到真实机群的故障分布。第二，LLM 实验用的是本地假 provider，验证的是接线契约与故障传播，没有调用真实模型，因此本文对模型本身的推理质量不下任何结论；真实模型在薄证据下的实际表现（多大比例会越界编造）需要接真模型后另测。第三，实验规模上限是 64 节点、约 1300 条事件，且都在一台虚拟机上完成，没有测并发摄入、持久化与告警通道。第四，查表覆盖只统计了表内规模与表外探针，没有逐条比对 NVIDIA 官方目录的完整码表，覆盖率的分母未在本文核定。

未解问题留三个：窗口聚合的粒度怎么定，同 GPU、同节点还是同 NVLink 域，三个粒度的升级规则与误报代价不同，需要真实故障序列才能标定；置信度门槛 0.7 是提示词草稿里拍的数字，没有校准依据，真实模型上线后要用历史工单回放来定；佐证证据进入分诊后，温度与 ECC 的基线事件量是 XID 事件的四倍上下，证据组装的成本与上下文长度怎么控，要在接真模型时一并实测。
