# 估出来的 s 敢不敢用：面积中位数反推缩放系数的端到端误差链实测

作者：Guangyi Zhao

## 1. 问题与背景

这个系列里我欠了两笔账，这篇一起还。

第一笔在 2026-10-20 那篇的第 4 节：我给了一条部署处方——换机位后不必重跑全套标定，先拍几帧，量出开花轮廓面积中位数，与基准中位数（3,806 px²）之比开根号，就是缩放系数 s 的估计 ŝ，再按 ŝ 全套缩放三个参数。当时我如实标注了：这条估计式没有单独验证过端到端精度，实验里的 s 是重采样给定的真值、不是估出来的，它只能算候选做法，不算结论。

第二笔在 2026-10-24 那篇的第 4 节：选路规则也开始消费 s——s≥0.30 走参数缩放（P 路线，便宜），0.15≤s<0.30 走输入重采样（U 路线，贵但稳），s<0.15 报警挪机位。那篇结尾同样留了话：现场靠估计 s 选路时，估计误差的影响未测。

两笔账是同一条误差链：面积量得准不准 → ŝ 偏多少 → 偏了的 ŝ 喂进参数缩放掉多少 F1 → 喂进选路规则选错几次、每次代价多大。这篇把链条整条量一遍。先说结论：估计式本身的偏差不是主要风险，真正的风险在量面积的那道工序——如果你用检测器自己的形态学管线去量，你量的是一个正在被核杀死的分布，ŝ 会在一段连续的尺度上系统性高估 13% 以上；而下游对误差的容忍是不对称的，低估宽容、高估危险，这个不对称又恰好能被一个固定的收缩系数利用。

场景与口径与前三篇完全一致：Bloom-Counter 颜色分割管线（`detector/color_segmentation.py`，基准参数 `min_area=120`、`bloom_area_min=900`、核 7），模拟器 4 张 1280×960 场景（种子 101/202/303/404），210 个目标（开花 134、花苞 76），逐个中心匹配、类别一致才算命中，4 场景微平均。基准自检 F1 1.000。

## 2. 方法

s 取 15 档：1.0 / 0.8 / 0.65 / 0.5 / 0.4 / 0.35 / 0.30 / 0.28 / 0.25 / 0.22 / 0.18 / 0.15 / 0.12 / 0.10 / 0.07，其中 0.35、0.28、0.18、0.12 是为选路边界（0.30 与 0.15）两侧加密的。每档先用 INTER_AREA 把基准图缩成原生小帧（与前作 A 组同一生成方式），然后测四件事：

**估计器（四个）**。每个估计器分两步：标定步在基准帧上用带真值匹配量出它自己的开花面积中位数作参考值；现场步在新机位帧上无真值地量出开花中位数，ŝ=√(现场中位数/参考值)。四个估计器只差在「怎么量面积」：

- ORA7：真值匹配 + 基准形态学（核 7）后的轮廓面积（`contourArea`），即 2026-10-20 篇量面积漂移用的方法。参考值 3,806.0，与那篇的基准中位数逐位一致。它需要真值，现场不可部署，只作这一类估计器的上界。
- BLIND7：把 ORA7 的管线原样搬到现场——核 7 形态学后的全部轮廓面积，在 log 面积上做一维 2-means 聚类，上簇中位数当开花中位数。这是「复用检测器代码量面积」的最自然实现，也是 2026-10-20 候选做法的字面实现。
- BLIND3：同上，但形态学核换成 3（最小的奇数核，只做最低限度的闭合与去噪）。参考值 3,740.0——这是核 3 管线在同一批基准帧上自己标出的开花中位数，与核 7 的 3,806 不是同一测量、不是笔误，两者相差 1.7% 正是核尺寸对面积的直接作用（第 3.1 节有对照）。
- BLINDRAW：不做形态学，直接用原始花瓣掩膜的连通域像素面积聚类。它的参考值是基准帧上按真值合并同一开花的全部碎块后的像素面积中位数，3,718.5——因为一张开花的原始掩膜本来就可能是好几块。

盲估计器的可信守卫在跑端到端之前就定死（预注册）：两簇分离度 ln(上簇中位数/下簇中位数) ≥0.8 才采信，否则记为拒绝（REFUSED）。基准帧上两类面积中位数之比的 ln 是 2.40，0.8 是个宽松门槛。

**容忍度扫描（与估计器无关）**。P 路线参数按 s_used=f·s_true 缩放，f 取 0.6 / 0.7 / 0.8 / 0.9 / 1.0 / 1.1 / 1.25 / 1.4 / 1.6，量每个 f 的 F1。这一步把「下游能容忍多大误差」和「估计器实际有多大误差」分开测，免得把两件事的功过混在一起。

**端到端**。每个估计器的 ŝ 分别喂 P 路线（参数按 ŝ 缩放）与选路规则，与用真值 s 的 oracle 对照。选路的执行口径：选中 P 就用该估计器自己的 ŝ 参数跑（不是 oracle 参数），选中 U 就跑 U-LINEAR，s<0.15 的在跑 U 的同时记一次报警。守卫变体：盲估计器被拒绝时不选路、直接回退 U。

原始数据与脚本：`data/2026-10-25-bloom-s-estimation-bench.json` 与同名 bench 脚本，仓库虚拟环境一条命令可复跑。

先看上界。ORA7 的偏差是 2026-10-20 篇面积漂移的直接投影：轮廓面积系统性小于 s² 预测（开花 -1.4% 到 -10.4%），开根号后 ŝ 系统性低估，从 s=0.8 的 -0.7% 一路走到 s=0.12 的 -13.0%。方向恒定、量级可预期，这本身不吓人。吓人的是尾巴：s=0.10 时它突然回到 -0.1%，s=0.07 时翻成 +37.0%——不是估计变准了，是能匹配到的开花只剩 44 个、6 个（总数 134），活下来的全是同类里最大的那批，中位数被幸存者偏差抬了上去。匹配数（134→133→130→126→118→97→44→6，随 s 递减）才是这一行真正的读数：s≤0.10 时 ORA7 的数字没有意义，无论它看起来多接近真值。

BLIND7 在 s≥0.35 与 ORA7 逐位重合——花苞还活着、两簇还分得开时，盲聚类找得到正确的上簇。但它的聚类计数把塌方过程录了下来：下簇（花苞）在 s=0.4 时只剩 44 个（真值 76），s=0.35 只剩 18 个——核 7 正在杀花苞，与前两篇的形态学存活数据完全对上。到 s=0.30，花苞轮廓基本被杀尽，2-means 只能把 130 来个开花轮廓劈成两半（68+63），上簇中位数 439.5 而真开花中位数（ORA7 口径）是 317.0，ŝ 于是高估 +13.3%。此后 0.28 到 0.15 一整段都钉在 +12% 到 +16%：这不是噪声，是「拿待标定的管线量标定量」的循环依赖——你要估的正是核的杀伤半径，而你的尺子先被同一把核削过。分离度守卫在这六档全部拒绝（分离度 0.595–0.729，均 <0.8）：劈开花得到的两簇挨得很近，守卫认得出这不是真双峰。但守卫不是万能的：s=0.12 时分离度 0.833 擦线通过（误差 +12.2%）；s=0.10、0.07 时它也通过了，而那时全场只剩 49 个、13 个轮廓（单帧连 8 个轮廓都凑不齐、逐帧估计全部无结果），ŝ 高估 +80.9%、+162.0%——样本量塌了，分离度却因为幸存轮廓彼此离散反而变大。只看分离度的守卫管得住中段，管不住极端档。

BLINDRAW 的塌法在另一头。s=1.0 时它给出 -55.1%：基准尺度下开花的原始掩膜是碎的，4 帧共 445 个连通域（真值对象 210 个），上簇是碎块与整花的混合，中位数 751.0 对合并参考 3,718.5，完全不是一回事，而且分离度守卫没拦住（它劈出的是噪声小碎块与「其余一切」，分离度反而高达 6.621）。但只要 s≤0.65，缩放先把花瓣间隙压到像素以下、碎块自己合并，BLINDRAW 立刻变成全场最准的估计器：合池误差全部在 ±1.0% 以内，一路到 s=0.07 的 -3.4%；逐帧误差在 s≥0.12 时收在约 ±2.3 个百分点内，0.10 与 0.07 两档放宽到 -4.4% 与 -6.3%——那两档开花中位面积只剩 37 与 17 px，单个像素的量化步长已经占到面积的百分之几，逐帧抖动放大是量级使然，不是估计器又坏了一种。过渡带在 s=0.8：合池 -4.4% 看着还行，逐帧却是 -55.4% 到 -2.0%——两帧还在碎、两帧已合并，合池把不稳定藏住了。这是本文第二次撞见「合池数字掩盖逐帧不稳定」，口径上以后凡报合池估计，必须同时报逐帧范围。
