# 扫描器报出来的漏洞，有多少是真的：Web-Vuln-Scanner 检测管线与误报控制实测

作者：Guangyi Zhao
日期：2026-10-15
实测对象：Web-Vuln-Scanner（自有开源项目，github.com/Ezra-Zhao/Web-Vuln-Scanner），scaffold v0.1，Python 3.12.3
实测环境：Linux x86_64 虚拟机；全部目标均为本机 127.0.0.1 上的自有应用（仓库自带演示应用 + 本文为实验编写的五个靶子应用），未扫描任何第三方系统

## 一、问题与背景

漏洞扫描器的报告有个很少被当面讨论的问题：报出来的条目，有多少是真的？

误报的代价不是「多看两眼」。一条假的高危 SQL 注入会把值班的人拖进一轮完整的排查：一边确认、复现、翻代码，最后发现页面只是在正文里提了一句数据库错误。误报多了，报告就没人细看了，真漏洞混在里面一起被划过去。所以检测管线的设计里，误报控制不是锦上添花，它决定这份报告值不值得被信任。

我自己的开源项目 Web-Vuln-Scanner 是一个 ethics-first 的小型扫描器：必须显式给目标、必须确认授权才肯跑。它现在有四项检查——反射型 XSS、基于错误的 SQL 注入、安全响应头、敏感路径探测。项目状态先说清楚：scaffold v0.1，README 里就是这么写的。存储型 XSS、盲注、CSRF、登录后扫描都没做，源码里以 TODO 明记，不假装有。

本文不写使用教程。我把这条检测管线放到六个靶子上跑了一遍：一个故意写漏的演示应用、一个按规矩写好的加固应用、一个对所有未知路径都返回 200 的单页应用壳、一个正文里正常谈论数据库错误的文章站、一个只有 POST 表单且表单背后真有注入的应用、一个把输入原样反射进 JSON 响应的接口应用。六个靶子分别量四件事：真漏洞抓没抓到、没漏洞时会不会乱报、误报以什么形态出现、管线的视野边界在哪里。结论先放这里：四项检查的判定逻辑各自克制，但真正闹出误报的两项检查（敏感路径探测与基于错误的 SQL 注入），缺了同一样东西——基线。没有「先看正常响应长什么样」这一步，软 404 的站点能让敏感路径检查 14 条全错，正文里一句「database error」能换来一条高危注入警报。

## 二、方法与架构

代码总量 846 行（含演示应用与测试）。管线是四段串行：scope.py 先做授权校验，crawler.py 同主机爬行收集页面、表单与带参数的 URL，四个检查各自独立对爬行结果运行，report.py 输出控制台与 JSON 报告。检查之间不共享状态，每个检查崩了不会拖死整轮扫描，CLI 层有逐检查的异常兜底。

四项检查的判定逻辑逐项交代，后文所有结论都从这里推：

反射型 XSS（scanner/checks/xss.py）：生成 8 位随机令牌，拼成形如 `"><svg/onload=alert('令牌')>` 的载荷，注入每个 URL 参数与每个表单字段。只有当响应正文里同时出现令牌原文和完整载荷原文，才报高危。转义过的反射（引号或尖括号被编码）不会命中，因为完整载荷对不上。

基于错误的 SQLi（scanner/checks/sqli.py）：载荷只有 4 个（单引号、双引号与两个恒真式），把响应正文拿去匹配 6 组数据库错误特征（SQLite、MySQL/MariaDB、PostgreSQL、MSSQL、Oracle 与一个通用组，共 21 条正则，含 `syntax error`、`database error` 这类通用词）。命中即报高危，每个参数只报一条。判定过程不发基线请求，不比对注入前后的响应差异。

安全响应头（scanner/checks/headers.py）：只看目标首页一个响应。缺 Content-Security-Policy、X-Frame-Options、X-Content-Type-Options、Referrer-Policy、Permissions-Policy 五个头逐个报，HTTPS 时另查 HSTS；响应带 Server 头则报一条 info 级版本暴露。

敏感路径（scanner/checks/sensitive_files.py）：固定探针表 14 条路径（.git/HEAD、.env、admin、backup.zip、db.sqlite 等），逐个请求，不跟随重定向，状态 200 且响应体非空就报，严重度按路径预设，从 info 到 high。判定不看响应内容——源码 TODO 里写明了软 404 识别与内容嗅探都还没做。

爬虫的视野决定检查的视野：只跟同主机链接，最多 20 页（默认值），只收 Content-Type 为 text/html 的页面，非 HTML 响应直接跳过、不记录、也不解析其中链接。

实验方法：仓库代码原样不改。演示应用用仓库自带的 demo/vulnerable_app.py；其余五个靶子为本文实验现写，源码随实验脚本一并归档。每个靶子走完整管线（爬行加四项检查），逐检查记请求数与耗时；演示应用重复跑三轮验稳定性；另对授权校验做五组探针，对 JSON 接口做一次手工载荷反射探针。实验脚本与原始 JSON 随本文归档，数字可复跑核对。

## 三、实测数据

### 3.1 演示应用：植入的四类问题全抓到，一轮 31 个请求

演示应用故意植入四类问题：/search 反射型 XSS、/user 字符串拼接 SQL 加详细错误回显、无任何安全头、/admin 与 /.git/HEAD 等敏感路径。扫描结果总计 13 条：

| 检查 | 请求数 | 命中 | 内容 |
|---|---|---|---|
| 爬行 | 4 | 4 页、1 表单、2 个带参 URL | — |
| reflected-xss | 3 | 3 | 参数 q、参数 id、表单字段 q 各一 |
| error-based-sqli | 9 | 1 | 参数 id（SQLite 错误泄露） |
| security-headers | 1 | 6 | 五个头全缺，加 Server 版本暴露 |
| sensitive-files | 14 | 3 | /robots.txt、/.git/HEAD、/admin |

整轮 31 个请求，逐检查耗时 0.04 到 0.19 秒，本地总时长不到 1 秒。三轮重复扫描结果一致：均为 13 条，严重度分布相同（high 5、medium 2、low 3、info 3），判定是确定性的，没有随机成分。

一条命中要展开说：XSS 在 /user?id= 上也报了。/user 的参数 id 本是 SQLi 的地盘，XSS 载荷被拼进 SQL 语句后触发数据库错误，错误信息原样回显进页面的 pre 标签，载荷在错误页里未转义反射，于是 XSS 检查命中。这条算真阳性，但路径是「经由错误回显的反射」，不是应用把参数渲染进正常页面。只看标题「Reflected XSS via parameter 'id'」的人会去错地方找问题——检查给得出证据字符串，给不出反射发生的上下文，这是报告表达的欠账。

仓库自带测试 11 个，pytest 全过，用时 1.61 秒，覆盖四项检查对演示应用的命中与 scope 校验。

### 3.2 加固应用：零漏洞命中，只剩一条躲不掉的 info

第二个靶子按规矩写：输出用 html.escape 转义、SQL 用参数化查询并校验类型、五个安全头全配、未知路径返回真 404、无敏感路径。扫描结果：四项检查里 XSS、SQLi、敏感路径全是 0，只剩 security-headers 的 1 条 info——Server 头暴露 Werkzeug 版本。

这条 info 值得单独说。它不是应用代码的问题：Server 头由开发服务器在响应层自动加上，本实验的加固应用没有去处理它。也就是说对跑在框架开发服务器默认配置上的目标，这条 info 大概率会出现，与目标自身的代码质量无关。把它写进「加固应用也躲不掉」不是苛责检查，而是提醒读报告的人：info 级的条目要先看来源层级，别把框架的默认行为记在应用头上。

本节的正面结论同样重要：在「正常写好的应用」这个基线上，四项检查的漏洞类命中是 0。误报不是这条管线的常态，它出现在特定的站点形态里，就是下面三节。

### 3.3 软 404：14 条探针全错，一份 93% 是噪声的报告

第三个靶子模拟单页应用（SPA）与兜底路由的常见形态：任何未知路径都返回 200 和应用壳页面，它本身配齐了五个安全头，搜索页输出也做了转义，是一个没埋漏洞的应用。扫描结果总计 15 条，其中 sensitive-files 一项就报了 14 条——探针表 14 条全部命中，包括 .env（high）、db.sqlite（high）、database.sql（high）、.git/HEAD（high）、backup.zip、phpinfo.php 等；剩下 1 条是 Server 版本暴露的 info（与 3.2 节同一条）。14 条敏感路径命中全是误报，该项误报率 100%；整份报告 15 条里 14 条是噪声，占 93%。

原因在判定逻辑里写得明白：只认状态码 200 与响应非空，不验内容。这类站点的每个路径都是 200，探针表有多长，误报就有多少。源码的 TODO 已经写了修法——先请求一个随机不存在的路径拿软 404 样本，再比对相似度——但在它实现之前，这个检查在 SPA 站点上的输出应该整段打上不可信标记，而不是混在真发现里按 high 排序。实际影响也在这里：一份报告里排在最前面的四条 high 全是假的，读报告的人对后面真条目的信任会被一起消耗。

### 3.4 没有基线比对：一句正文换来一条高危

第四个靶子是一个文章站，页面正文在正常讨论数据库错误，原文里有「database error」和「SQL syntax」字样，页面参数 topic 不参与任何 SQL 查询，不存在注入。扫描结果：error-based-sqli 报 1 条 high，「Possible SQL injection via parameter 'topic' (Generic SQL error disclosed)」。

拆解这次误报的机制：检查把 4 个载荷依次拼到参数上，每个响应都拿去匹配错误特征；文章正文与载荷无关、恒定包含特征词，于是第一个载荷就命中，与注入是否发生毫无关系。判定缺了基线这一步：没有先发一次不带载荷的请求、确认特征词在正常响应里是否已经存在。基线比对是注入类检测的常识动作（连这个项目自己在 SQLi 源码 TODO 里给盲注写的方案都是比对真假条件两次响应的差异），但错误型检测这一路没做。6 组特征里通用组用的又是 database error 这类日常词，误报门槛进一步降低——正文里只要在谈数据库运维，就可能中招。

这一条和 3.3 节是同一种病的两个器官：判定只看「响应里有没有我要找的东西」，不看「这东西在我没攻击之前是不是已经在那里」。

### 3.5 POST 表单：真注入在眼前，检查按设计跳过

第五个靶子只有一个 POST 表单，表单背后的查询用字符串拼接、错误详细回显——一个真的、可利用的 SQL 注入。扫描结果：error-based-sqli 报 0。它在源码里明确只测 GET 表单与 URL 参数，POST 表单直接跳过，TODO 写明未做。这次漏报是设计边界，不是实现 bug，但报告里不会有任何地方提示「这个表单没被测过」，读报告的人看到的是干净的 0。

同一个靶子上还出现了一组对照：XSS 检查测 POST 表单，它报了 1 条 high——它发的 HTML 载荷因含引号意外触发了后端 SQL 报错，错误页把载荷未转义回显，XSS 检查据此确证了反射型 XSS（与 3.1 节同一条回显路径，它记下的是 XSS 本身，不是 SQLi）。但注意那次响应里客观上带着完整的数据库错误信息，只是管线里没有任何一环去匹配它：SQLi 检查跳过了 POST 表单，XSS 检查不看错误特征。证据在流量里出现过，却没有任何检查负责认领它。跨检查的证据不能互通，是管线分工的代价：每个检查只对自己的结论负责，没人对「覆盖是否完整」负责。报告里加一节「未覆盖面清单」（哪些表单、哪些参数没被哪项检查测过），成本不高，能把这种沉默的漏报变成显式的边界。

### 3.6 JSON 接口：爬虫的视野之外

第六个靶子首页链向一个 JSON 接口 /api/search?q=，接口把 q 原样放进 JSON 响应。我另外手工发了一次 XSS 载荷探针验证：接口 200 返回，Content-Type 为 application/json，令牌与完整载荷都原样出现在响应体里——也就是说，若这个端点被探，XSS 检查的命中条件会成立。但正式扫描里它从未被探：爬虫请求到该链接后，因 Content-Type 不是 text/html 直接跳过，端点没进页面列表，也没进带参 URL 列表，两项注入检查的输入里根本没有它，最终总结果 6 条全是 headers 类条目，注入类为 0。

这条的定性要克制：JSON 响应里的原样反射在 application/json 的内容类型下并不等同于 HTML 上下文的 XSS，现代浏览器不会把它当页面执行；把它说成漏报一个 XSS 是夸大。真正的结论是视野问题：这条管线只能看见 HTML 页面构成的那部分应用，接口型端点（API、JSON、移动端后端）整体在视野之外，而报告不会告诉你视野有多大。对一个自称 web 扫描器的脚手架，这需要在报告里明示，不是在 README 里提一句就算数。

### 3.7 授权护栏：五组探针

最后一组是对 scope.py 的探针，与检测质量无关，量的是这条管线肯不肯跑：

| 探针 | 结果 |
|---|---|
| 目标不带 http(s) 前缀 | 拒绝（ScopeError，要求显式 URL） |
| 未确认授权 | 拒绝（ScopeError） |
| 已确认 + 本地目标 | 放行 |
| allowlist 不含目标主机 | 拒绝 |
| allowlist 含目标主机 | 放行 |

五组全符合设计：没有默认目标、没有确认不跑、给了白名单就按白名单收口。护栏本身是代码强制而非文档倡议，这一点在同类学习型扫描器里并不常见，值得记一笔。

## 四、分析与取舍

### 4.1 四项检查的误报控制，成色各不相同

把四项检查按判定方式排一遍，能看清各自的误报成色。XSS 是证据最硬的一项：随机令牌加完整载荷双条件，天然排除了转义反射与静态内容，加固应用上是干净的 0，它的问题只在上下文表达（3.1 与 3.5 节里经错误页的反射与正常渲染不分）。敏感路径是判定最弱的一项：只认状态码，内容零验证，在当代最常见的 SPA 部署形态下整项失效。SQLi 居中：载荷与特征都不算离谱，但没有基线比对，使它在「谈论数据库的站点」上系统性误报；特征词选得越通用，这个问题越重。headers 是确定性最高的一项：有就是有、缺就是缺，唯一要提醒的是 Server 这条 info 的来源是服务器层，与应用代码无关，分级时不该与应用自身缺头混排。

### 4.2 修复顺序：先基线，后扩面

按性价比排修复顺序。第一，基线与软 404 样本：敏感路径检查先取一个随机路径的响应作基线，探针响应与基线高度相似的降级为 info 或不报；SQLi 在注入前先发基线请求，特征词已存在于基线响应的参数直接跳过。这一项同时治 3.3 与 3.4 两节，是误报控制的枢纽。第二，内容嗅探：.git/HEAD 应以 ref: 开头、.env 应含键值行，探针命中后再验内容，验不过不升 high——源码 TODO 里已有这个想法，排在基线之后是因为基线对全部 14 条探针都有效，嗅探要逐路径写规则。第三，报告加未覆盖面清单：POST 表单、非 HTML 端点、超过爬行上限的页面，逐项列明没测什么，把漏报从沉默变成显式。第四，才是扩面：POST SQLi、存储型 XSS、盲注都在 TODO 里，但扩面扩大的是承诺，基线没补之前，扩得越大、误报越多。

顺序背后的判断是：扫描器的可信度先来自「报出来的大体是真的，其次才是「能报的足够多」。这条管线当前的状态恰好反过来：覆盖在涨（哪怕是 TODO 里的规划），而判定基线还没补齐。

### 4.3 一个判断：误报控制的本质是给每条结论配上「反证程序」

回看四项检查，判定可靠的那一项（XSS）有一个共同结构：结论附带一个排他性证据——随机令牌不可能在页面里预先存在，完整载荷原样出现排除了转义。不可靠的两项缺的正是这个：状态码 200 不是排他性证据（软 404 也是 200），正文里的特征词不是排他性证据（没注入时它也在）。给检测管线做误报控制，落到工程上就是给每类判定补一道反证程序：先证明「不攻击时它不在」，再报告「攻击后它出现了」。基线请求、软 404 样本、随机令牌，都是同一件事的不同实现。这也是为什么我把基线排在所有扩面工作之前——它不是某个检查的补丁，而是判定方法论的缺口。

## 五、局限与未解问题

本文的局限写明。第一，六个靶子全部是本机自建的最小应用，每个靶子只隔离一种站点形态；真实站点的形态是混合的（SPA 加真敏感文件、文章站加真注入），本文没有测混合形态下误报与真报的相互影响。第二，加固应用由作者本人按检查清单反着写，存在「按考点复习」的偏差：它证明了检查在理想基线上不乱报，不证明真实世界里写得一般的应用上有同样的低误报。第三，全部实验是单机回环请求，耗时数字只说明本地量级（3.1 节的 0.04 到 0.19 秒是演示应用一轮的逐检查耗时；六个靶子全部逐检查耗时的极值范围为 0.003 到 0.23 秒），真实网络延迟下敏感路径的 14 个串行请求与注入检查的逐参数串行载荷会把总时长拉长，本文未测并发与超时行为（每请求超时在源码里统一为 10 秒，最坏情况的等待未实测）。第四，XSS 经错误页反射这条路径，本文定性为真阳性，依据是载荷确实未转义进入 HTML 响应；它在真实浏览器里的可利用性取决于错误页的内容类型与上下文，本文未做浏览器级验证。第五，靶子应用与演示应用同为 Flask/Werkzeug 栈，框架换成其他栈时 Server 头、错误页形态都会变，结论的普适性限于同类形态。

未解问题留三个：基线相似度用什么算法与阈值判定软 404，太松漏真文件、太紧误杀真页面，需要一批真实 SPA 样本标定；SQLi 做了基线过滤之后，对「注入前后都回显同一段错误堆栈」的目标会不会把真报一起过滤掉，需要构造这类目标另测；未覆盖面清单做到什么粒度（列端点、列参数、还是列检查乘端点的矩阵），要等真在报告里加上、用过一轮再定。
