# 内存和磁盘都压过了，缺口只来了 46 个包：台架缺口的内存与 IO 维度实测

作者：Guangyi Zhao

## 1. 问题与背景

台架缺口的旧案查到第三篇了。2026-10-28 量注入带告警时，发生器发出 10,000 个包、进入代理的却时少时多，第一跳缺口 gap = 1 − in_client/sent 在那批 28 轮里从 0 漂到 29.8%，大到能左右告警结论。2026-11-03 我用受控实验查 CPU 一维：纯 CPU 负载直到 1.5 倍超订，缺口才常态出现，最大 9.69 个点——形状、机制（接收缓冲溢出，逐包对账）、上界都清楚了，唯独 29.8% 复现不出来。那篇结尾写明：缺口需要 CPU 之外的共因子，下一笔账查内存与磁盘 IO 两维。

这一篇还这笔账。设计与 CPU 篇同构：同一条链路（发生器、故障代理、q=0 计数垫片、回声服务器）、同一组注入参数（双向丢 20%、延迟 40 加抖动 30 毫秒、抖动窗 0.6/2.5、代理种子 1234）、同样的流量（2000 pps 乘 5 秒共 10,000 包），判定线 0.75 与分解线 0.10 沿用冻结值，只换操纵变量。内存臂四档：驻留触摸内存 0、0.5、1.0、1.6 倍基线可用内存（以 bench 启动时实测 MA0 为准，绝对上限 1000 MB）。IO 臂四档：0、1、2、4 个同步写进程，每个循环做 4 KB 追加写加 fdatasync——这台机器的盘本来就慢，立项实测 fdatasync 单次平均 22.1 毫秒。每档 4 轮，两臂共 32 轮。设计、护栏（可用内存连续两次低于 120 MB 立即杀内存 hog、该轮留账）与八条预测在跑数前冻结落盘（data/2026-11-11-memio-gap-prereg.md）。

结论先行：两维都压过了，缺口基本没来。32 轮里 31 轮缺口精确为零，唯一非零的一轮出现在内存最高档，46 个包、0.46 个点，且与系统接收缓冲错误的增量逐包相等（46 对 46）。可压力不是没加上：IO 臂最高档每轮的 IO 全停顿（PSI io full）中位 2.48 秒、是零档的约 22 倍，往返时延 p99 涨了 14%；内存臂把轮内可用内存最低点压低了约 430 MB。也就是说，在各自的压力指纹都确凿动了的前提下，内存（驻留 1 GB、无换页）与磁盘 IO（4 个同步写手把盘的同步带宽吃满）单独都造不出缺口——排除法又划掉两维。29.8% 的旧案还剩下的嫌疑，是多维同时在场与突发式压力，写在第 5 节。

## 2. 方法

- 内存 hog：自有 Python 进程，按档位分配 bytearray 并逐页写入触摸，随后循环逐页重触摸保活，让内核不能廉价回收它。每档首轮前启动、分配加全量触摸完成并稳 2 秒后才开跑，该档跑完杀掉。护栏线程每 0.25 秒采样 MemAvailable，本轮 32 轮从未触发。
- IO hog：自有 Python 进程组，每写手一个独立文件（跑后删除），4 KB 写加 fdatasync 死循环，退出时汇总各自完成的同步写次数。整档（预热加 4 轮）完成量：一写手 1,459 次、二写手 2,066 次、四写手 3,901 次——写手数翻倍，总量只涨到 1.42 倍与 2.67 倍，同步通道饱和的形状与 3.3 节 PSI 停顿的饱和互证。
- 每轮记录：全链六跳逐向计数、exporter 真实 collect() 回读的总丢包 L 与重构 D 所需五量、轮前 loadavg、轮内 MemAvailable 采样（0.25 秒间隔的最小值与中位）、轮前后 PSI memory/io 的 some/full 停顿增量、/proc/vmstat 的扫描/回收/换页增量、系统级 UDP RcvbufErrors 与 InErrors 增量。
- 量法沿用前作：gap 如上；L_iso 为隔离口径丢包；D = 1 − in_server/F_c；顶线所需缺口 g* 以两组零档合池 L_iso 均值解析求解。操纵检验预注册在内：某档压力指纹（PSI）不动，该档的零结果只许读作压力没加上，不许读作该维无害——这一条在本轮内存臂上真的用上了，见 3.2。
- 两个画像数字先交代。本机名义 8 GB，与多条生产线共用，立项采样时 MemAvailable 只有 622–672 MB；但 bench 真正启动测 MA0 时它已回到 1,199.2 MB（5 次采样中位），IO 臂期间零档轮内中位甚至到 1,769 MB——主机状态在约 13 分钟的实验窗内自己漂了。档位按启动时 MA0 定格（599/1000/1000 MB，见 3.2 的封顶说明），漂移本身作为局限记入第 5 节，不拿它冒充操纵量。

## 3. 实测数据

### 3.1 总账：32 轮只有一轮非零

|---|---|---|---|---|---|
| M0 | 无 | 0 / 0 / 0 / 0 | 0 | 0.5273 | 0 |
| M1 | 驻留 599 MB | 0 / 0 / 0 / 0 | 0 | 0.5271 | 0 |
| M2 | 驻留 1000 MB | 0 / 0 / 0 / 0 | 0 | 0.5257 | 0 |
| M3 | 驻留 1000 MB（封顶，见 3.2） | 0 / 0.46 / 0 / 0 | 0 | 0.5243 | 0 |
| I0 | 无 | 0 / 0 / 0 / 0 | 0 | 0.5264 | 0 |
| I1 | 1 写手 | 0 / 0 / 0 / 0 | 0 | 0.5269 | 0 |
| I2 | 2 写手 | 0 / 0 / 0 / 0 | 0 | 0.5266 | 0 |
| I3 | 4 写手 | 0 / 0 / 0 / 0 | 0 | 0.5271 | 0 |

六跳逐向对账比总账更干净：32 轮乘 6 跳，只有第一跳在 M3 第二轮缺过 46 个包，其余 191 个跳次读数全部精确为零——链路除了注入丢包之外是无损的，与 CPU 篇超订档「下游跳也开始缺」形成对照。唯一缺口事件的归属与 CPU 篇同一种签名：该轮系统级 RcvbufErrors 增量正好 46，与缺口包数逐包相等，即代理有那么一小阵没及时收，内核在缓冲满时丢了 46 个。总丢包 L 全轮在 0.5157–0.5303 之间，无一轮接近 0.75；D 在 32 轮里恒为 0.0000（不是小于线，是逐轮精确零）。

还有一个与 CPU 篇不同的地方：注入基线自己纹丝不动。L_iso 八档均值全在 0.5243–0.5273 之间（极差 0.30 个点），抖动份额合池去程 23.5%–24.1%、回程 3.0%–3.2%，逐档无趋势。CPU 超订时基线漂了 +3.57 个点（决策时刻被调度滞后糊住），内存与 IO 两维连这个指纹都没有——它们没有碰到代理的读包节律本身。

### 3.2 内存臂：压力是「存量」不是「流量」，且最高两档被封顶合并

先认设计账：MA0 实测 1,199.2 MB，1.0 倍与 1.6 倍分别是 1,199 与 1,919 MB，双双撞上预注册的 1000 MB 绝对上限，于是 M2 与 M3 的 hog 一样大（各 1000 MB）。最高两档的对比强度因此打了折——M3 相对 M2 多出的只有 hog 存活期间背景状态的差异，不是一个更大的驻留量。这一条跑前没有预见到（立项采样时可用内存只有约 0.64 GB，按当时的 MA0 估算封顶不会触发），如实记档，正文所有涉及 M2/M3 对照的读法都按「同量两批」处理。

压力到底加上没有，两组读数方向不同，都报。加上的证据：轮内 MemAvailable 最低点的中位，M0 为 1,130 MB、M1 为 698 MB、M2 为 719 MB、M3 为 802 MB——hog 确实驻留了，把可用内存的地板压低了 430 MB 上下，护栏（120 MB 线）全程没有接近。没加上的证据更要紧：32 轮里 pswpout 与 pswpin 增量全程为零，一次换页都没有发生；PSI memory full 每轮增量中位反而逐档下降（M0 93 毫秒、M1 61 毫秒、M2 20 毫秒、M3 5 毫秒）。按预注册的操纵检验，内存臂的「压力指纹」没有随档位上升——但这不是 hog 没干活：PSI 是整机口径（含同宿主的其他租户），M0 恰好跑在本轮实验窗的最前面、背景回收活动最重（M0 四轮 pgsteal 合计 244,842 页，远高于 M1 的 2,881 页，那不是 hog 的账，hog 还没启动）。机制上说得通的是另一条：驻留 hog 是一次性存量压力——分配加触摸在预热期就把页缓存挤掉、达成平衡，开跑后它只是反复重触摸自己的页，不再产生持续的回收工作；链路组件的匿名页从未被挤出（无换页即无缺页重读），接收循环就没有被内存子系统饿住的通道。CPU hog 与 IO hog 都是持续做功的流量型压力，驻留内存不是——这是本轮内存臂最值得带走的区分，比「内存无害」准确得多：本轮压根没有制造出持续的内存停顿，结论只许写成「1 GB 级驻留存量、零换页的压力形态下缺口不出现」。

唯一那 46 个包出现在这臂的最高档一轮里（M3 第二轮，轮内 MemAvailable 最低 615 MB、pgsteal 增量 64,803 页），签名仍是接收缓冲溢出。它更像背景回收活动与 hog 存量叠加时的一次短暂滞后，而不是档位效应的开端——同档其余三轮与全部其他轮次都是零，正文不把它读成趋势。

### 3.3 IO 臂：停顿确凿、时延确凿，缺口为零

IO 臂的操纵检验没有歧义。PSI io full 每轮增量中位：I0 为 0.114 秒、I1 为 2.357 秒、I2 为 2.374 秒、I3 为 2.483 秒——一个写手就把整机 IO 全停顿抬了约 20 倍，之后饱和（写手数再翻倍，停顿只微涨，盘的同步队列已经排满）。链路自己的体感也对得上：往返时延 p99 中位从 I0 的 136.4 毫秒涨到 I3 的 155.9 毫秒（+19.6 毫秒、+14.3%），代理逐轮迭代末尾 flush 决策日志、发生器与服务器也各有文件输出，这些 IO 都实实在在慢了。

但缺口四档全零。原因从量级上能讲清：fdatasync 的 22 毫秒是写手自己的等待，不是链路的等待——页缓存吸收了链路的顺序写（代理日志是缓冲写、flush 只到内核不落盘等确认），链路进程没有任何一步在等磁盘确认；时延涨的那 19.6 毫秒摊在包的往返账上（抖动窗本身有 30 毫秒的量级），没有转化成接收循环的成批停摆。接收缓冲 212,992 字节在 2000 pps 下容得下零点几秒的量，IO 停顿要饿住它，得先让某个链路进程整段阻塞到那个量级——同步写压力下没有任何一环有这种阻塞点。换句话说，这一维的压力打在了链路不设防也不受伤的地方：它没有同步 IO。

### 3.4 误报余量：排除图又添两块

解析层照旧：以两组零档合池 L_iso 均值 0.5268 解顶线所需缺口，g* = 47.17%——与 2026-10-28 的 47.1%、2026-11-03 的 47.19% 三次互证（基线差零点几个点所致）。把三篇的实测上界并排，注入带告警的台架排除图现在长这样：纯 CPU（至 1.5 倍超订）最高 9.69 个点；纯内存驻留（至 1 GB、零换页）最高 0.46 个点；纯磁盘同步 IO（至整机 IO 全停顿每轮约 2.5 秒）最高 0 个点。三维单打没有一维够到 g* 的五分之一强。运维读法随之更具体：若哪天真见到 20 个点以上的第一跳缺口，按本系列证据，它不来自这三维中任何一维的单独作用——要么是多维同时在场，要么是压力的形态不同（突发尖峰而非持续档位），要么台架之外还有没进过实验的变量（同宿主其他租户的 UDP 流量挤同一批缓冲、宿主机层面的调度事件）。这三条正是第 5 节的未解问题清单。

### 3.5 预注册对账

P1（内存四档中位数非递减）：字面命中但无信息量——四档中位数全为零，非递减成立，实质内容由 P3 判定。P2（两组零档 8 轮全 ≤ 2 个点）：命中，实测全为零。P3（M3 中位数 ≥ M0 + 2 个点）：未中——M3 中位数为零、最大 0.46 个点；预测的「驻留压力把接收循环成批饿住」机制被 3.2 的存量/流量分析修正：没有换页、没有持续回收，饿住的通道不存在。P4（IO 中位数非递减且 I3 ≥ I0 + 1 个点）：未中——四档全零；IO 压力的指纹（PSI 约 22 倍）与时延（+14.3%）都成立，缺的只是把停顿传进接收循环的阻塞点，预测错在默认日志 flush 会同步等盘。P5（缺口档的 RcvbufErrors 归属 ≥ 50%）：无档位满足触发条件（要求中位数 > 0.5 个点），按预注册口径空置；唯一的单轮事件归属为 46/46 = 100%，如实附记、不算命中。P6（32 轮 D 全 ≤ 0.03）：命中且强于预测——逐轮恒为 0.0000，分解感知规则的免疫跨 CPU、内存、IO 三维复验成立。P7（无一轮 OLD 触发）：命中，L 最大 0.5303。P8（操纵检验）：IO 侧命中（I3/I0 约 22 倍，预测 ≥ 3 倍）；内存侧未中（PSI memory full 逐档下降，见 3.2 的背景归因与存量压力分析）——本轮内存臂的零结果按预注册规矩降级解读为「驻留存量形态下」的结论，不外推成内存维度全称。

## 4. 分析与取舍

三篇连起来，台架缺口这个对象的画像已经相当立体：它有明确的机制（接收方被饿住、内核缓冲溢出、逐包可对账）、有 CPU 维的门槛形态（超订才常态出现）、有注入基线被 CPU 拖漂的第二指纹（抖动份额），现在又有了两维干净的排除（内存存量、磁盘同步 IO）和一条压力形态的区分（存量对流量）。对实验台运维，我带走三条可直接用的：一，实验开始前记台架状态的清单从四个数扩成六个数——gap、抖动份额、RcvbufErrors 增量、loadavg 之外，再加 PSI memory/io 增量与轮内 MemAvailable 最低点，多维压力在场时先看哪一维的指纹在动；二，驻留型内存占用（缓存类、预加载类负载）不该与 CPU/IO 压力混列进「主机很忙」的笼统判断，它在本链路画像下连基线都不漂；三，告警侧读法不变且更硬：20 个点以上的第一跳缺口出现时，先按多维并发或突发形态去查，不要再怀疑单一维度的持续负载。

本轮没有顺手做的两件事，写明取舍：一是没有把内存 hog 放大到真正逼出换页的量级（数 GB）——护栏与共用主机的安全边界不允许在别人的生产线在跑时拿整机 OOM 风险做实验，这一格只能等独占窗口或换隔离手段（如 cgroup 限额下压单个组件）再测，不是本轮偷懒；二是没有做多维组合档（CPU 超订乘内存乘 IO）——那是旧案最像的形态，但组合档的档位空间与归因设计需要单独一轮预注册，不在本轮结论里预支。

## 5. 局限与未解问题

- 内存臂的上限形态受限：hog 封顶 1 GB 且全程零换页，「可用内存被压到换页区、链路组件匿名页被挤出」的形态没有测到；M2/M3 又被封顶合并成同量两批。本轮对内存维的结论严格限定在「1 GB 级驻留存量、无换页」范围内，换页形态仍是开口。
- PSI 与 pgsteal 等是整机口径，同宿主其他租户的活动（实验窗前段明显更重）会漂移背景，档位顺序又未随机（M 臂在前、I 臂在后），内存臂的背景衰减与档位效应无法完全分离——缺口为零这个主结论对背景方向不敏感（背景最重时缺口也是零），但 PSI 逐档下降这类细读数只许作归因参考，不许读成档位规律。
- IO 臂只测了同步写这一种磁盘压力：大块顺序读、随机读、页缓存抖动（大量文件遍历把缓存挤爆）都没有测；且链路本身无同步 IO 的事实决定了这一臂的上限，后半句对带 fsync 的被测系统不成立，不许搬运。
- 每档 4 轮，对「概率约 1/32 的偶发事件」（如那 46 个包）没有频率分辨力：它到底是内存档的产物还是纯背景偶发，本轮分不清，只报了签名与同轮协变量。
- 29.8% 旧案仍未结案，本轮只是再排除两维。剩余嫌疑按可能性排：多维同时在场（2026-10-28 那批的抖动份额指纹与 CPU 超订档重合，说明 CPU 当时在场，但量级对不上，缺的正是共因子）、突发尖峰形态（秒级满载脉冲对缓冲的冲击与持续档位不同）、同宿主 UDP 租户竞争。下一篇候选即组合因子实测：CPU 超订与内存驻留与同步写三维同开，再加一组突发脉冲臂，设计另行预注册。
- 全部证据仍是本机回环、Python 组件、默认接收缓冲一台主机的画像；上界数字（9.69 / 0.46 / 0 个点）都是这台机器的数，换主机须重测。
