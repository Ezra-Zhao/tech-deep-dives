# exporter 死在发送端身后，接收端 79 秒就响了：陈旧标记随 remote write 传播实测

作者：Guangyi Zhao

## 1. 问题与背景

上一篇（2026-11-09）测的那一格，死的是推送链：发送端 Prometheus 被杀，exporter 活得好好的，接收端的 present 序列活满 300 秒回望期才消失，absent 告警 firing 区间 366.8–371.1 秒，up 冻结在 1 上纹丝不动。那篇最后留了一个对称的格子没测：exporter 死在仍存活的发送端之后——发送端继续抓取、继续推送，只是抓到的东西变了。这一格里接收端的三条路径各是什么形态？

我跑活体前的推理是这样的：present 在发送端本地会被陈旧化停产，停产这件事是发送端本地 TSDB 的记账，不随样本流传到接收端；接收端只能等最后一个样本按 300 秒回望自然过期，所以 absent 还得等约 370 秒。倒是 up 应该很快：发送端活着，抓取失败会产生 up=0 样本、带当前时间戳持续推过来，接收端的 up==0 规则应当在一两分钟内响。两个信号一个慢一个快，差出一个回望期——这是我写进预注册的主预测。

先说结论：up 那一半对了，present 那一半错得干净。exporter 被杀后 5.1 秒，接收端的 present 即时查询已经变空；absent 与 up==0 两条告警在接收端同一个评估周期 pending（杀后 19.0 秒，activeAt 逐微秒相同），firing 下界同为 79.0 秒。错因是我漏了一个机制：陈旧标记本身就是一个样本。发送端的抓取层给停产序列追加的那个特殊 NaN，会像普通样本一样进 remote write 队列、被推到接收端、被接收端存下来并在查询时生效。上一篇立的判据——「序列的时间是谁记的账」——要修：真正决定盲窗档位的，是陈旧标记有没有被写下、并且有没有一条活着的通道把它送到查询的那台机器上。

实验设计在跑数前冻结落盘（data/2026-11-21-exporter-death-prereg.md）：六条预测里 P-E1、P-E4、P-E5、P-C 命中，P-E2（回望档主预测）与 P-E3（两信号差不小于 240 秒）未中，错因在第 3.2 节照实交代。

## 2. 方法

台架与 2026-11-09 篇同口径：Prometheus 3.15.0（官方 tar 包 111,651,578 字节，gzip 校验通过；本轮台架目录已被清理，系重新下载解压），抓取间隔 5 秒、超时 4 秒、规则组评估间隔 15 秒、回望期默认 300 秒，每条路径全新 TSDB、回环单机。exporter 为仓库真 exporter（src/prom_exporter.py）服务运行 20261019-171627 产物副本。

- E 主格：发送端 Prometheus 抓取 exporter、经 remote write 把全部序列推给接收端（接收端以 --web.enable-remote-write-receiver 启动、全新 TSDB、不抓取 exporter）。接收端与发送端本地各挂两条候选规则：absent(nal_exporter_results_present{group="scenario_summaries"})（与前作逐字同式）与 up{job="net-assurance-lab"} == 0（本篇新增候选），同为 for: 1 分钟。死法只杀 exporter：SIGTERM 之后直连其 /metrics 得到连接拒绝（确认已死），发送端进程全程存活、收尾时仍在运行。
- C 对照格：单个 Prometheus 直接抓取同一 exporter，同挂上述两条规则，死法同为 SIGTERM exporter——直接抓取档的第四次复测。

流程同构：等健康基线（E 格为接收端 present 为 1 且 up 为 1）并保持 30 秒，执行死法，轮询至 absent 告警 firing，再保持 20 秒收尾。轮询每 5 秒记录 present、absent()、up 的即时查询与全部告警快照，E 格同时记发送端本地同组查询。盲窗量法与前作一致：pending 取告警 API 的 activeAt，firing 给区间（activeAt + for:，首次轮询见到 firing）。规则文件经 promtool check 为 SUCCESS（2 条）。

照例披露冷启动竞态：E 格两台机器的 absent 告警在基线早期各有 3–4 个轮询处于 pending（第一次评估时序列未到），序列出现后即解除、从未 firing，杀前基线干净；下文 pending 均为杀后那次独立的 activeAt。C 格本轮无此现象。

## 3. 实测数据

### 3.1 接收端：两条告警同周期响起

杀 exporter 后跨过一个轮询（杀时刻正落在轮询点上，该轮询里 up 与 present 都还是 1），5.1 秒的轮询里接收端同时翻了三件事：up 首次为 0，present 即时查询首次变空，absent() 首次返回 1。up 此后再未回到 1，present 再未出现。

两条告警的账逐位重合：pending 同为杀后 19.0 秒，activeAt 同为同一时刻（逐微秒相同），firing 下界同为 79.0 秒，首次轮询见到 firing 同为 81.7 秒。也就是说在这一格里，absent 与 up==0 不是「一个快一个慢」，是同一条信号的两种写法——它们骑在同一批抓取周期上：抓取失败的那一轮，up=0 样本与 present 的陈旧标记同时产生、同时被推送，接收端的规则组在同一个评估周期里把两条都置为 pending。

up 的连续性单独记账（预注册 P-E5）：杀后全部 21 个轮询里接收端 up 都非空，序列从未断过——发送端一直在推，只是推的值从 1 变成了 0。这与 2026-11-09 杀发送端格里 up 冻结在 1、296 秒纹丝不动恰成镜像：那边是通道死了、值冻住；这边是通道活着、值立刻翻转。

### 3.2 present 为什么没有等回望期：我的主预测错在哪

先把证据摆齐。接收端最后一个 present 样本的时间戳与杀时刻之差为 -0.0 秒（样本就落在杀的那一瞬）；这个样本在杀后 5.1 秒的即时查询里已经不可见。回望期是 300 秒——一个年龄约 5 秒的样本在即时查询里消失，靠回望过期解释不通。Prometheus 里能让一个新鲜样本立刻不可见的机制只有一个：它后面跟了一个陈旧标记（值为特殊 NaN 的样本），查询在回望窗口里先撞到标记，序列就此判定为已终止。

我预注册时的推理漏的正是这一环。我以为「发送端本地陈旧化」是发送端 TSDB 内部的记账动作，停产不产生任何向下游流动的东西。实际上陈旧标记不是记账注记，它是一个被追加进序列的真实样本：抓取层发现序列从抓取结果里消失时，给它追加一个 NaN 标记样本，这个样本与其它样本走同一条路——进本地 TSDB，也进 remote write 队列。Remote-Write 规范对此有明文：发送端在可检测到序列停产时必须发送陈旧标记，标记以特殊 NaN 值（0x7ff0000000000002）表示、不得作他用（规范 2.0 版原文为 MUST，本轮发送端走 1.0 协议、行为与之一致，以本轮实测为准）。接收端把标记存进自己的 TSDB，查询语义与本地产生的标记无区别。

于是上一篇的四格表要改判据。旧判据问「序列的时间是谁记的账」；新判据问两步：停产时有没有人给这条序列写陈旧标记，写下的标记有没有活着的通道送到查询端。杀发送端格里标记根本没机会产生（进程已死），更谈不上送达，所以回望档；时间戳格里样本自带时间戳，Prometheus 按文档不对这类样本合成陈旧标记，所以回望档；本格里标记产生且通道活着，所以陈旧档。通道活着与否，成了同一条路径上 79 秒与 370 秒的分界。

### 3.3 发送端本地与直接抓取对照

发送端本地的账：present 与 up 的翻转同样在 5.1 秒轮询；两条告警 pending 同为杀后 4.0 秒，firing 下界同为 64.0 秒，首次见到 firing 为 66.4 秒。接收端比发送端本地整整晚 15.0 秒——pending 与 firing 下界两个差值逐位相同——正好一个规则组评估间隔：样本推送与队列刷送只花了亚秒级，多出来的时间是接收端规则组评估相位与发送端错开的那一拍。预注册 P-E4（本地 absent 落 60–90 秒、up 落 60–110 秒）命中。

C 对照格：present 与 up 同样在 5.1 秒轮询翻转，两条告警 pending 同为 1.1 秒、firing 下界同为 61.1 秒、首次见到 firing 65.8 秒。直接抓取档前三轮的 firing 下界是 73.9、74.2、70.1 秒，本轮 61.1 秒快了一截，仍在预注册 P-C 的 60–85 秒内；四轮的差都在评估相位里，档位不变。顺带记一笔：直接抓取格里 up==0 与 absent 也是同周期同 activeAt——这两条规则在抓取路径下从来就是同速的，本篇的新信息只在远端写入这一格。

## 4. 分析与取舍

对中心化接收部署，第一条结论是纠正上一篇可能留下的过头担心：上一篇说「配在接收端的 absent 规则，盲窗预算一律按回望档写」——那句话只对停推那一格成立。当发送端是活着的真 Prometheus、死的是它身后的目标时，陈旧标记会被推送过来，接收端的 absent 与 up==0 都是分钟级（本口径 79 秒），不必按六分钟做值班预期。真正要按回望档防的，是发送端本身死亡或失联那一格。

第二条是判据的修订版，值得替换掉旧框架：一条序列在查询端的盲窗档位，由「陈旧标记产生 × 送达」决定。产生端看生产方式——抓取与录制规则停产即写标记，自带时间戳的样本不写；送达端看通道——本地查询天然送达，remote write 在发送端存活时送达、发送端死亡时无从送达。估任何一条防盲规则之前，先把这两格填了，再谈数字。

第三条是关于两条规则的取舍。本格与直接抓取格里，absent 与 up==0 同周期响起，速度上没有区别，选哪条看语义：up==0 说的是「抓取在失败」，对 exporter 进程死、端口不通、端点挂起都成立；absent 说的是「这条序列没了」，对目标还活着但不再产出这条序列（产物被删、配置改了、序列改名）也成立——2026-10-27 篇里删产物那一格就是 up 恒 1、只有 absent 响。两条都配、语义分工，比纠结谁快更实际；本轮数据说明在发送端存活的前提下，两条在接收端都不慢。

第四条留给非 Prometheus 接收端：本轮接收端是 Prometheus 本人，它存下并尊重陈旧标记。一些第三方远端存储历史上对陈旧 NaN 的处理并不一致——有的忽略、有的当普通样本存——若接收端忽略标记，本格会塌回回望档。这句是推断（证据等级 C，本轮未实测第三方接收端），但它是部署前值得花十分钟验一件事：拿一个测试序列在发送端停产，看它在你的接收端几秒消失，答案直接决定你属于哪一档。

本轮没有改仓库里的任何规则文件，候选与实测材料留本项目 data/，处置与前作一致。

## 5. 局限与未解问题

- 只测了 Prometheus 到 Prometheus 的 remote write 1.0 协议。第三方接收端（各类远端存储与网关）对陈旧标记的尊重程度未逐个实测，第 4 节第四条只给了验证方法、没给答案；发送端为 agent 模式时走同一套抓取与推送代码，按机制应当同档，但未单独实测。
- 网络分区格未测：发送端活着但推不过去时，陈旧标记会积压在发送端队列里，接收端盲窗应当随分区时长延长、并在恢复推送后迅速补响——这是推断，未实测。
- exporter 的死法是 SIGTERM 干净退出。进程挂死（SIGSTOP 型、抓取每次走满 4 秒超时）时，发送端给 present 写标记的时刻可能被超时拖后数秒，up=0 的产生也要等当轮抓取判失败；2026-10-10 篇只测了直接抓取路径下的挂死，本格未测。
- 间歇成功型半死（抓取在超时上下浮动、时好时坏）仍未测：成功样本会反复刷新序列、陈旧标记与回望的账怎么算，是选题池里的下一格。
- 本轮 C 格 firing 下界 61.1 秒为四轮最快，与前三轮的差（最大约 13 秒）归因于评估相位，未做相位受控实验单独隔离；档位结论不受影响，绝对数引用时请连同前三轮一起看（61–76 秒一带）。
- 回环单机、单发送端单接收端、for: 1 分钟的口径边界与前作相同；79 秒这个绝对数绑定本口径，接收端与发送端的规则组相位差（本轮 15.0 秒）会随部署相位在 0–15 秒间浮动。
