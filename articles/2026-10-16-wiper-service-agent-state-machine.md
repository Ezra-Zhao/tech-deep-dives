# 一句「可以便宜点吗」，客服 Agent 就把单下了：Wiper-Service-Agent 对话状态机实测

作者：Guangyi Zhao
日期：2026-10-16
实测对象：Wiper-Service-Agent（自有开源项目，github.com/Ezra-Zhao/Wiper-Service-Agent），scaffold v0.2，提交 9675291，Python 3.12.3
实测环境：Linux x86_64 虚拟机，本机进程内直接调用 Agent 接口；未接 WhatsApp、未发任何真实消息、未使用任何真实客户数据；车型库、价格表、NLU 均为仓库自带的模拟实现，文中如实标注

## 一、问题与背景

给小店做 WhatsApp 客服 Agent，难点不在「接上大模型」，而在一通对话要走完一条有钱的路径：问车型、查尺寸、报价格、答问题、收下单意向。中间任何一步认错意思，代价都是真金白银——把砍价听成下单，店里多一张没人认的订单；把随口一句「我不知道」听成拒绝，一笔快成的生意当场关掉。

Wiper-Service-Agent 是我为雨刷销售场景写的客服 Agent。它没有把对话交给大模型自由发挥，而是用一个显式状态机管流程：GREETING → COLLECT_VEHICLE → QUOTE → DONE，四态。语言理解层默认是确定性的规则解析器（MockLLM，仓库里标明 SIMULATED），真实 LLM 解析器（RealLLMProvider）只负责把消息解析成意图和车型槽位，不碰价格、不碰尺寸、不决定成交——这是仓库 README 里写明的分工。项目状态也先说清楚：scaffold v0.2，车型库只有 8 条模拟适配记录（5 个品牌），价格是演示价目表，这套东西今天还不能拿去接真实订单。

本文要量的不是它能不能跑通演示脚本——自带演示和 56 个测试都是绿的（本轮实测 56 passed；README 里写的 44 个已经过期）。我要量的是状态机在演示之外的行为：27 组脚本对话、62 条消息，外加 13 条意图碰撞探针、8 条适配记录的全量报价验算、一组持久化往返和一组双客户隔离。结论提前放：主干流程比我预期的稳，报价数学一分不差，FAQ 在报价态里六个主题全部不跳流程；但意图层的子串匹配有三个会伤生意的误判，其中最重的一条是标题那句——在默认规则解析器（MockLLM）下，客人在报价态说「可以便宜点吗」，Agent 直接进 DONE，生成一张 confirmed 的订单意向，总价还是没打折的原价。先把范围说死：本文全部意图层结论都只针对这个默认解析器，真实 LLM 解析器下的表现是另一回事，第五节会再交代。

## 二、方法与架构

代码规模：核心包、工具层与 WhatsApp 边界合计 1,659 行（含 258 行的 webhook 服务端）。对话状态存在 Conversation 对象里：当前状态、车型三槽位（make / model / year）、适配结果、报价、一个 haggled 布尔标记（砍价额度是否已用）、结果（confirmed / declined）、语言与置信度、完整历史。

状态机的转移规则逐态交代，后文结论都从这里推：

GREETING：消息里带齐车型三槽位就直接查适配，查到进 QUOTE，查不到（年份超出目录区间等）退回 COLLECT_VEHICLE 并回复查不到；只带一部分就转 COLLECT_VEHICLE 追问缺项；什么都没带就回问候语，状态留在 GREETING。这一态不处理拒绝、不处理 FAQ、不处理问价——代码里就没有这些分支。

COLLECT_VEHICLE：只认两件事——拒绝（进 DONE 记 declined）和槽位补齐（查适配）。确认、问价、砍价、FAQ 在这一态全部不被处理，统一回复「还差什么」。

QUOTE：分支最全。砍价（只让一次，额外 5%）、FAQ（答完留在 QUOTE）、问价（重呈报价）、确认（DONE / confirmed）、拒绝（DONE / declined）、带车型信息（重新查适配，视为换车），其余一律重呈报价加一句催单。

DONE：handle_message 层拦截——DONE 之后再来任何消息，整段对话作废、新开一段，旧车型、旧报价、砍价标记全部清零（本轮实测往返核对过）。

意图解析（MockLLM.parse）的判定顺序是整篇文章的关键，原文顺序为：拒绝 > 确认 > 砍价 > FAQ > 问价 > 问候 > 提供车型 > 未知。关键词用子串包含匹配（`w in low`），只有 sí / да / نه 三个短词做了词边界匹配。确认词表里有「买」「好的」「可以」「ok」「yes」这类日常词，拒绝词表里有裸露的 "no"。车型提取只认目录内车型：遍历模拟目录的 (品牌, 型号) 对，两者都作为子串出现在消息里才算提取成功；年份用正则 (19|20)\d\d 抓第一个四位数。

工具层两个：wiper_db.lookup 按品牌、型号、年份区间查 8 条模拟适配；pricing.build_quote 按长度三档定价（≤20 寸 $12.99、21–24 寸 $14.99、≥25 寸 $16.99），整单小计打九折（代码注释写 bundle discount 10%），砍价后再多让 5%。

实验方法：仓库代码原样不改，进程内用不同「手机号」（实为任意字符串 ID）跑脚本对话，逐条记录消息、状态、报价总额、砍价标记、订单意向全文；报价验算对 8 条适配记录逐条独立复算期望值比对；意图碰撞先单独调 parse 看分类，再挑最重的三条放进真实对话看后果。实验脚本与原始 JSON 随本文归档，可复跑。

## 三、实测数据

### 3.1 主干流程：分步给车型、西语全程、报价数学全对

标准路径（你好 → Toyota Camry → 2018 → 怎么安装 → 好的，要了）五步状态依次为 GREETING → COLLECT_VEHICLE → QUOTE → QUOTE → DONE，最终订单意向 confirmed，车型、尺寸（26/20 寸）、总价 $26.98 齐全。一条消息给齐三槽位（Toyota Camry 2018）则一步直达 QUOTE。西语全程（Hola → Corolla 2021 → ¿Cuánto cuesta? → ¿Incluye instalación? → Vale, sí）五步全部用西语回复，语言在第一条就锁定 es，最终意向的 detected_language 为 es。

报价验算 8 条全对，逐条复算一致：以 Camry 为例，小计 $16.99 + $12.99 = $29.98，九折后 $26.98，砍价价 $25.48（即小计的 85%）；唯一带后雨刷的 RAV4 小计 $42.97，总价 $38.67，砍价价 $36.52。一个口径问题顺带记下：代码注释把九折写成「主副驾套装折扣」，但折扣基数是含后雨刷在内的整单小计——RAV4 的折扣额 $4.30 是按三支算的，不是按前两支算的。注释与实现不一致，金额方向对顾客有利，但账要记清。另一个舍入口径也写明，免得读者拿计算器对不上：Quote 的 discount 字段是单独四舍五入到分的（Camry 的九折折扣精确值 2.998，存 3.0），total 则用未舍入的折扣算完再四舍五入；本轮把 8 条记录、含砍价共 16 种组合逐一对账，discount 与 total 相加全部精确还原小计，没有出现一分钱的对不平。

### 3.2 砍价只让一次：第二次、第三次报价纹丝不动

Altima 2019 报价 $26.98；说「太贵了」，降到 $25.48，haggled 标记置真；再说「再便宜点」「还能便宜吗」，两次都回「已是最低价」，总额保持 $25.48。一次性的额度控制是硬编码布尔标记加重新算价，没有可绕的路径——这条设计在实测里站得住。

但它有个没被测试盖住的后续：砍完价再换车。先对 Altima 砍价到 $25.48，再报一台 Civic 2020，_do_lookup 用不带砍价的方式重算报价，新总价回到 $26.98，而 haggled 标记仍为真；此时再说「太贵了」，Agent 回「这已经是最低价了」——可这台车的价格根本没让过。顾客听到的是一句与事实不符的拒绝。根源是标记的粒度：haggled 记在对话上，不记在报价上；换车生成新报价时既不继承折扣、也不清标记，两个选择里它哪个都没做。

### 3.3 FAQ 只在 QUOTE 里活着

报价态里六个 FAQ 主题（安装、保修、寿命、付款、自取、邮寄）逐个实测，全部答完留在 QUOTE、报价不变，答后附一句下单引导。这是状态机文档里写明的设计——FAQ 不跳出销售流程，实测与设计一致。

报价之前问，问题会被吞掉。GREETING 态直接问「怎么安装」，回复只有问候语，问题不答、不记（notes 里没有这条 FAQ 记录）；COLLECT 态问同样的问题，回复是重复追问缺失年份，问题同样消失，顾客补完年份进 QUOTE 后必须再问一遍。问价和砍价在 COLLECT 态是同样的命运：「多少钱」「太贵了」都只换来一句追问。也就是说这台状态机在成交路径之外没有「先记下来、到站再答」的暂存区，路径外的输入不是被拒绝，而是被无声地丢弃，顾客从回复里看不出来自己的问题没被听见——他只会觉得客服答非所问。

拒绝也分态：COLLECT 和 QUOTE 里的「算了」都正确进 DONE 记 declined；但 GREETING 里的「不要了」不被处理，回复是热情的问候语。一个开口就说不要的人被迎进门，场面有点尴尬，性质是小事，记在这里是因为它说明 GREETING 分支的意图覆盖是零，不只是缺 FAQ。

### 3.4 意图碰撞：13 条探针，子串匹配的三类误伤

把日常说法喂给 parse，13 条里分类与说话人本意明显不符的有 7 条，集中在三类：

第一类，确认词太宽，抢走其他意图。「可以便宜点吗」判 CONFIRM（「可以」在确认词表里，判定顺序又在砍价之前）；「好的，多少钱」判 CONFIRM；「我想买，先问问保修」判 CONFIRM（「买」命中确认，FAQ 话题其实被正确识别成 warranty，却没机会用）；英文 "yes but too expensive" 同样判 CONFIRM。

第二类，拒绝词是裸子串。拒绝词表里的 "no" 是子串匹配，于是 "I don't know" 和 "another question" 都判 DECLINE——know 和 another 里都含 "no"。仓库里其实有词边界匹配的机制（CONFIRM_TOKENS / DECLINE_TOKENS 就是为短词准备的），但 "no" 没进那个集合，进了子串集合。

第三类，拒绝压过砍价。「不要太贵了」「不买了太贵」判 DECLINE。这类算不算误判可以商量——顾客也许真在拒绝——但前者更像砍价的口语开场，状态机没有任何澄清动作，判死刑还是放行砍价，二选一里它选了死刑。

挑最重的三条放进真实对话看后果：

- 报价态说「可以便宜点吗」→ 直接 DONE，订单意向 confirmed，总价 $26.98 原价。顾客问折扣，系统记成交。
- 报价态说「我想买，先问问保修」→ 直接 DONE，confirmed，保修问题没有回答。顾客的购买意向是真的，但他的问题被跳过、流程被提前关闭，人工跟进时手里只有一张「已确认」和一段没答完的对话。
- 报价态说 "I don't know" → 直接 DONE，declined，理由是 declined at quote。顾客只是没想好，系统记成拒绝；在 COLLECT 态说同一句，结果一样。

对照组说明这不是词表全坏：「能便宜点吗」（没有「可以」二字）正确判 HAGGLE，「先看看保修再说」正确判 FAQ，「好的」「OK」在报价态判 CONFIRM 是对的。坏的是组合句——真实顾客恰恰很少只说一个词。

### 3.5 换车：目录外车型被静默拼回旧车

QUOTE 态里说「Honda Civic 2020」，正确换车重报（新旧总价恰好同为 $26.98，尺寸从 26/20 变 26/18 可辨）。但说「BMW X5 2020」，回复是「查到了！Toyota Camry 2020」——BMW 和 X5 不在模拟目录里，车型提取整个失败，只抓到年份 2020；槽位合并把新年份并进旧车型，再查适配，Camry 2020 在目录区间内，于是生成一份 Camry 的新报价。顾客以为自己在问宝马，客服言之凿凿报了凯美瑞的价格，全程没有任何一句「这个车型我查不到」。

目录外车型在一通对话开头出现时行为还算诚实：首条就说「BMW X5 2020」，提取失败，Agent 追问车型——虽然它追问的方式（「还差车型」）会让顾客困惑，因为顾客明明说了车型。这里要把两种失败分清：这是提取失败（品牌型号根本没被解析出来，槽位不齐，只能追问）；另一种是提取成功但查适配失败，如首条就说「Toyota Camry 2005」，三槽位齐全、查不到，回复的是明确的「查不到」并退回 COLLECT（本轮实测过）。但在 QUOTE 态，提取失败被槽位合并掩盖，变成了静默替换。差别只在旧槽位是否已有值。

只改年份同理：「2025」被并进 Camry 去查，超出目录区间（2018–2024），这回查不到，状态退回 COLLECT 并请顾客核对——处理本身没错，错在退回时旧报价没有清：对话对象里仍挂着 $26.98 的旧报价。紧接着顾客说「算了」，生成的 declined 订单意向里附的正是这份旧报价，车型字段写的是 Camry 2025——一台查不到适配的车，配着一份 2018 款的报价，进了订单意向记录。人工事后看这张单，会以为顾客对着一份真实报价拒绝了。

### 3.6 持久化与隔离：两条及格线

把对话进行到报价并砍价后，换一个全新的 Agent 实例从同一个 JSON 文件存储里恢复：状态 QUOTE、车型、砍价后总价 $25.48、haggled 标记、历史 4 条全部对得上，恢复后继续问保修仍留在 QUOTE。对话状态的 to_dict / from_dict 往返是完整的。两个顾客交错对话（一个砍价、一个补年份），车型、报价、标记互不串扰，按手机号分键的隔离成立。

报价态收到无意义输入（asdf qwer），回复是重呈报价加催单，状态不动——不算聪明，但不崩、不误关单，在这一节的对照里反而是意图层最稳妥的兜底：只有 UNKNOWN 才有这种待遇，问题全出在「似是而非的命中」上。

## 四、分析与取舍

### 4.1 这套架构真正做对的：成交决定权不在解析层

把实测结果放回架构上看，最值得保留的是分工：状态机管流程，工具管数字，解析层（无论规则还是真实 LLM）只产出意图和槽位。报价数学全量验算无误、砍价额度一次封顶、FAQ 不跳流程、持久化无损——这些都来自决定权被关在确定性代码里。接入 RealLLMProvider 后解析质量会变好，但它输出的 intent 仍然要过同一张状态转移表，价格和成交结论不由它生成。这个边界是这类小店 Agent 该守的：语言可以概率，账必须确定。

### 4.2 缺陷不在状态机，在状态机的「入口契约」

三类实测问题——组合句误判、目录外车型静默合并、换车后标记与报价脱节——没有一条是转移表画错了。转移表的问题是它默认入口送进来的东西是可信的：parse 给什么意图就执行什么意图，槽位合并给什么车型就查什么车型。实测里伤生意的动作（误关单、报错车、假意向）全部发生在「输入被过度信任」的位置：

- CONFIRM / DECLINE 是不可逆动作（进 DONE、生成意向），却由最弱的证据触发：一个子串。不可逆动作的触发证据应该比可逆动作（重呈报价、答 FAQ）更强，这是顺序反了——现在的优先级恰恰是不可逆意图排在最前面先判。
- 槽位合并是逐字段覆盖，它分不清「顾客补充了年份」和「顾客换了台车但新车没提取出来」。后者应该走查不到的澄清路径，而不是拿旧值补齐新句子的残缺。
- haggled 与 quote 的生命周期不一致：报价可以换，标记不换；查适配失败退回时报价不清。状态字段各自为政，缺一条「换报价即作废旧报价全部派生状态」的规则。

### 4.3 修的顺序：先给不可逆动作加门槛，再谈换更好的 NLU

按性价比排。第一，把 "no" 这类短词从子串集合挪进已有的词边界集合，顺手把确认词表里的「买」「可以」收紧为组合条件（如「可以」只在无砍价/问价词共现时算确认）——纯词表与判定顺序的活，一下午量级，直接拆掉 3.4 节里的大部分误伤。第二，意图优先级改为可逆在前：FAQ、问价、砍价先于确认/拒绝判定，确认只在整句没有其他诉求时成立；组合句「想买但先问保修」的正确处理是先答 FAQ、留在 QUOTE，而不是抢跑关单。第三，CONFIRM 增加一次显式复核：进 DONE 前把车型和总价回读一句「确认下单吗」，顾客回「是」才落意向——状态机多一个 CONFIRMING 态就能装下它，这也是 WhatsApp 对话里真人客服的自然做法。第四，槽位合并加一条规则：消息里出现年份或疑似车型文本但品牌型号提取为空、且与当前车型不一致时，不合并、走澄清；查适配失败退回 COLLECT 时同步清掉 quote 与 haggled。第五，才是把 MockLLM 换成 RealLLMProvider 并用本轮 13 条探针加真实对话语料做回归集——NLU 换脑子解决组合句的一部分，但解决不了槽位合并和标记生命周期，那是状态机自己的账。

这个顺序背后的判断是：演示阶段最容易被忽略的，不是答得准不准，而是关单关得对不对。答错一句 FAQ 顾客会再问，误记一张 confirmed 意向，店主会照着它去备货、去联系、去扑空。

## 五、局限与未解问题

本文的局限写明。第一，全部实验跑在 MockLLM 上，意图碰撞的形态是规则解析器特有的；RealLLMProvider 的组合句理解大概率更好，但本轮没有在真实端点上复测这 13 条探针，换上之后误判率会降到多少，未测。第二，车型目录只有 8 条模拟记录、价格为演示价，目录外车型静默合并的严重程度在真实目录（成百上千条）下会变：提取失败的概率下降，但一旦失败，后果相同；本文的结论是机制性的，不依赖目录大小。第三，对话脚本由作者按状态转移表反着写，覆盖的是「想得到的路径」；真实顾客的跳跃说法（语音转文字的错字、中英混杂、一句里报两台车）只测了零星几条（中英混杂未系统测）。第四，WhatsApp 边界层（webhook 验签、Cloud API 回发、用量计数）不在本文范围，本轮只测进程内 Agent 接口；webhook 服务端仓库自带测试覆盖，本轮 56 个测试全过，但没有做端到端消息实测。第五，西语之外的俄语、波斯语只验了问候与语言检测（沿用仓库测试口径），全流程未逐语种复测，模板翻译质量未经母语者校对，仓库 README 亦如实标注。

未解问题留三个：CONFIRM 复核态加上之后，完成率会掉多少，需要真实流量才知道，演示环境测不出；槽位合并的澄清规则做到什么粒度（只拦年份冲突，还是拦一切「有车型文本但提取为空」），要拿真实对话日志标定；多台车同单（顾客给自己和家人各买一副）在当前单 Conversation 单车型的数据模型里装不下，是先记 notes 凑合还是扩成多意向，未定。
