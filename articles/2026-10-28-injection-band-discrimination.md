# 再丢四成七才报警：注入带 0.75 上界的判别力实测

作者：Guangyi Zhao

## 1. 问题与背景

net-assurance-lab 的十条告警规则里，有一条是给故障场景本身看的。fault_sustained 场景按设计就该丢一半以上的包——代理在双向各丢 20% 的随机包，再叠一个每 2.5 秒关 0.6 秒的链路抖动窗——所以基线那套「丢包超过 5%」的回归告警对它毫无意义。它自己的合理性带告警 NalFaultLossAboveInjectionBand 换了个问法：端到端丢包率超过 0.75，就说明有些包不是注入参数丢的，是别的东西在丢，结论不能再记在注入参数账上。规则注释里把注入能解释的范围写成「roughly 50–65%」，0.75 是站在这条带上沿之外留出的余量。

我在 2026-10-24 的告警链路审计里验过这条规则的阈值边界：夹具推过 exporter 的真实代码路径，丢包恰为 0.75 时不触发、0.80 时触发，大于号语义无误。但边界对不等于判别力对。那篇的未解问题写得很明确：没有构造过「注入之外另有丢包」的场景，这条上界在检出侧（真有带外丢包时响不响、要丢多少才响）和误报侧（只有注入时离 0.75 有多远、运行间抖动会不会把它顶上去）都没有实测。这篇来还这笔账。

先把注入带自己算清楚，因为后面的判别力全是相对它说的。代理的决策顺序是先抖动后随机（src/fault_proxy.py 的 decide()：先查 flap_is_down，命中即丢；未命中才掷随机丢弃）。抖动占空比 0.6/2.5 = 24%，一腿的存活率是 0.76 × 0.80 = 0.608，单腿丢包 39.2%。端到端要过两腿，账怎么算取决于两腿的抖动相关性：若两腿抖动相互独立，端到端丢包 1 − 0.608² = 63.0%；若完全相关（两腿同处一个抖动窗状态），是 1 − 0.76 × 0.80² = 51.4%。规则注释的 50–65% 正是这个相关性不确定区间，不是随手写的约数。真实链路里两腿处在区间的哪一端，第 3.1 节用逐方向分解账给出答案——比预想的还要靠边。

本篇的问题只有一个，拆成两侧：注入参数一个字不改，在服务器侧再加一级独立的额外丢弃（概率 q，只丢客户端到服务器方向、且只丢已经活过注入的包），q 要多大这条规则才响？另一侧，q = 0 时它离误响有多远？先说结论：隔离掉台架噪声后，这条线是一个台阶而不是一个斜坡——q 到 0.40 时 4 次重复无一次触发（最高 0.7324），q 到 0.50 时 4 次全部触发（最低 0.7678），模型给出的临界点 q* ≈ 0.47。也就是说，活过注入的包要在服务器侧再被吞掉近一半，折合成端到端再加约 22 个点的丢包，这条告警才看得见。而误报侧它稳得近乎浪费：只有注入时，模型 2,000 次试验无一次越线，活体最高 0.5381，离线还差 21 个点。中间这 22 个点，就是这条规则的盲区宽度。

## 2. 方法

实验设计在第一轮实跑之前冻死，写在实测脚本（data/2026-10-28-injection-band-bench.py）的头部，连同网格与种子规则一起落盘：

- 活体层：全用实验台的真实组件在本机回环上跑。流量与 fault_sustained 完全一致——traffic_gen sustained 模式、2000 pps、5 秒共 10,000 个包、包长 256 字节、收尾宽限 1.5 秒。链路是 traffic_gen → fault_proxy（loss 0.20、delay 40 ms、jitter 30 ms、flap 0.6/2.5、seed 1234，全部与 run_experiment.py 的故障场景逐字一致）→ 额外丢弃垫片 → echo_server。垫片是我为本实验写的一个 UDP 中继（data/2026-10-28-injection-band-shim.py）：只在客户端到服务器方向上，以概率 q 丢弃到达它的包并计数，回程原样转发。它丢的每一个包都已经活过了注入、且让服务器根本没机会回显——这是「服务器侧额外丢弃」最字面的实现。垫片实测丢弃率与名义 q 的偏差在各轮都在 ±0.011 以内（例如 q = 0.60 时实丢 0.589–0.597，q = 0.10 时 0.093–0.100），垫片本身先对得上账。
- q 网格：0、0.10、0.20、0.30、0.40、0.50、0.60，每档 4 次重复，共 28 轮。额外丢弃的种子逐轮不同，代理种子固定为实验台默认值 1234；每轮端口轮换。发生器汇总、代理逐包 JSONL、垫片计数、服务器计数四份日志逐轮全留，总丢包必须能逐级分解到每一级丢了多少，对不上不许进结论。
- 告警判定走真链路：每轮产物组装成一个最小 results 目录，推过 exporter 真实的 collect() 代码路径，把 nal_loss_ratio{scenario="fault_sustained"} 回读出来，再在它身上求值规则表达式（> 0.75）。28 轮里 exporter 回读值与发生器汇总值逐轮完全一致，无一例外。
- 模型层：一个 NumPy 复刻的代理决策逻辑（抖动先行、每腿伯努利随机丢弃、注入延迟把回程腿的抖动相位推后、垫片只作用于去程），每档 2,000 次试验，抖动相位在 [0, 2.5) 秒均匀抽。它是模型不是实测，用途是把检出概率曲线描细；它的 q = 0 分布必须先对上活体与存档运行才有资格说话。复刻与活体的一个已知差别：活体代理双向共用一个随机数流，复刻用独立流——每一次掷骰都是伯努利 0.20，丢包律不变，差别只在抽样相关性，而那里没有可保留的相关性结构。
- 解析层：两腿相关性两极端的端到端带（51.4% 与 63.0%，见第 1 节），以及给定注入侧丢包 L 时解总丢包 = 0.75 得到的临界 q = 1 − 0.25/(1 − L)。这一层是算术，不冒充实测，只给活体与模型的数做参照。

还有一个方法上的交代：实验中途分解账暴露出一个原设计没预料的混杂因素（发生器到代理之间的台架丢包，见 3.2），所以结果按两条曲线报告——「部署口径」是 exporter 实际看到的总丢包，规则真正在它身上触发；「隔离口径」是只算进入代理之后的包（以代理 in_client 为分母）的丢包，它把台架噪声剔掉、单独量垫片这一级的判别力。两条都报，不许只挑好看的。

## 3. 实测数据

### 3.1 q = 0 的锚点：注入带落在相关性区间的低端

没有额外丢弃时，注入单独造成的丢包是：

| 来源 | 总丢包（部署口径） | 隔离口径丢包 |
|---|---|---|
| 存档 R1（20261019-154535） | 0.5275 | 0.5275（该轮代理前丢包为 0） |
| 存档 R0（20261019-171627） | 0.5897 | 0.5596 |
| 本轮活体 q = 0，四次 | 0.5252 / 0.5295 / 0.5334 / 0.5381，均值 0.5315 | 0.5237 / 0.5295 / 0.5273 / 0.5316，均值 0.5280 |
| 模型 q = 0，2,000 次 | — | 均值 0.5277，标准差 0.0041，区间 [0.5143, 0.5424] |

三方在 0.527–0.528 上对齐：安静的一轮存档运行、本轮活体的隔离口径、模型均值，两两相差不超过 0.001。R0 是唯一的离群者，连隔离口径都有 0.5596——它是带抓包的完整运行，主机最忙，其成因在 3.2 一起说。

为什么落在 51.4%–63.0% 区间的低端、紧贴完全相关界？逐方向分解账（本轮 q = 0 四次合并）：去程抖动丢弃占代理入包的 23.97%，几乎就是占空比 24% 本人；回程抖动丢弃只占服务器回包入数的 3.30%。机制不难懂：回声只由去程在开启窗内被放行的包产生，回到代理时已是 40–70 ms 注入延迟之后；一个回声要落在关闭窗里，它对应的去程放行必须发生在关闭窗开启前的一个延迟（至多 70 ms）以内——按延迟中值约 55 ms 估算，期望份额约 55/2500 ≈ 2.2%，实测 3.30%，同一量级。抖动实际上只作用了一次，不是两次。用实测份额拼回去：回程存活率 1 − 0.0330 − 0.1943 = 0.7727（随机丢弃份额 0.1943 与 0.20 × (1 − 0.033) = 0.1934 对得上，先抖动后随机的决策顺序在账上成立），端到端预测丢包 1 − 0.608 × 0.7727 = 0.5302，与隔离口径实测均值 0.5280 差 0.0022。存档 R1 的份额结构相同（去程抖动 24.09%、回程 3.05%），所以它的 0.5275 与今天的数重合不是巧合。

### 3.2 混杂因素：台架自己也在丢包，而且丢得不少

28 轮的分解账里有一级原设计没有安排的丢包：发生器发出 10,000 个包，进入代理的 in_client 并不总是 10,000。q = 0 的四轮里缺口是 0–139 个（至多 1.4%），但随着轮次推进，缺口最大涨到 2,983 个（q = 0.20 第二轮，占发出量的 29.8%）；其余各级之间的账全部严丝合缝——代理放行数与垫片入数之间只有一轮差 145 个，其余 27 轮为 0；垫片放行数与服务器收数、服务器回数与垫片回程数、代理回程放行数与发生器收数，逐轮全等。丢包就丢在发生器到代理这一跳的 UDP 接收路径上，本质是这台主机的调度与接收缓冲噪声，与 2026-10-24 那篇里基线 p99 两轮横跨门槛两侧是同一类台架抖动，只是这次它大到能左右结论。

处理方式不是把这些轮次删掉，而是两条曲线分开报（见第 2 节）。并且要点名：这个混杂因素恰好长得和被测信号一模一样——对 exporter 来说，台架丢的包与服务器侧丢的包没有任何区别，都只是「没回来的包」。它对检出侧与误报侧的影响在下面两节分别算。

### 3.3 检出侧：临界 q 在 0.47 附近，曲线是台阶

隔离口径下，各档丢包与触发（4 次重复）：

| q | 隔离丢包均值 | 隔离丢包范围 | 触发 |
|---|---|---|---|
| 0 | 0.5280 | 0.5237–0.5316 | 0/4 |
| 0.10 | 0.6043 | 0.5881–0.6255 | 0/4 |
| 0.20 | 0.6549 | 0.6382–0.6658 | 0/4 |
| 0.30 | 0.6939 | 0.6858–0.7051 | 0/4 |
| 0.40 | 0.7299 | 0.7248–0.7324 | 0/4 |
| 0.50 | 0.7747 | 0.7678–0.7812 | 4/4 |
| 0.60 | 0.8123 | 0.8050–0.8163 | 4/4 |

模型给出的同一条曲线（每档 2,000 次）：均值 0.5277 / 0.5751 / 0.6223 / 0.6694 / 0.7166 / 0.7640 / 0.8111，触发概率在 q = 0.40 时为 0（2,000 次最高 0.7305）、q = 0.50 时为 1（2,000 次最低 0.7519）。活体隔离均值在中段比模型高 1–3 个点（q = 0.10 时 +2.9 点、q = 0.20 时 +3.3 点、q = 0.50 时 +1.1 点、高档收敛），成因还是台架：负载重的轮次里代理决策时刻滞后于到达时刻，去程抖动份额全网格合并涨到 26.96%（q = 0 安静轮次是 23.97%），注入侧基线被整体抬高。但活体与模型在结论上一致：触发与不触发之间没有过渡带，q = 0.40 的活体最高值 0.7324 与 q = 0.50 的最低值 0.7678 之间隔着 3.5 个点的空档。临界点两法互证——解析式以 L = 0.5277 解得 q* = 0.4707，模型均值在 q = 0.40 与 0.50 之间线性插值到 0.75 得 0.4705。模型的标准差只有 0.0041，所以这个台阶的宽度（触发概率从近 0 到近 1）只有约 ±0.01 的 q——它不是灵敏度渐变的检测器，是一个在 0.47 处翻转的开关。

把 q* 翻译成运维语言：活过注入的包约占发出量的六成（去程存活 0.608），服务器侧要丢掉其中 47%，相当于发出量约 28.6% 的包死在服务器侧、端到端丢包在注入基线 52.8% 之上再叠 22.2 个点，这条告警才第一次有机会响。q 在 0.40 以下的服务器侧故障——已经丢掉活包的四成——在这条规则眼里与完全健康不可区分。

### 3.4 部署口径：提前触发的两次，响的是台架

规则实际消费的是总丢包。部署口径的触发明显提前：q = 0.20 与 q = 0.30 各触发 1/4，q = 0.40 触发 3/4，q = 0.50 起全触发。但逐轮对分解账，两次提前触发的轮次正是台架缺口最大的两轮：q = 0.20 第二轮总丢包 0.7655，隔离口径只有 0.6658，代理前缺口 29.8%；q = 0.30 第四轮总丢包 0.7693，隔离口径 0.7051，缺口 21.8%。q = 0.40 第三轮以 0.7502 触发——只越线 0.0002，其隔离口径是 0.7314，是台架缺口 7.0% 把它推过的线。

这不是说规则响错了。它的注释本来就写着「超过 75% 说明有超出注入的东西在丢包」——台架接收路径确实是「超出注入的东西」，从告警语义上它没有误报。但归因到此为止：exporter 的总丢包对丢包发生在哪一级完全不可见，同一个 0.7655 可以是服务器在丢、台架在丢、或两者各丢一半。想用这条规则定位「服务器侧另有丢包」，先得把分解账摆出来，否则响了也只是知道出事了，不知道在哪。

### 3.5 误报侧：21 个点的余量，和它的成立条件

q = 0 时规则离误响的距离：活体总丢包最高 0.5381（余量 21.2 点），模型 2,000 次最高 0.5424（余量 20.8 点），安静存档轮 0.5275。用第 3.3 节的同一条代数反过来算：隔离丢包停在 0.5277 时，光靠代理前台架丢包把总丢包顶过 0.75，需要台架先丢掉 47.1% 的发出包——本轮观测到的最大台架缺口是 29.8%，2026-10-19 的完整运行 R0 是 6.84%（684 个），都还差得远。注入本身的随机涨落更不用担心：10,000 个包、模型标准差 0.0041，0.75 在均值上方约 54 个标准差处。

但这个结论有一个必须写明的成立条件：它依赖台架丢包不失控。这台主机的台架缺口在本轮 28 次运行里从 0.3% 到 29.8% 都出现过，分布随主机负载漂移、没有先验上界；47.1% 不是物理不可能，只是本轮没见到。规则注释把 0.75 写成经验上界，我的实测支持它在当前台架负载画像下的保守性，但不支持把它当作与环境无关的常数——换一台更忙的主机，这条线的误报余量要重新量。

## 4. 分析与取舍

把三条线并排，这条规则的性格就清楚了：它是一条防误报优先的合理性带。好处是真的：在注入参数不变的前提下，它几乎不可能被注入自身的涨落顶响，本轮与模型合计 2,000 多次 q = 0 观察零越线，可以放心地把它的触发读作「确有带外丢包」。代价也是真的：盲区宽达 q ≈ 0.47、end-to-end 约 22 个点——服务器侧从轻微到相当严重的丢包（活包丢一成、两成、三成、四成）全部落在这个盲区里，规则一言不发。对 fault_sustained 这种「丢一半是设计」的场景，这个取舍不荒谬：带设窄了，台架噪声就能把它顶响（见下段），归因价值反而归零；带设在这个位置，响了就是实锤，只是响得晚。

顺带用同一批已记录数值回答一个自然的追问：把阈值降到 0.70 或 0.65 会怎样（这是对已测数值的换线重评，不是新一轮实测）。隔离口径下，0.70 时 q = 0.30 开始触发（1/4）、q = 0.40 全触发，临界 q* 降到约 0.36；0.65 时 q = 0.20 已触发 3/4，q* 约 0.26。检出灵敏度确实换回来了。但误报侧的账要一起算：阈值 0.65 时，光靠台架丢包顶线所需的缺口降到 25.9%——低于本轮已实测到的 29.8%，也就是说在 0.65 口径下，一轮注入完全正常、只是主机忙的运行，仅凭台架丢包就可能越线（本轮 q = 0 的四次总丢包都停在 0.5381 以下，是因为那四轮恰好跑在主机安静时，这一点不能当作 0.65 安全的证据）。0.70 时所需缺口 36.5%，高于本轮最大值，余量已薄但还没被击穿。所以我的判断是（工程判断，证据等级 B）：单调阈值这条路已经到头了——0.75 的问题不在数字选得不对，在于总丢包这个观测量本身把三级丢包搅在一起；exporter 本来就发布代理逐级计数（nal_fault_proxy_packets_total 等），把「由代理计数推算的期望端到端丢包」与实测端到端丢包做差、差值越线才报警，才可能同时保住灵敏度和归因。这一改法本轮没有实现与实测，只作为方向记下，不冒充结论。

最后一个读法上的提醒，与 2026-10-24 那篇的结论接得上：这条规则 for: 是 1m，而 exporter 发布的是已完成运行的快照，for: 量的是「这份坏数据被连续抓取了多久」而非网络状态的持续时长。本篇的「触发」指表达式在单轮数据上成立，与 for: 的时间条件无关；把判别力结论搬到流式 exporter 场景时，检出延迟还要另加 for: 与评估间隔，这笔账不在本篇范围内。

## 5. 局限与未解问题

- 全部活体证据来自本机回环与这一台主机的负载画像：台架缺口的分布（0–29.8%）是这台机器、这段时间窗的实测，不是任何其他环境的常数；q* ≈ 0.47 中注入基线 0.5277 是注入参数的函数，参数一变就要重算、重测。
- 活体每档只有 4 次重复，触发率的分辨粒度是 25 个点；曲线形状（台阶位置与宽度）靠模型 2,000 次/档补足，模型与活体在中段有 1–3 个点的系统差（成因已在 3.3 归因于台架抬高了注入基线），所以 q* 的可信区间应读作约 0.45–0.48，而不是 0.4707 的单点值。
- 模型对抖动相位取均匀抽样，活体的相位由启动时序决定、近乎固定；相位敏感性只经由模型给出（其 q = 0 的 5–95 分位宽仅 0.0136，说明相位不是大头），没有做专门的相位扫描活体实验。
- 垫片只丢去程请求，模拟的是「服务器侧在收包环节丢弃」；若真实故障丢的是服务器的回程答复，端到端代数相同（存活率连乘），但分解账的形态不同，本篇没有实跑回程丢弃的对照轮。
- R0 的隔离口径 0.5596 至今没有完全解释：已知的抬高因素（抓包并发、台架缺口 684）能解释方向，量上是否完全对得平没有单独复验；它不影响本篇主结论（其余三方锚点互相咬合），但作为存量疑点如实留在这里。
- 未解问题：第 4 节提出的分解感知告警（期望丢包与实测丢包作差）没有实现；它对台架缺口的免疫力是推理而非实测。另，本轮台架缺口随轮次漂移的规律（与主机负载的定量关系）只做了观察，没有受控实验。
