# 源头活着，推送停了，盲窗还是六分钟：远端写入路径的 absent 盲窗实测

作者：Guangyi Zhao

## 1. 问题与背景

这个系列量 absent() 盲窗量到第四条路径了。前三条的账是这样的：普通抓取路径下，源头一死，抓取层立刻给序列打陈旧标记，盲窗约 75 秒；录制规则复刻的序列与原件同周期死亡，还是约 75 秒；样本自带时间戳的路径没人打陈旧标记，序列活满 5 分钟回望期，盲窗回到约 370 秒（2026-10-27、2026-10-31 两篇同口径实测）。2026-10-31 那篇在最后留了一条没测的边界：远端写入（remote write）推入的序列，接收端既不抓取它、也没有本地规则评估替它记账——它停推之后，盲窗落在陈旧档还是回望档？

这条边界不是书斋问题。中心化接收是现在很常见的部署形态：边缘侧一个 Prometheus（或 agent 模式）抓取本地目标，把样本 remote write 推给中心接收端，告警配在接收端。推送链断掉的方式有很多种——发送端进程挂了、升级重启、网络分区——而被推的源头本身可能活得好好的。这一格里 absent() 多久才响，决定了「推送断了」这件事在监控上要盲多久。

先说结论：回望档。发送端被杀后，exporter 全程存活（杀后直连验证仍返回 present 为 1），接收端的 present 序列又活了 301.0 秒才消失，absent 告警 firing 区间 366.8–371.1 秒，与自带时间戳路径的 369.4–373.8 秒几乎重合；同轮直接抓取对照的 firing 下界是 70.1 秒，两档差 296.7 秒，就是一个回望期减去陈旧化的零头。还有一格比主结论更值得记住：接收端连 up 都是被推出来的样本——发送端死后它冻结在 1，整整 296 秒纹丝不动，最后与 present 在同一个轮询里一起消失。这条路径上不存在任何快速死亡信号，up 型规则写了也是摆设。

实验设计在跑数前冻结落盘（data/2026-11-09-remotewrite-prereg.md）：四条预测里主预测与两条全中，一条字面未中——我预注册说接收端「查不到 up 序列」，实测 up 在场，只是冻住了。错因在第 3.3 节照实交代。

## 2. 方法

两条路径同口径：Prometheus 3.15.0（官方 tar 包 111,651,578 字节，gzip 校验通过；与前三篇同版可比），抓取间隔 5 秒、超时 4 秒、规则组评估间隔 15 秒、absent 告警同用 for: 1 分钟、回望期默认 300 秒，每条路径全新 TSDB、回环单机。

- C 普通抓取（对照复测）：单个 Prometheus 直接抓取仓库真 exporter（src/prom_exporter.py）服务运行 20261019-171627 产物副本，告警 absent(nal_exporter_results_present{group="scenario_summaries"})，与前作逐字同式。死法是 SIGTERM 杀 exporter，与前作同。
- W 远端写入：发送端 Prometheus 以同口径抓取同一 exporter，经 remote_write 把全部序列推给接收端 Prometheus（接收端以 --web.enable-remote-write-receiver 启动、全新 TSDB、完全不抓取该 exporter，告警同 C 式、作用于被推入的序列）。死法只杀发送端：SIGTERM 后发送端 0.1 秒内退出，exporter 不动，杀后立即绕开两台 Prometheus 直连 exporter 的 /metrics 验证其健康——这样 W 测的纯粹是「停推」，不掺源头死亡。

流程同构：等健康基线（C 为 present 为 1；W 为接收端 present 为 1）并保持 30 秒，执行死法，轮询至主告警 firing，再保持 20 秒收尾。轮询每 5 秒记录 present、absent()、up{job="net-assurance-lab"} 的即时查询与全部告警快照。盲窗量法与前作一致：pending 取告警 API 的 activeAt，firing 给区间（activeAt + for:，首次轮询见到 firing）。规则文件经 promtool check 为 SUCCESS（1 条）。

两条路径各有一处与 2026-10-31 篇 T 路径相同的冷启动竞态，照实披露：Prometheus 起来后第一次规则评估时序列还没到，absent 告警在基线早期 4 个轮询里 pending，序列出现后随即解除、从未 firing，杀前基线干净；下文 pending 均为杀后那次独立的 activeAt。

## 3. 实测数据

### 3.1 C 路径：70.1 秒，第三次复测

杀 exporter 后第一个 5 秒轮询里 present 已空、absent() 已返回 1、up 翻 0。告警 pending 在杀后 10.1 秒（第一个评估周期），firing 下界 70.1 秒、首次轮询见到 firing 也在 70.1 秒。对前两轮（pending 13.9/14.2 秒、firing 73.9–75.1/74.2–75.5 秒），本轮快了约 4 秒，差在评估对齐的相位，仍在预注册 P-C 的 60–85 秒内。三轮独立活体把直接抓取档钉在 70–76 秒这一带，本文后续对照用本轮的 70.1 秒。

### 3.2 W 路径：序列在停推后又活了 301 秒

发送端被杀的那一刻，接收端什么都不知道——它没有抓取、没有连接状态可看，只有样本流断了这件事本身，而样本流断不断，要等查询时才见分晓。present 在接收端的即时查询里一直返回 1，直到杀后 301.0 秒的轮询才首次为空，absent() 同轮首次返回 1。告警随之整体后移：pending 在杀后 306.8 秒（回望过期后的第一个评估周期），firing 区间 366.8–371.1 秒。预注册主预测 P-W1（355–390 秒）命中。

把可见期换算到样本自己的时间轴上夹逼：发送端每 5 秒抓取一次，最后一批被推样本的时间戳只能落在杀前一个抓取间隔内；而发送端 SIGTERM 后 0.1 秒即退出，优雅停机的队列刷送最多把这个上界推到退出时刻——最后样本时间戳落在杀前 5 秒至杀后 0.1 秒之间。序列在该时间戳之后又存活了 300.9–306.0 秒，即 300 秒回望期加查询与评估对齐的零头，与自带时间戳路径的夹逼（303.1–308.1 秒）是同一个形状。两条路径殊途同归的原因也相同：样本的时间由别处决定，接收端本地没有任何记账动作能在停推时给序列打陈旧标记。

与 C 路径的差账：pending 晚 296.7 秒，firing 下界晚 296.7 秒，两个差值逐位相同——整条告警链平移了一个回望期（300 秒）减去 C 路径约 3 秒的陈旧化与对齐零头。firing 下界比值为 5.23 倍。

源头存活这一格单独记账（预注册 P-W3）：杀发送端之后立即直连 exporter /metrics，返回的 present 行值为 1，exporter 进程在整轮 W 里从未被动过。也就是说这 366.8 秒的盲窗里，被监控的对象一直健康地活着，坏掉的只有观测链的推送段——absent 在接收端响起时，它报告的不是「目标死了」，是「我已经六分钟没收到消息了」，这两件事在这一格里必须分清。

### 3.3 up 也被推了过来，然后冻在 1 上

预注册 P-W2 写的是：接收端全程查不到该 job 的 up 序列，因为接收端没有抓取记账。字面未中。实测接收端 89 个轮询里 67 个能查到 up{job="net-assurance-lab"}——原因是我落笔时漏了一件事：up 不是接收端本地生成的记账，它就是发送端抓取时产生的一条普通序列，和 present 一样被 remote write 原样推过来。

但这条预测的实质结论活了下来，而且比预注册写的更糟。发送端死后，接收端的 up 值在全部杀后轮询里只有一个取值：1.0。它最后一次非空出现在杀后 296.0 秒的轮询，首次变空与 present 同在 301.0 秒那个轮询。也就是说，接收端就算配了 up==0 规则，也永远等不到那个 0——样本流里最后一个 up 样本写的是 1，之后没有新样本改写它，它只能在回望期满后与其它被推序列一起消失。对照 C 路径：up 在杀后第一个轮询就翻 0 并保持可见（值变了、序列在）。同一个 up，抓取路径下是最快的死亡信号，远端写入路径下是一块冻住的墓碑。

这个错记进方法论账：P-W2 与 2026-10-27 篇那格预注册错误是同一族——都漏了一个机制。前者漏的是陈旧标记，这次漏的是「up 本身也是被推送的样本」。预注册的价值恰好在这里：错法被提前写死，实测才能把「哪一步推理漏了什么」指得清清楚楚。

## 4. 分析与取舍

四条路径的账现在可以并成一张表（同口径：for: 1 分钟、回望 300 秒）：

| 记账路径 | 陈旧标记由谁写 | absent firing | 快速信号 |
|---|---|---|---|
| 直接抓取 | 抓取层，停抓即写 | 70.1 秒（本轮；前两轮 73.9–75.5） | up 杀后 5 秒翻 0 |
| 录制规则复刻 | 规则评估层，停产即写 | 74.1–75.2 秒（2026-10-31） | 同抓取 |
| 样本自带时间戳 | 无人写 | 369.4–373.8 秒（2026-10-31） | up 杀后 5 秒翻 0 |
| 远端写入接收端 | 无人写 | 366.8–371.1 秒（本轮） | 无：up 冻结在 1 |

分档的判据只有一条：序列停产时，接收它的这台 Prometheus 本地有没有一个记账动作会给它打陈旧标记。抓取与规则评估都是本地记账，停了就打；时间戳与远端写入的时间都由别处决定，本地无从打起，只能等回望期自然过期。估一条防盲规则的盲窗之前，先问被盯序列的时间是谁记的账——这是这个系列四篇下来唯一需要记住的判断框架。

对中心化接收部署的三条可执行结论。第一，配在接收端的 absent 规则，盲窗预算一律按回望档写：约等于回望期加 for:，本口径下约 370 秒；按抓取档的 75 秒写值班预期，推送断掉那天会先盲六分钟再谈处置。第二，死亡信号要回到发送端去配：发送端本地有真正的抓取记账，它那边的 up 与 absent 都是快的；把发送端自身的健康（进程存活、remote write 发送成功率与队列积压，这类指标在发送端本地）纳入告警，而不是指望接收端从样本流里看出死亡。第三，若实在只能在接收端判断生死，唯一能缩短盲窗的杠杆是调小实例的回望期（--query.lookback-delta），但它是全实例一刀切，会同时改变所有即时查询的语义，拿全实例的查询行为换一条链的盲窗，多数部署不划算——这是取舍判断，本轮未实测该参数，证据等级 C，只作方向提示。

还有一条容易踩的误判要提前拆掉：给被推序列配一条「心跳指标加 absent」的链并不能变快。心跳也是被推样本，停推后同样活满回望期——本轮的 up 冻结就是现成的证据，心跳与业务序列在这一格里没有任何区别。

本轮没有改仓库里的任何规则文件，候选与实测材料留本项目 data/，处置与前作一致。

## 5. 局限与未解问题

- 发送端是完整的 Prometheus 抓取后转发，与生产里常见的 agent 模式走同一条 remote write 协议，但其他推送方（各类 exporter 直推、OTLP 网关、vmagent 等）的停推行为未逐个实测；按第 4 节的判据它们同属「时间由别处记账」一档，但队列刷送与退出行为各家不同，最后样本时间戳的夹逼会随之移动数秒，不移动档位。
- 死法是发送端被 SIGTERM 优雅退出（0.1 秒）。kill -9、宿主机断电或网络分区时发送端来不及刷队列，最后样本只会更旧、不会更新，盲窗按杀时刻口径只会更长数秒；未逐死法实测。
- 本轮 W 的死法是杀发送端、留 exporter；对称的另一格——exporter 死在存活的发送端之后——未测：那一格里发送端会继续把 up=0 推过来，present 却在发送端本地先被陈旧化、停产后在接收端按回望过期，up 与 absent 谁先响、差多少，是下一个可测的边界，已列入选题池。
- 抓取超时型死法（进程挂死、每次抓取走满超时）下各路径的陈旧化时刻仍未测，选题池里还欠着这一格，本轮的变量是记账路径、不是死亡过程。
- 只测了 present 一族与 up 两条序列；带高基数标签的被推序列族在回望期内的可见性按同一机制推断，未逐族实测。
- 回环单机、单发送端单接收端、for: 1 分钟的口径边界与前作相同；370 秒这个绝对数绑定回望期默认 300 秒，改了 lookback 配置的链按第 4 节框架重算，不直接搬数字。
