# 让智能体自己拿 Ghidra 干活：REA 实测复盘——170 个 MCP 工具、一次口令恢复，和它到不了的地方

作者：Guangyi Zhao
日期：2026-10-13
实测对象：morluto/rea（REA: Reverse Engineer Anything），npm 包 rea-agents 6.4.0，MIT 协议
实测环境：Ubuntu 24.04（Linux x64），Node 24.20，靶子为自写 C 程序编译的 ELF

## 一、问题与背景

逆向一个陌生二进制，传统做法是人坐在 Ghidra 前面，一页页翻汇编、跟交叉引用、猜函数是干什么的，再把结论一条条记下来。慢是其次，更麻烦的是结论和证据经常脱节：三天后回头看自己写的笔记，连我自己都说不清某句判断当时是看见了什么才下的。

REA 换了个分工。它不自己实现反编译，而是把逆向工具的操作面标准化成 MCP 工具，让 Claude Code、Codex、Cursor、Gemini CLI 这类智能体直接驱动工具：智能体提出问题，自己去开二进制、列函数、取伪代码、查引用、跑目标程序对比行为，最后拿回带证据的结果。人要做的，从“亲手翻每一页汇编”变成了“问对问题，再核对证据链”。

问题是，这套分工到底是真能干活，还是演示好看、实测拉胯？我花了一天，把它从安装跑到口令恢复，中间该踩的坑一个没躲。本文所有数字都来自当天的实测日志和 Evidence JSON，我在定稿前又逐项对了一遍原始文件；对不上的，一个不写。

还有一句要放在前面：本文只分析我自己写的程序。逆向的法律边界写在第五节，不是凑字数，是这条线必须守的规矩。

## 二、方法与架构

REA 可以拆成四层看，理解了这四层，后面的实测结果才有坐标。

第一层是智能体接入层。`rea mcp` 以 stdio 方式起一个 MCP 服务器。我用 JSON-RPC 做了真实握手：`initialize` 成功，`tools/list` 返回 170 个工具，名字是 `open_binary`、`analyze_function`、`batch_decompile`、`inspect_binary_layout` 这一类。`npx rea-agents setup` 负责把这个服务器注册进你选的智能体客户端，并附带装一套调查工作流指令，让智能体知道先查什么、后查什么、证据不够时怎么追问。

第二层是工作流层，CLI 和 MCP 共用同一套应用逻辑。CLI 有一百多个命令，`rea analyze`、`function`、`decompile`、`xrefs`、`search` 是原生分析的常用组合；`capture-process` 做行为捕获；`compare-process-captures` 把两次运行做差异对比。区别只在调用方式：CLI 每次是独立进程，结果要落盘再喂给下一步；MCP 是常驻会话。

第三层是分析引擎层，也是最容易被误解的一层。深度原生分析——反编译伪代码、函数档案——REA 自己不做，它桥接三家现成引擎：Ghidra 走一个放在 Ghidra 里的 Java 桥接脚本（ReaGhidraBridge），headless 模式，经本地 unix socket 通信，要求 Ghidra 12.1.x；Hopper 走 Python 桥接；IDA 走 IDA 自己的 MCP 注册，属于自带许可证、自带实例。REA 是 MIT 开源，但它不送你任何商业引擎的许可证，IDA 和 Hopper 该买还得买。Ghidra 免费，所以是本文实测的路线。

不依赖这三家引擎的，还有一类自带能力：离线 ELF 布局解析（调用你自己提供的 Python 环境，钉版 pwntools 4.15.0、pyelftools 0.33、Unicorn 2.1.2，只读解析节、段、符号、重定位和缓解措施，不执行目标）、Go 二进制内嵌元数据检查、JavaScript 和 .NET 的纯静态解析、以及用 PTY 真跑一遍目标的进程行为捕获。

第四层是证据层，我认为是它真正的设计重心。每次调用返回一个结构化 Evidence 记录：`evidence_id`、目标文件的 SHA-256、provider 及版本、原始结果、归一化结果、置信度（如 observed、inferred），还有一份明确列出的 limitations——哪些没查清、哪些是推断。它刻意不替你下判断。这和“一键出报告”类工具的气质完全不同，也是它敢让智能体自动追问的底气：每一步结论都能回溯到具体证据和未决项。

另外两个设计取向值得记一笔：按其官方说明，分析全程在本机跑，目标文件不上传到 REA 的服务器——这一点我没有做网络抓包验证，是引用官方口径，不是实测结论；且智能体拿到结果后怎么处理，取决于你用的模型服务商的数据政策，别把这两件事混为一谈。覆盖的目标面按其清单很宽，原生二进制之外还有 Go、.NET、JavaScript/Electron、Android APK、固件、WASM、EVM 字节码、SQLite、pcap 和崩溃转储——本文只实测了原生 ELF 这一条线，其余不在本文结论范围内。

靶子程序是我自写的 `checkme`，源码 30 行：命令行传入一个 key，`check_key()` 先比长度，再逐字节与内置常量异或累加，全零才放行。分别编出带符号版和 strip 版。正确口令是 13 字节——下面要看的，是在假定不知道答案的前提下，这条工具链能走到哪一步、又在哪一步必须靠人（或智能体）动脑子。

## 三、实测数据

### 3.1 就绪检查：开箱只有一半能用

`npm install --global rea-agents` 装的是 6.4.0，耗时约 1 分 51 秒。装完跑 `rea doctor`，结论很诚实：Node 与主机正常，但 Hopper、Ghidra、IDA 三个深度引擎全缺，调查工作流 skill 也未安装。换句话说，开箱状态只能用自带引擎的那部分能力，深度反编译必须先补引擎。doctor 把每项缺什么、怎么补都写清了，这一点比多数工具甩一个报错栈强得多。

还有一个贯穿全程的体感先说清：每个 rea 命令冷启动约 20 到 30 秒，连 `rea --help` 都要约 20 秒。至于慢在哪一步，我没有做过分段计时，只能推测与 Node 冷启动时加载完整工具目录有关，这里标为推测，不当结论写。交互式探索时如果按传统节奏狂点，很快就会烦躁；它适合的是想好问题、批量取证。

### 3.2 离线 ELF 布局：一次成型的拼图

先建一个 Python 虚拟环境装 pwntools，装到的版本恰好与 REA 钉版一致，然后用环境变量 `REA_PWNTOOLS_PYTHON` 指过去，跑 `rea inspect-binary-layout ./checkme --json`，约 22 秒返回约 45 KB 的 Evidence JSON。我定稿前重新打开这份 JSON 核过，数字如下：

- 31 个节、13 个段、48 个符号、11 条重定位，文件 SHA-256 锚定；
- 缓解措施逐项与编译实情相符：PIE 为真、NX 为真、栈不可执行、Full RELRO，canary 为假——源码里没有局部数组，确实不会有 canary。这一整组被标为 inferred，不冒充实测；
- 符号表直接点名 `main`、`check_key`、`strlen`，分析从哪下手一目了然；
- 附 12 条 limitations，例如链接地址不等于运行时地址、重定位清单完整性未知，没有藏着掖着。

这份输出和人手工跑 `checksec` 加 `readelf` 再拼图的等价，但一次成型且带证据标注。对 strip 版重复同一命令，符号只剩 9 个动态符号，就是 libc 导入那一类，`check_key` 和 `main` 的名字消失——符合预期，也划清了这条路线的边界：它只做布局层，不做函数恢复。

### 3.3 行为差分：不看代码先定位分歧点

第二步是黑盒行为捕获。对错误口令和正确口令各跑一次 `rea capture-process`（每次约 30 秒，含 PTY 启停），再用 `rea compare-process-captures` 对比。结果直接给出 first_divergence：终端维度第 0 号事件，左侧是 ACCESS DENIED，右侧是 ACCESS GRANTED，退出状态维度同时标为 changed。我对过原始对比 JSON，置信度标为 derived——它是两次捕获的推导结果，不是单次观察，这个标注是对的。

这一步的价值不在这个简单靶子上，而在顺序：先用行为差分确认“就是这个输入点决定成败”，再进静态分析。顺序对了，后面少走很多弯路。

### 3.4 Ghidra 深度分析：跑通了，但第一次是失败的

补引擎的成本先交账：本机原本没有 Java。下载 Temurin JDK 21（198 MB，约 2 分钟）和 Ghidra 12.1 发布包（542 MB，约 10 分钟），解压后约 874 MB，设好 `GHIDRA_INSTALL_DIR` 与 `JAVA_HOME`，深度路线才通。光下载就是约 740 MB，这个成本在评估要不要用这条线时不能装看不见。

设好之后跑 `rea analyze ./checkme --provider ghidra --json`：

- 第一次，约 3 分 26 秒，失败，错误码 `cleanup_incomplete`。Ghidra 本体日志显示导入和 post-analysis 都成功了，但 REA 在收尾时判定进程树里有无主或 PID 复用的进程，拒绝确认清理完成，整单按失败返回。我倾向于认为这是它的进程所有权校验与这台容器化环境不合，但这一点没有做根因定位，容器 PID 命名空间、进程回收方式等因素都没有逐一排除，所以只能记为未定位的失败，不能当成已查明的原因。如实记录，没有绕过，也没有把它写成成功。
- 第二次，约 2 分 50 秒，成功。但要注意，`analyze` 概览的归一化结果只有约 2.7 KB（落盘 JSON 全件约 4.4 KB），内容是段布局加上计数——它数出了 30 个过程、80 个字符串，却不给任何一个函数的伪代码。深挖必须继续点名调用。

于是点名 `check_key`：`rea function ./checkme check_key --provider ghidra --json`，约 2 分 42 秒，返回约 52 KB 的函数档案。里面有三样硬货：

一是反编译伪代码，与源码逻辑逐行对得上，变量名是 `param_1`、`DAT_00102004` 这类占位符：先 `strlen` 比长度是否为 0xd，也就是 13；再把输入逐字节与 `DAT_00102004` 起始的常量异或累加；累加为零才返回真。

二是完整汇编清单：函数体 76 字节，地址 0x101189 到 0x1011d4，这个数字我也对过原始 JSON。

三是调用关系：caller 是 `main`（0x1011d5），callee 是 `strlen` 的 PLT thunk，带入向引用地址。

闭环验证在这一步完成：伪代码说输入逐字节与 `DAT_00102004` 异或、累加为零才通过。在本文靶子的取值范围内（口令与常量都是普通 ASCII 字节，异或结果落在 0 到 127），累加为零等价于逐字节相等，读出该地址的 13 字节就是正确口令，用文件偏移读出来验证无误。严格说要补一句：伪代码里异或结果被截成 char 再累加，若字节取到高位值，有符号解释下理论上存在多处不相等却正负抵消、总和仍为零的构造——所以这段校验作为教学靶子没问题，换成真实口令校验就是个可利用的弱点，不能把“累加为零”当成密码学意义上的严格相等判定。从打开一个陌生二进制，到恢复出口令校验逻辑、再拿到口令，全程没有人工翻汇编。顺带一提，未配引擎时同一条 analyze 命令失败得也很规矩：结构化错误 `provider_unavailable` 加补救说明，而不是崩栈。

### 3.5 MCP 通道与耗时汇总

`rea mcp` 以 stdio 传输启动，JSON-RPC 的 `initialize` 握手成功，服务端标识 rea 6.4.0，`tools/list` 返回 170 个工具。这里要把口径说清：170 是目录数量，我实际调用并验证过的只是其中一小部分——二进制打开、布局检查、行为捕获与对比、Ghidra 分析与函数档案，其余一百六十多个工具本文没有逐一验过，不能拿目录数字冒充能力验证。CLI 与 MCP 是同一套工作流的两个入口，这一点在我用过的这部分工具上成立：CLI 能跑的，MCP 侧有对应工具。

全程耗时与结果汇总如下，全部来自当天日志：

- 仓库浅克隆（56 MB）：成功，约 28 秒
- `npm i -g rea-agents`：成功，约 1 分 51 秒
- `rea doctor`：成功，三引擎缺失如实报告，约 30 秒
- 离线 ELF 布局两次（带符号与 strip）：均成功，各约 22 秒
- 进程捕获两次加对比：成功，精确定位第一处行为分歧，各约 30 秒
- 未配引擎时 analyze：失败，结构化报错 provider_unavailable，属预期内，约 23 秒
- 补 JDK 21 与 Ghidra 12.1 下载解压：成功，约 740 MB，约 14 分钟
- Ghidra analyze 第一次：失败，cleanup_incomplete，引擎分析本身成功、收尾校验失败，约 3 分 26 秒
- Ghidra analyze 第二次：成功，仅段布局概览，约 2 分 50 秒
- Ghidra function 取 check_key 档案与伪代码：成功，逻辑完整恢复，约 2 分 42 秒
- MCP initialize 加 tools/list：成功，170 个工具，约 23 秒

## 四、分析与取舍

先说这套分工真正成立的地方。它把 Ghidra 的学习曲线拆成了两段：先通过智能体问答理解一个函数的行为和证据，再回头对照汇编和伪代码学工具本身。对正在学恶意代码分析、二进制基础的人，这个顺序比对着空白的 Ghidra 界面发呆高效得多。行为差分也是个值得养成的工作习惯，先行为、后静态，和动态分析里比对正常与异常样本是同一件事。

再说取舍，四个判断供要选型的人参考：

第一，引擎选 Ghidra 还是 IDA。REA 不改变引擎本身的性价比：Ghidra 免费、headless 友好，代价是本文实测的这套补装成本和分钟级的单次调用耗时；IDA 的恢复质量和生态另有优势，但许可证成本是你的，REA 的 MIT 协议不覆盖它。已有 IDA 许可证的团队走 IDA 接入，没有的先用 Ghidra 把工作流跑通，是我会给的顺序。

第二，CLI 还是 MCP。一次性脚本、留档复跑，用 CLI，证据落盘天然可追溯；让智能体连续追问、跨多步调查，用 MCP。理论上常驻会话能摊薄反复冷启动的成本，但本文没有测过 MCP 会话内连续调用的单步耗时——握手本身就花了约 23 秒，和一条 CLI 命令同量级——所以“MCP 更快”在本文里只是架构上的预期，不是实测结论，真要选型请自己测会话内延迟。另外，MCP 常驻会话意味着证据管理要靠会话语义，别把两种模式的产物混在一个目录里对账。

第三，证据契约值不值这个钱。每次结果带 limitations 和置信度，看起来是啰嗦，实际省的是复核时间：复核者不用猜哪句是观察、哪句是推断。我的判断是，在要出报告、要交付、要考试案例题这类场景里，这份啰嗦是净收益；在一次性随手看看的场景里，它就是纯开销。

第四，也是最要紧的：需要人动脑子的环节，工具一个都没替你做。读懂伪代码的语义——异或累加为零为什么等价于逐字节相等——是调用方做的；决定去读 `DAT_00102004` 的字节，是调用方做的；把长度 0xd 翻译成 13 个字符，也是调用方做的。REA 给证据和未决项，结论由调用方下。智能体读错伪代码，一样会得出一份貌似有据的错误结论。所以“智能体加 REA”不等于“无人逆向”，它等于“取证自动化加判断仍在人这边”。谁把后半句省了，谁迟早在这上面栽跟头。

## 五、局限与未解问题

能力局限，都是实测得出的：

- 冷启动慢。每条 CLI 命令 20 到 30 秒起步，Ghidra 会话级操作以分钟计。函数级结论必须逐个点名调用，成本随函数数量近似线性上升；大二进制全量深挖的时间账，本文没有测，不能外推。
- `analyze` 概览很浅，只有段布局。指望一条命令拿到函数级结论的人会失望，它的设计就是逼你带着问题去点名取证。
- strip、加壳、混淆目标面前，布局路线只剩动态符号；深度路线依赖引擎本身的恢复能力，REA 不额外变魔术。本文靶子是无混淆的自写程序，对真实世界样本的恢复率没有发言权。
- 进程所有权校验在容器化 Linux 上出现过一次 cleanup_incomplete 的失败，重跑才过。无人值守批量跑时要预留重试和失败留档，不能假设一次成功率。
- 本文只测了原生 ELF 一条线。APK、固件、WASM、EVM 等目标类型在 REA 的覆盖清单里，但我没跑过的，一律不下结论。
- 结论质量的上限取决于调用它的智能体和复核的人。证据链会跳步、伪代码会被读错，这类错误还带着 Evidence 编号，看起来格外可信，反而更危险。

法律与合规边界，务必守住：

- 只分析自己拥有或明确获授权的软件：自有程序、CTF 与靶场、自购且条款允许的样本、客户书面授权的交付物。
- 未授权逆向商业软件可能同时踩到三条线：软件许可协议的反逆向条款、美国 DMCA 第 1201 条反规避（绕过技术保护措施本身即可能违法，正当目的也有例外范围限制）、以及越权访问类法规。REA 仓库自带 DISCLAIMER，立场与此一致：合法研究、教育、互操作、软件保存。
- 商业引擎的许可证要自己合法取得，试用版的自动化与输出分享限制同样有效。
- 实务建议：学习就用 crackme、CTF 题和自己写的程序，就是本文的做法；工作里碰客户二进制，先确认授权文件在手，再动手。

未解问题留给后续实测：同一靶子换 IDA provider 的恢复质量差异、加壳样本上深度路线的实际表现、MCP 长会话里证据累积的上下文成本。这三个问题有数据之后，我会另文更新，不在本文里预支结论。
