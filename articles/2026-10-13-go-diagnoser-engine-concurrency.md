# 诊断任务该用多大的并发池：Go-Diagnoser-Engine 的并发模型实测与源码取舍

作者：Guangyi Zhao
日期：2026-10-13
实测对象：Go-Diagnoser-Engine（自有开源项目，github.com/Ezra-Zhao/Go-Diagnoser-Engine），Go 1.24，零第三方依赖
实测环境：Linux x86_64 虚拟机，2 vCPU，服务端与压测客户端同机

## 一、问题与背景

给一批节点做诊断，调用方最怕两件事：一是同步等结果，一次慢检查把请求拖死；二是无限制地开协程并发，任务一多先把自己压垮。所以我给 Go-Diagnoser-Engine 定的形态是异步的：POST /api/v1/diagnose 提交任务，拿一个 job ID 就走，之后轮询 GET /api/v1/jobs/{id} 取结构化结果。执行侧是一个有界的工作池：固定数量的 worker 从有界队列里取任务，单个任务内部的检查再并行扇出。

这套结构写出来不难，难的是回答数字问题：池子开多大？队列多深？一个任务挂三项检查，延迟是单项的三倍还是接近单项？队列满了该阻塞还是拒绝，拒绝的比例能不能预先算出来？本文不谈感觉，我把服务真跑起来压了一遍，再回到源码逐条对：哪些取舍被数据支持，哪些只是当时顺手写的、经不起细看。

先把丑话说在前面：这个项目目前是脚手架阶段，仓库 README 里就标着 scaffold。三项已注册的检查（connectivity、disk_usage、service_health）全是模拟实现——随机睡 50 到 200 毫秒，再以 90% 概率返回通过，每条结果都标了 SIMULATED。真实探针（ICMP/TCP 探测、磁盘采集、/healthz 查询）还在代码的 TODO 里。所以本文测的是并发骨架，不是诊断能力：骨架的吞吐、延迟、背压和竞态行为都是真数据；换上真实探针之后数字会变，第五节专门讲哪些结论会失效。

## 二、方法与架构

代码一共 523 行、6 个 Go 文件，go.mod 里只有模块名和 Go 版本，没有一行第三方依赖。分工是四块：cmd/server 是入口，读 PORT、WORKERS、QUEUE_SIZE 三个环境变量，装配各部件并负责优雅关机；internal/api 是 net/http 路由，用 Go 1.22 起的 method 加 pattern 写法注册三条路由；internal/engine 是工作池和检查注册表；internal/store 是并发安全的内存任务仓库；pkg/models 放共享类型。

并发模型有四条，都是刻意选的：

第一，固定工作池，不按请求开协程。worker 是长驻 goroutine，数量默认取 runtime.NumCPU()，可由 WORKERS 覆盖。并发上限因此是一个部署参数，而不是随流量漂移的变量。

第二，有界队列加快速失败。Submit 用 select 做非阻塞入队：队列满了立刻返回错误，API 层回 503，而不是让提交请求排队等。代价是调用方必须自己重试，这个取舍对不对，第三节的数据会说话。

第三，任务内扇出。runJob 把一个任务的检查各开一个 goroutine 并行跑，用一个按下标预分配的 results 切片收集结果，各协程写各自的下标，不用锁也不用结果通道，sync.WaitGroup 等齐后统一落库。每个检查单独套一个 30 秒的 context 超时，防止单项慢检查拖住整个任务。

第四，关机走协作式取消。main 收到 SIGINT 或 SIGTERM，先关 HTTP（15 秒超时），再调 engine.Shutdown：cancel 掉引擎 context，等 worker 排空，同样 15 秒封顶。

实验方法：把仓库原样复制到临时目录构建（普通版二进制 8.7 MB，-race 版 11 MB），用一个 Python 压测脚本驱动，脚本和原始结果都随本文归档。四组实验：A 组顺序提交 30 个单检查任务和 30 个三检查任务，比端到端延迟；B 组分别以 1、2、4、8 个 worker 并发提交 60 个三检查任务，测总耗时与每秒完成数；C 组把队列压到 5、worker 压到 1，一次性并发提交 30 个，数 202 和 503 的分布；D 组用 -race 构建，并发跑 100 个任务并高频轮询，检查竞态报告，并验证 SIGTERM 关机。

## 三、实测数据

### 3.1 扇出是真的并行：三项检查只贵了两成

A 组结果（各 30 个任务，worker 数 4）：

| 配置 | 端到端延迟均值 | p50 | p95 | 单项检查延迟均值 |
|---|---|---|---|
| 单检查（仅 connectivity） | 139.8 ms | 151.5 ms | 198.6 ms | 135.6 ms |
| 三检查（全选） | 166.5 ms | 169.9 ms | 201.9 ms | 126.0 ms |

检查从一项变三项，端到端延迟均值只涨了 19%。如果扇出是假的、实际串行跑，三项的延迟应该接近单项的三倍，也就是 400 毫秒量级。实测站在了并行这边，而且和理论能对上：单项延迟是 50 到 200 毫秒的均匀分布，三项并行时任务延迟取决于最慢的那一项，其期望是 50 + 150×3/4 = 162.5 毫秒，实测均值 166.5 毫秒，差 2.5%。单项检查延迟均值两组分别是 135.6 和 126.0 毫秒，也贴着均匀分布期望的 125 毫秒。这组数据同时验证了两件事：扇出确实并行，以及我对模拟延迟分布的描述没有写错。

多出来的那 27 毫秒（166.5 减 139.8）是什么？我没有做分段计时，只能给出推测：三个 goroutine 被同批定时器唤醒后的调度、结果落库的锁竞争都可能有份，这一条标为推测，不当结论。这个量级在模拟负载下不值得优化，但它提醒了一件事：扇出的收益来自检查之间互相等待的部分，一旦检查变成 CPU 密集，这个账要重算。

### 3.2 吞吐随 worker 数近乎线性——但别高兴太早

B 组结果（每组 60 个三检查任务，20 个客户端线程并发提交与轮询）：

| worker 数 | 总耗时 | 完成速率 | 相对单 worker 加速比 |
|---|---|---|---|
| 1 | 9.71 s | 6.2 任务/秒 | 1.0 |
| 2 | 4.98 s | 12.0 任务/秒 | 1.9 |
| 4 | 2.58 s | 23.2 任务/秒 | 3.7 |
| 8 | 1.34 s | 44.9 任务/秒 | 7.2 |

线性得有点过分：8 个 worker 在一台只有 2 个 vCPU 的机器上跑出了 7.2 倍加速。原因不在 Go 的调度有多神，而在负载的性质——模拟检查的全部工作就是睡，goroutine 挂在定时器上不占 CPU，worker 数量就是纯粹的并发度，速率自然等于 worker 数除以单任务时长。单 worker 的理论值是 1 / 0.1625 ≈ 6.15 任务/秒，实测 6.2，对上了。

这组数字能证明的只有一件事：池子本身没有隐藏的串行瓶颈（队列、落库的锁都没有成为卡点），并发度给多少就兑现多少。它不能证明真实诊断场景也能这么扩。真实探针里若有 CPU 密集的解析或分类逻辑，2 个 vCPU 下 worker 开到 4 以上大概率就饱和甚至倒退；若探针是网络 IO，瓶颈会先出现在目标端或连接数上。把此处的线性外推到生产，是这类压测最常见的自欺。

### 3.3 背压是可以预先算出来的

C 组把条件压到最紧：1 个 worker，队列深度 5，瞬间并发提交 30 个任务。结果：6 个拿到 202，24 个拿到 503。6 这个数字不是碰巧——1 个正在跑加 5 个在队列里，系统总接纳能力就是 worker 数加队列深度，第 7 个起全部快速失败，没有一个请求被挂住等待。被接纳的 6 个任务事后逐一轮询，全部正常完成，没有静默丢失。

快速失败的另一面在源码里能看到缺口：503 响应只有一个 error 文本，没有 Retry-After，也没有任何关于当前队列深度的信息，调用方只能盲目重试、自己定退避间隔。对一个给机器调用的 API，这是下一步该补的，比加任何新检查都优先。

### 3.4 竞态与关机

D 组用 -race 构建跑 100 个任务，提交、执行、轮询三路并发压在同一个内存仓库上：竞态检测器全程零报告，100 个任务全部完成。源码上这个结果站得住：仓库所有读写都过同一把 sync.RWMutex，Get 返回的是拷贝；扇出结果写不重叠的下标，WaitGroup 的 Wait 返回建立了 happens-before，落库时读到的结果是完整的。

有一处要如实交代：第一轮跑这个实验时，只有 92 个任务在我的轮询预算内返回完成。复查后确认是我压测脚本的轮询次数上限太紧（-race 构建的每次请求更慢），把预算放宽到 20 秒后重跑，100 个全部完成。把这一笔写出来，是因为它正是这类测试最容易误判的地方：观测工具的上限会伪装成被测系统的故障。

关机验证：空闲状态下发 SIGTERM，进程约 1.0 秒内打完 shutting down、all workers stopped、bye 三行日志退出。这里只验了空闲关机；有任务在飞时的关机行为，实测没覆盖，源码分析却发现了问题，放在下一节说。

### 3.5 一个顺手测出的小毛病：结果顺序不稳定

全选检查时，results 数组的顺序并不固定：抽了 20 个任务，出现两种顺序（connectivity、disk_usage、service_health 出现 17 次，service_health 打头的出现 3 次）。根子在 resolveChecks：全选时它遍历 map 生成检查列表，Go 的 map 遍历顺序本来就是随机的，而 results 按这份列表的下标填充，随机性就这样漏进了 API 输出。对调用方的要求因此是硬性的：必须按 name 匹配结果，不许按位置取。这个毛病修起来只要给注册表加一个有序切片，但它值得单独记一笔——凡是内部用了 map 的地方，随机性迟早会以这种方式渗到接口层。

## 四、分析与取舍

把四组数据和源码放在一起，这个骨架的取舍可以归纳成四条可复用的判断：

一，并发上限要显式，不要交给流量决定。固定池加有界队列让系统的接纳能力成为一个可计算的常数（worker 数加队列深度），压测里 503 的分界点和这个常数分毫不差。容量能算清，告警、扩容和限流策略才有依据；反之，每请求一协程的写法在低负载下更快，但天花板在哪儿，没人说得清。

二，异步加轮询换来的是提交路径的确定性。提交请求只做校验、建记录、入队三件事，队列满就立刻失败，HTTP 层 10 秒读超时、30 秒写超时永远不会被慢检查碰到。代价是调用方要写轮询，且没有推送机制时完成感知有延迟；长任务将来该补 SSE，仓库路线图里已经列了，但现在没有就是没有。

三，扇出的实现选了最省事且正确的原语组合。预分配下标切片加 WaitGroup，避免了结果通道的收集逻辑和锁，竞态检测零报告给这个选法背了书。前提是检查之间无共享写、无顺序依赖；哪天检查之间要传中间结果，这个结构要换，不要硬撑。

四，零依赖是刻意的约束，不是没来得及引。523 行只用标准库，路由靠 Go 1.22 的新 ServeMux，ID 靠 crypto/rand，好处是构建和审计的面都小，二进制 8.7 MB，go vet 和常规构建一次通过。代价同样明显：没有指标、没有限流中间件、没有结构化日志，这些生产件都得自己补或迟早引库。我的判断是脚手架阶段零依赖是对的，但这个判断的有效期只到真实探针落地为止。

源码里还有三个经不起细看的地方，按严重程度排：

第一，关机语义和任务状态对不上。engine.Shutdown 是先 cancel context 再等 worker，而 worker 的循环是 select 两路：context 取消和队列有货同时成立时选哪条是随机的。排队中未开工的任务可能被直接丢下，其状态永远停在 queued；在飞任务的检查会因 context 取消返回失败结果，但 runJob 照样调 SetResults 把任务标成 done——关机杀掉的任务和正常跑完的任务在状态上长得一模一样。内存存储下进程一退这些都无所谓，但路线图里要换持久化存储，这个语义债到时必须先还：至少给关机丢弃的任务一个明确的终态。

第二，内存仓库没有回收。所有任务记录只进不出，进程跑得越久、任务越多，map 就越大。脚手架无所谓，长驻服务必须加 TTL 或容量上限，这是确定性问题，不是会不会的问题。

第三，Submit 的 select 在引擎正在关机且队列恰好有空位时，可能随机选到入队成功这一路，随后这个任务大概率无人执行。窗口很窄，但属于那种平时不发作、一发作就查半天的类型。修法是入队前先单独判一次 context 状态。

## 五、局限与未解问题

本文最大的局限写在开头，这里展开：全部负载都是定时等待型的模拟检查。因此，吞吐线性扩展只证明了并发骨架没有串行瓶颈，不代表真实探针（网络探测、命令执行、结果解析）的扩展性；扇出的延迟收益以检查互相等待为前提，CPU 密集检查下会缩水；内存占用、GC 压力这类指标在模拟负载下测了也没意义，本文没有测。

实验方法上的局限也要交代：每组配置只跑了一批（A 组各 30 个任务，B 组各 60 个，C 组一次突发），没有多轮重复和置信区间；服务端与压测客户端同机，网络延迟近似为零，跨机调用的轮询成本不在数据里；机器是 2 vCPU 的共享虚拟机，邻居噪声无法排除，各数字应看量级和比例，不要抠小数点后一位。

未解问题留三个，都是下一步动代码时要先回答的：真实探针落地后，worker 数应该按 CPU 还是按目标端的承受能力定，两种定法的压测曲线要各跑一遍；队列深度和 503 比例、客户端重试策略之间怎么联动，需要一个带重试的客户端再压一轮；持久化存储换上之后，关机丢弃与状态终态的语义按第四节的分析修正，再补一组带在飞任务的关机实测。
